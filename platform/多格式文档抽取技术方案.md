# 多格式文档抽取技术方案

> 本方案用于将 PDF、Word、Excel、PPT、Markdown、TXT 等项目原料，可靠地转换为可确认、可追溯、可版本化的项目配置。

---

## 1. 目标与原则

多模态模型能够理解扫描页、图片、表格和复杂布局，但不能单独完成生产级文档抽取。完整系统还必须解决文件安全、结构解析、上下文切分、Schema 校验、来源定位、跨文档冲突、人工确认和版本化注入。

核心目标：

- 支持多种文档格式和不同解析路径。
- 将非结构化内容提取为统一的结构化产物。
- 每个结果均可定位到原文件、页码、Sheet 或单元格。
- 关键规则未经人工确认不得进入线上配置。
- 文档、抽取器和配置均可版本化、回滚和重新处理。

核心原则：

1. 原生解析优先，多模态模型按需增强。
2. 模型只生成候选抽取结果，不直接修改线上配置。
3. 无来源证据的抽取结果不得自动生效。
4. 真实冲突必须显式展示，不允许静默覆盖。
5. 原始文件和中间产物必须保留，以支持重新抽取。

---

## 2. 总体架构

```text
文件上传 / 飞书文档导入
          │
          ▼
文件识别与安全检查
          │
          ▼
原生结构解析 ──────┐
          │         │解析质量不足
          │         ▼
          │   OCR / 多模态版面理解
          └────┬────┘
               ▼
      统一 DocumentBlock
               │
               ▼
      结构化切分与引用关联
               │
               ▼
      目标化 Extractor
               │
               ▼
  Schema 校验 + 业务校验 + 来源绑定
               │
               ▼
    去重、合并与跨文档冲突检测
               │
               ▼
           人工确认
               │
               ▼
      版本化配置注入与回滚
```



### 2.1 多模态模型的职责

适合交给多模态模型：

- 扫描 PDF 的文字与版面理解。
- 图片、流程图、箭头和图例解释。
- 复杂表格阅读顺序和关系恢复。
- PPT 文本框、图形和备注的联合理解。
- 原生解析失败页面的补充识别。

不应只依赖多模态模型处理：

- 文件存储、权限和恶意内容检查。
- Excel 公式、隐藏 Sheet 和精确单元格关系。
- 大文档切分、重试和任务恢复。
- 结构化结果校验与业务冲突检测。
- 来源追溯、人工确认和版本管理。

## 3. 格式难点与处理策略


| 格式           | 主要难点                       | 推荐策略                     |
| ------------ | -------------------------- | ------------------------ |
| PDF          | 扫描页、双栏、跨页表格、页眉页脚           | 原生文本与坐标解析；扫描页使用 OCR/VLM  |
| Word         | 标题层级、批注、修订、嵌套表格            | OOXML 原生解析，保留样式和修订状态     |
| Excel        | 多 Sheet、合并单元格、公式、隐藏行列、颜色语义 | 直接解析工作簿结构；VLM 只辅助理解视觉语义  |
| PPT          | 文本框顺序、流程图、备注页、图形关系         | 原生提取元素及坐标，再使用 VLM 解释页面关系 |
| Markdown/TXT | 非标准表格、链接、弱结构文本             | 解析标题树和代码块，按章节切分          |
| 飞书文档         | 权限、嵌套块、表格和附件               | 使用飞书 API 拉取结构化块并保存版本信息   |

## 4. 核心数据模型



### 4.1 原始材料

```ts
interface RawMaterial {
  id: string
  spaceId: string
  filename: string
  mimeType: string
  sha256: string
  storageRef: string
  documentType?: string
  documentVersion?: string
  uploadedBy: string
  status: 'uploaded' | 'parsing' | 'extracting' | 'pending_review' | 'confirmed' | 'failed'
}
```



### 4.2 统一文档块

```ts
interface DocumentBlock {
  blockId: string
  type: 'heading' | 'paragraph' | 'table' | 'image' | 'list'
  text?: string
  table?: {
    rows: string[][]
    mergedRanges?: string[]
    formulas?: Record<string, string>
  }
  hierarchy: string[]
  references: string[]
  source: {
    materialId: string
    page?: number
    sheet?: string
    cellRange?: string
    slide?: number
    boundingBox?: number[]
  }
}
```



### 4.3 提取产物

```ts
interface ExtractedArtifact<T> {
  id: string
  materialId: string
  targetType: string
  extractorVersion: string
  value: T
  sourceRefs: Array<{
    blockId: string
    page?: number
    sheet?: string
    cellRange?: string
    quote?: string
  }>
  confidenceLevel: 'high' | 'medium' | 'low'
  validationErrors: string[]
  conflicts: string[]
  reviewStatus: 'pending' | 'confirmed' | 'edited' | 'rejected'
}
```

## 5. 完整开发流程



### 阶段 1：文件接入与安全检查

- 上传文件到对象存储，记录项目空间、上传者、哈希和版本。
- 校验真实 MIME 类型、文件大小和文件完整性。
- 扫描病毒、宏、压缩炸弹和异常嵌入对象。
- 对重复文件和新版本文档给出提示。
- 将文档内容视为不可信数据，防止 Prompt Injection。

产物：可审计的 `RawMaterial`。

### 阶段 2：文档识别与解析路由

根据文件格式和解析质量选择路径：

```text
原生解析质量高              → 直接使用原生结构
存在文本但布局复杂          → 原生结构 + 页面图片 + VLM
扫描件或图片型 PDF          → OCR + VLM
页面或工作簿解析失败        → 标记人工处理，不静默跳过
```

产物：原生解析结果、页面渲染图和解析质量报告。

### 阶段 3：标准化与结构化切分

- 将各格式统一转换为 `DocumentBlock`。
- 按标题、条款、完整表格和附录切分，不能只按固定字符数切分。
- 保留父级标题、表头、条款编号和来源坐标。
- 建立“见附录 A”等跨章节引用。
- 识别跨页表格，避免表头与数据行分离。

产物：带层级和来源的标准化文档块。

### 阶段 4：按目标执行结构化抽取

不同目标使用独立 Schema 和 Extractor：

- 领域词表。
- 模块分类体系。
- 写作原则和审核原则。
- 客户验收规范、评分规则和硬性失败条件。
- 严重等级和自动判级规则。
- 历史 Query 和来源标记。
- Log Parser 字段字典和解析规则草稿。

禁止使用一个万能 Prompt 同时抽取所有目标。

### 阶段 5：校验与来源绑定

Schema 校验示例：

```text
severity 必须属于 P0/P1/P2
score_threshold 必须在 0～100
sourceRefs 不能为空
```

业务校验示例：

```text
通过阈值不能大于总分
同一条件不能同时为 P0 和 P2
硬性失败条件不能被普通分数覆盖
模块名称必须存在于项目分类体系
文档声明 6 条规则但只抽出 5 条时必须报警
```

每个结果必须能够定位到原始文件位置。

### 阶段 6：跨文档合并与冲突检测

合并时考虑：

- 文档类型优先级。
- 文档版本和生效日期。
- 客户规范与内部规范的覆盖关系。
- 完全重复、近似重复和真实冲突。
- 基础配置与项目级覆盖关系。

发现冲突时生成候选项和推荐理由，但必须由人确认：

```json
{
  "type": "SEVERITY_CONFLICT",
  "candidates": [
    { "value": "P0", "source": "验收规范 v1.0" },
    { "value": "P1", "source": "历史 Bug 表" }
  ],
  "recommended": "P0",
  "reason": "正式验收规范优先于历史记录",
  "requiresReview": true
}
```



### 阶段 7：人工确认

- 普通术语允许批量确认。
- 验收阈值、硬性失败、严重等级和自动判级规则必须重点确认。
- 冲突和低置信度结果必须查看原文后处理。
- 保存模型原值、人工最终值、修改人和修改原因。
- 未确认产物不得进入线上项目配置。



### 阶段 8：版本化注入与回滚

确认后生成不可变配置版本：

```text
DomainGlossary benz@v5
CustomerAcceptanceSpec benz@v3
WritingPrinciples benz@v2
LogParserDraft benz-e300l@v1
```

每个合成任务和测试任务绑定实际使用的配置快照，后续配置修改不能改变历史结果。

### 阶段 9：质量评估与持续监控

建设人工专家标注的抽取黄金集，覆盖不同格式、复杂表格、扫描件和冲突文档。每次修改解析器、模型、Prompt 或 Schema 后重跑黄金集。

重点指标：


| 指标       | 含义               |
| -------- | ---------------- |
| 字段准确率    | 抽取结果中正确字段的比例     |
| 字段召回率    | 标准答案中的字段被成功抽出的比例 |
| 关键规则漏抽率  | 硬性验收规则未被抽出的比例    |
| 来源定位准确率  | 结果是否正确指向原文位置     |
| 冲突发现率    | 真实跨文档冲突被发现的比例    |
| 人工修改率    | 模型结果被人工修改的比例     |
| 单文档成本与耗时 | 生产处理效率和模型成本      |

## 6. 具体示例：验收规范与历史 Bug 表



### 6.1 输入是什么

一次抽取任务的输入不只是文件文本，而是“原始文件 + 用户指定的文档类型和提取目标 + 项目上下文”。本例包含两个原始文件。

#### 输入文件 A：验收规范 PDF

```json
{
  "filename": "奔驰语音助手验收规范-v1.0.pdf",
  "mimeType": "application/pdf",
  "documentType": "acceptance_spec",
  "extractionTargets": [
    "pass_policy",
    "hard_fail_conditions",
    "severity_rules"
  ]
}
```

PDF 第 12 页“3.2 通过判据”包含：

```text
总分 100 分，项目验收分数达到 80 分方可通过。
但出现以下任一情况时，无论总分多少均直接不通过：
1. 导航到错误目的地；
2. 用户要求取消导航但系统仍继续导航。
```

这里有三个容易漏掉的语义关系：

- `80` 是通过阈值，`100` 是总分，二者不能混淆。
- “但”后面的条款优先于分数规则。
- 两个编号条款是独立的硬性失败条件，不能合并成普通备注。

#### 输入文件 B：历史 Bug Excel

```json
{
  "filename": "奔驰-I2Max-历史Bug汇总.xlsx",
  "mimeType": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
  "documentType": "historical_defects",
  "extractionTargets": [
    "severity_rules",
    "rootcause_categories"
  ]
}
```

工作簿包含 `严重等级定义` Sheet，其中 `A2:A3` 是合并单元格：

| 单元格 | 原始值 |
|---|---|
| `A1` | 模块 |
| `B1` | 条件 |
| `C1` | 严重等级 |
| `A2:A3` | 导航 |
| `B2` | 完全无法使用 |
| `C2` | P0 |
| `B3` | 部分目的地失败 |
| `C3` | P1 |

原生 Excel 解析器必须将合并单元格中的“导航”向下关联到第 2、3 行。如果只读取单元格显示值，第 3 行的模块可能被错误解析为空。

#### 任务级输入

平台还会附加项目上下文：

```json
{
  "spaceId": "benz-i2max",
  "materialIds": ["material-pdf-001", "material-xlsx-001"],
  "projectTaxonomy": ["导航", "车控", "媒体"],
  "allowedSeverities": ["P0", "P1", "P2"],
  "documentPriority": {
    "acceptance_spec": 100,
    "historical_defects": 60
  },
  "requireHumanConfirmation": true
}
```

### 6.2 输入经过哪些处理

#### 步骤 1：接入与安全检查

系统保存原始二进制文件并生成哈希，检查文件类型、大小、损坏、恶意宏和重复上传。此时不进行语义抽取。

```json
{
  "materialId": "material-pdf-001",
  "sha256": "...",
  "storageRef": "materials/benz-i2max/material-pdf-001",
  "securityStatus": "passed"
}
```

#### 步骤 2：原生解析与质量路由

PDF 解析器提取文字块、页码、标题层级和坐标；Excel 解析器读取 Sheet、合并范围、单元格值、公式和隐藏状态。

如果 PDF 第 12 页有可用文本层，则不调用 VLM；如果是扫描页或条款层级无法恢复，则渲染该页并调用 OCR/VLM。多模态模型只处理需要视觉理解的页面，不重复处理整个文件。

```json
{
  "materialId": "material-pdf-001",
  "nativeTextCoverage": 0.98,
  "layoutConfidence": 0.96,
  "route": "native_parser",
  "fallbackPages": []
}
```

#### 步骤 3：转换为统一文档块

PDF 条款转换为：

```json
{
  "blockId": "pdf-001-p12-b07",
  "type": "list",
  "hierarchy": ["3 验收规则", "3.2 通过判据"],
  "text": "总分100分，达到80分方可通过；出现任一硬性条件时直接不通过……",
  "source": {
    "materialId": "material-pdf-001",
    "page": 12,
    "boundingBox": [82, 214, 514, 486]
  }
}
```

Excel 表格转换为：

```json
{
  "blockId": "xlsx-001-severity-a1-c3",
  "type": "table",
  "table": {
    "rows": [
      ["模块", "条件", "严重等级"],
      ["导航", "完全无法使用", "P0"],
      ["导航", "部分目的地失败", "P1"]
    ],
    "mergedRanges": ["A2:A3"]
  },
  "source": {
    "materialId": "material-xlsx-001",
    "sheet": "严重等级定义",
    "cellRange": "A1:C3"
  }
}
```

#### 步骤 4：结构化切分与上下文补齐

系统按完整条款和完整表格切分，不把“80 分通过”与“硬性条件直接失败”拆到两个无关联片段。每个片段附带父级标题、文档类型和项目枚举。

此时形成两个 Extractor 请求：

```text
AcceptancePolicyExtractor
输入：PDF 的 3.2 通过判据块
输出目标：scoreThreshold、totalScore、hardFailConditions

SeverityRuleExtractor
输入：Excel 的严重等级定义表
输出目标：module、condition、severity
```

#### 步骤 5：LLM 结构化抽取

`AcceptancePolicyExtractor` 的 Schema 要求硬性条件逐条输出，并绑定来源：

```json
{
  "totalScore": 100,
  "scoreThreshold": 80,
  "hardFailConditions": [
    {
      "code": "wrong_destination",
      "description": "导航到错误目的地",
      "sourceRefs": ["pdf-001-p12-b07#item-1"]
    },
    {
      "code": "cancel_navigation_not_effective",
      "description": "用户要求取消导航但系统仍继续导航",
      "sourceRefs": ["pdf-001-p12-b07#item-2"]
    }
  ]
}
```

`SeverityRuleExtractor` 输出：

```json
{
  "rules": [
    {
      "module": "navigation",
      "condition": "completely_unavailable",
      "severity": "P0",
      "sourceRefs": ["xlsx-001-severity-a1-c3#row-2"]
    },
    {
      "module": "navigation",
      "condition": "partial_destination_failure",
      "severity": "P1",
      "sourceRefs": ["xlsx-001-severity-a1-c3#row-3"]
    }
  ]
}
```

#### 步骤 6：程序化校验

模型输出后执行确定性检查：

```text
0 <= scoreThreshold <= totalScore                       通过
severity 属于 P0/P1/P2                                 通过
module 存在于项目分类体系                              通过
每个抽取项至少有一个 sourceRef                         通过
原文编号列表有 2 项，抽取结果 hardFailConditions 也有 2 项  通过
```

如果模型只抽出阈值，漏掉硬性失败条件，系统必须产生 `INCOMPLETE_EXTRACTION`，不能进入自动注入流程。

#### 步骤 7：去重与冲突检测

系统将候选结果与现有项目配置及其他文档比较。例如验收规范将“完全无法导航”定义为 P0，而另一份历史表定义为 P1，则生成冲突记录，不静默选择其中一个。

正式验收规范可以作为推荐值，但 `requiresReview` 仍为 `true`。

#### 步骤 8：人工确认

确认页面同时展示：

- 结构化候选值。
- PDF 页码、原文高亮或 Excel 单元格。
- 校验结果和跨文档冲突。
- 模型置信等级。
- 接受、编辑、拒绝操作。

人工确认记录模型原值、最终值、确认人和修改原因。

### 6.3 输出是什么

系统存在两级输出：待确认提取产物和确认后的正式配置。

#### 输出 A：待确认提取产物

```json
{
  "artifactId": "artifact-acceptance-001",
  "targetType": "customer_acceptance_spec",
  "extractorVersion": "acceptance-extractor@1.2",
  "reviewStatus": "pending",
  "confidenceLevel": "high",
  "validationErrors": [],
  "conflicts": [],
  "value": {
    "passPolicy": {
      "totalScore": 100,
      "scoreThreshold": 80,
      "hardFailConditions": [
        "wrong_destination",
        "cancel_navigation_not_effective"
      ]
    },
    "severityRules": [
      {
        "module": "navigation",

        "severity": "P0"
      },

        "module": "navigation",
```

#### 输出 B：确认后的正式配置

项目负责人确认后，系统生成不可变配置版本：

```json
{

```

后续合成任务和测试任务只引用该配置版本号。即使重新上传文档或修改抽取器，历史任务使用的 `benz-v3` 也不会改变。

## 7. MVP 范围

第一阶段建议支持：

- Markdown、TXT、结构规范的 Excel、文本型 PDF 和普通 Word。
- 领域词表、验收规则、历史 Query 三种抽取目标。
- 原生解析、结构化分块、LLM Schema 抽取、来源定位和人工确认。
- 所有关键产物人工确认后生效。
