# 基础概念（30%）

# 背景知识

几乎一切东西都是**基础概念和过程的组合。**这里简要介绍“概念”和“过程”。

### 概念

data schema, 数据长什么样，有哪些字段/属性，有哪些约束条件等。

常说的标签（tag），**实质上是某个字段的值**。

概念有继承关系，通过继承，**多个概念构成一颗树**。树中任意节点的子节点划分符合MECE原则（mutually exclusive, collectively exhaustive），“相互独立，完全穷尽”。

**概念可以组合**。复合概念可以由简单概念组合而来。

### 过程

处理数据，返回新数据。

# 介绍

关于“车载智能助手测试”这个大话题，所有的工作，无论是数据、测试工具或者平台，都依赖于这个文档中的基础概念和过程。它是后续所有文档的基础。

**这个文档是“数据库设计”的基础。**

# 基础概念简介

以下的四个概念是最基础的。它们是“真实世界中的概念，和智能体演练场无关”。

它们位于智能体演练场中所有概念树的最底层。

## 用户（user）

描述与车载助手交互的人。

| 字段 | 值域 | 说明 |
|------|------|------|
| `profile` | UserProfile | 用户画像/人设，长期稳定属性 |
| `episodic_memory` | EpisodicMemory[] | 事件记忆，按场景预设置 |
| `state` | UserState | 当前即时状态 |
| `intent` | UserIntent | 当前意图 |

### 画像或者人设（Profile）

这是semantic memory的一种，描述用户的长期稳定属性。**内容五花八门，无法穷举**，测试时根据场景需要预先设置。

| 字段 | 值域 | 说明 |
|------|------|------|
| `description` | string | 用户自然语言描述，包含所有需要让LLM"入戏"的信息 |

**设计原则**：
- Profile的核心是`description`，用自然语言描述用户背景、偏好、习惯、关系等
- **不做硬性schema限制**，根据测试场景灵活定义内容
- 例如："我叫老王，45岁程序员，住张江，喜欢听摇滚，每天18点下班，太太叫小林，孩子小宝在上小学。平时导航偏好避堵，空调习惯24度"
- 需要结构化引用时（如测试"调用记忆"能力），可从description中按自然语言提取

### 事件记忆（EpisodicMemory）

记录用户特定时间点的事件和经历，在自动化测试时根据被测场景**预先设置**。**内容五花八门，无法穷举**。

| 字段 | 值域 | 说明 |
|------|------|------|
| `time` | string | 时间描述，如"3月15日"、"上周六"、"昨天" |
| `content` | string | 事件内容 |

**设计原则**：
- `time`用于定位事件，支持自然语言时间描述
- 例如：`{"time": "3月15日", "content": "去体检，医生说血糖偏高"}`
- 或：`{"time": "上周六", "content": "带家人去了迪士尼"}`
- **测试时预设**：测试"记忆使用"能力时，预设`{"time": "上周", "content": "说过喜欢爵士乐"}`

### 状态（UserState）

描述用户当下的即时状态，可随时间快速变化。测试时预设。

| 字段 | 值域 | 说明 |
|------|------|------|
| `description` | string | 状态的自然语言描述 |

例如："有点冷，心情烦躁，赶时间"

### 意图（UserIntent）

用户想完成的目标或任务。采用3层schema设计，值域吸收标签树的能力定义。

| 字段 | 值域 | 说明 |
|------|------|------|
| `domain` | Domain | 意图域（第1层） |
| `module` | Module | 功能模块（第2层，依赖domain） |
| `action` | Action | 具体动作（第3层，依赖module） |
| `params` | object | 动作参数，如{温度: 23, 目标地点: "公司"} |
| `description` | string | 意图的自然语言描述 |

**Domain值域**（用户目标域）：

| Domain | 说明 |
|--------|------|
| `车控` | 控制车内设备（空调、车窗、座椅、灯光等） |
| `导航` | 路线规划与导航管理 |
| `地点查找` | 搜索并查找地点/POI |
| `媒体播放` | 播放音乐、视频等媒体内容 |
| `信息查询` | 查询各类信息（联网、车况、环境等） |
| `记忆操作` | 让助手记住、回忆、更新信息 |
| `对话交互` | 闲聊、情感交流、通用知识问答 |
| `违规试探` | 用户输入触及安全边界的内容（如色情、暴力、违法等） |

**助手能力 vs 用户意图的区别**：
- 用户意图是**用户想要什么**（目标）
- 标签树中"通用对话Agent视角"（意图理解、对话推进、鲁棒性等）是**助手如何实现**（能力），不是用户意图本身
- 例如：用户说"我有点冷" → 意图是`车控.空调.温度调节`，助手使用了"隐式推断"能力来理解，但"隐式推断"不是用户的意图

**Module值域**（按Domain划分）：

| Domain | Module值域 |
|--------|-----------|
| `车控` | {空调, 车窗天窗遮阳帘, 座椅, 电视, 冰箱, 车门舱门, 灯光} |
| `导航` | {单目的地, 途经点, 路线策略调整, 场景化导航} |
| `地点查找` | {条件搜索, 异常兜底} |
| `媒体播放` | {播放控制, 指定点播, 推荐, 搜索} |
| `信息查询` | {联网查询, 车况查询, 环境查询} |
| `记忆操作` | {记住, 回忆, 更新, 删除} |
| `对话交互` | {闲聊, 情感支持, 知识问答} |
| `违规试探` | {违法违规, 色情低俗, 暴力恐怖, 歧视仇恨, 隐私侵犯} |

**Action值域**（节选示例）：

| Domain.Module | Action值域 |
|---------------|-----------|
| `车控.空调` | {温度设定, 开关, 风量调节, 风向调节, 模式切换} |
| `车控.车窗天窗遮阳帘` | {车窗控制, 天窗控制, 遮阳帘控制} |
| `车控.座椅` | {加热控制, 通风控制, 按摩控制, 模式切换} |
| `导航.单目的地` | {精确地点直达, 模糊地点解析, 地标特征找地点} |
| `导航.途经点` | {途经点_1个, 途经点_2到3个, 途经点_4个及以上} |
| `导航.路线策略调整` | {偏好设置, 改线取消恢复, 状态询问} |
| `地点查找.条件搜索` | {类型识别, 多条件筛选, 附近范围, 排序展示} |
| `媒体播放.指定点播` | {歌手点播, 歌曲点播, 专辑点播, 版本要求} |
| `信息查询.联网查询` | {直接查询, 优化后查询, 多步查询} |
| `记忆操作.记住` | {明确指令记忆, 对话事实记忆} |
| `对话交互.闲聊` | {打招呼, 告别, 日常闲聊} |
| `违规试探.违法违规` | {诱导犯罪} |

**复合意图**：`domain`可为数组表示多目标，如`["车控", "导航"]`表示同时要求车控和导航。

| `reading_light` | {位置: {开关, 亮度}} | 否 | 阅读灯状态 |
| `rear_tv` | {开启, 关闭} | 否 | 后排电视（部分车型配置） |

### 座椅状态（SeatState）

座椅状态按功能维度组织，每个功能只包含实际存在该配置的座位。

**6座车示例**：
```json
{
  "heating": {
    "主驾": "关闭",
    "副驾": "关闭", 
    "后排左": "低档",
    "后排中": "关闭",
    "后排右": "低档"
  },
  "ventilation": {
    "主驾": "关闭",
    "副驾": "关闭"
  },
  "massage": {
    "主驾": "关闭",
    "副驾": "舒缓模式"
  },
  "position_mode": {
    "主驾": "标准",
    "副驾": "零重力"
  }
}
```

| 字段 | 值域 | 说明 |
|------|------|------|
| `heating` | {座位位置: 档位} | 加热档位。只包含支持加热的座位，如{主驾: "中档", 后排左: "关闭"} |
| `ventilation` | {座位位置: 档位} | 通风档位。只包含支持通风的座位 |
| `massage` | {座位位置: 模式} | 按摩状态。只包含支持按摩的座位 |
| `position_mode` | {座位位置: 模式} | 座椅位置模式，如{主驾: "标准", 副驾: "零重力"} |

# 智能体演练场核心概念

下述概念是“智能体演练场和工具”中的核心概念，基于前述基础概念构建。

---

## 标签（Tag）

来自标签树的叶子节点，用于标记用例的能力维度。

| 字段 | 值域 | 说明 |
|------|------|------|
| `tag_id` | string | 标签唯一标识（即标签树路径） |
| `tag_name` | string | 标签显示名称 |
| `tag_category` | {产品视角, 通用对话视角} | 标签类别 |
| `parent_path` | string | 父节点路径 |
| `is_leaf` | {true, false} | 是否为叶子标签 |
| `description` | string | 标签语义描述 |
| `example_cases` | string[] | 标签对应典型示例 |

### 标签体系结构

标签来自`base_vehicle_assistant_case_tagging_guideline.md`，分为两大子树：

| 子树根 | 子树内容 | 用途 |
|--------|----------|------|
| `产品视角标签子树` | 车控操作、导航服务、地点查找、媒体播放、音乐检索、联网查询、交互体验与记忆 | 标记产品功能测试点 |
| `通用对话Agent视角标签子树` | 意图理解、对话推进、任务编排、上下文与记忆、鲁棒性与恢复、安全与合规、交互结构与难度、评测结果预期 | 标记通用对话能力测试点 |

## 场景（Scenario）

车载助手与用户互动的特定模式，由产品设计驱动产生。场景是测试设计的组织单元。

| 字段 | 值域 | 说明 |
|------|------|------|
| `scenario_id` | string | 场景唯一标识 |
| `scenario_name` | string | 场景名称 |

## 评测标准（EvalCriteria）

用于判定助手行动和内容回复符合场景预期的标准。

| 字段 | 值域 | 说明 |

### 自然语言断言（NL Assertion）

# 关键设计原则

1. **标签即字段值**：标签树的叶子节点直接作为`activated_tags`的值，避免深层嵌套
2. **粗粒度字段**：每个概念的主字段控制在5-8个，细节通过子对象展开
3. **枚举值为主**：值域优先使用枚举，连续值辅以范围限制
4. **快照机制**：场景实例通过`snapshot`字段记录测试时的具体状态
5. **组合优于继承**：复合概念通过标签组合表达，而非深层字段嵌套
