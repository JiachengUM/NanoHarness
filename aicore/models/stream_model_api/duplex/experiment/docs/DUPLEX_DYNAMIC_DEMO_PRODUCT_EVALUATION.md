# Duplex + DynamicTask Demo 产品评估报告

## 1. 产品结论

Duplex + DynamicTask 已达到**可面向客户演示、内部试用和场景化 PoC 的初步成熟状态**。

它不再只是“实时语音模型接几个工具”的技术样例，而是一套完整的全双工语音 Agent Demo：

> 用户可以自然说话、随时打断、切换闲聊或方言；耗时工具在后台执行，前台立即确认，任务完成后
> 主动回来播报，并支持取消和连续修改。

相较此前 v2 的 ASR + 文本 Agent + TTS 级联方案，新方案同时保留了 Duplex 原生声学交互能力
和 v2 接近的异步任务生命周期。对于 Demo 产品，当前主要能力链路已经闭环；剩余问题集中在
工具结果表达质量和主动唤醒效率，属于可继续优化的工程边界，不再是方案不可行的架构阻塞。

## 2. 产品定位

### 核心价值

**能聊、能听、能打断、能办事，任务完成后还会主动回来汇报。**

这套 Demo 适合展示：

- 车载语音助手：车控、导航、天气、地点和内容搜索；
- 全双工智能助手：用户不必等待工具结束，可以继续说话或提出新需求；
- 异步任务 Agent：长任务先确认、后台执行、完成后主动播报；
- 个性化语音交互：四川话等语言风格、唱歌、闲聊和任务问答自然切换；
- 可控任务体验：取消旧任务、修改查询条件、只保留最新目标。

### 对用户的直接感知

传统级联方案更像“语音输入一个文本机器人”；Duplex + DynamicTask 更接近一个始终在场的
语音助理：它能听懂说话方式和语气，回复可以被打断，任务等待期间不必沉默，工具结果也不是
冷冰冰地显示在界面上，而是由同一个语音角色主动继续对话。

## 3. 实验依据

本结论来自 12 个场景、14 个独立 Dynamic session，并与 14 个 StreamTask 同步 session 对照。

| 指标 | DynamicTask 实测 | 产品含义 |
|---|---:|---|
| 业务 FC | 38 | 覆盖搜索、POI、车控、导航、音乐和并发任务 |
| 进入 TaskManager 的任务 | 36 | 2 个非法 schema 在入口即被拒绝，没有错误启动 worker |
| 任务终态 | 25 success + 11 cancelled | 36/36 全部闭环，无悬空任务 |
| 结果写回 | 25 update / 25 ACK | 工具结果全部被 Duplex 服务端确认接收 |
| 主动激活 | 22 / 22 成功触发推理 | 任务完成后能够主动恢复回复 |
| 成功取消后的迟到结果 | 0 / 11 | 已取消任务不会继续污染对话 |
| 多结果合并 | 3 组 | 同一问题的多个并发结果可合并播报 |

代表性样例：

- **Case 02**：同时打开空调并导航；两项并发完成后一次完整回复。
- **Case 05**：一次搜索支撑连续三轮歌曲追问，证明工具事实进入了可持续上下文。
- **Case 07**：香港天气 pending 时插入车控；车控先回复，天气稍后仍能主动回来播报。
- **Case 09**：旧台风查询被真实取消，新查询重新建立，旧任务没有迟到结果。
- **Case 11_02**：连续四次修改天气目标，只保留最终贵阳查询。
- **Case 12**：四川话连续完成天气、电影、演唱会、车控 + 温度以及唱歌交互；四个工具轮
  均能基于结果回答，长对话连续性良好。

## 4. 已初步成熟的产品能力

### 4.1 基于工具事实回答

真实结果通过 `conversation.item.update` 写回原问题，再由 Duplex 继续推理。25 次结果写回
全部收到 ACK，Case 05 又证明结果能被后续普通语音轮继续使用。

天气、歌曲、台风、车控、导航、电影和演唱会等主要样例已经多次给出有事实依据的回复。
这说明“异步结果模型不可见”的根本问题已经解决，当前系统具备真正的工具增强问答能力。

### 4.2 秒回占位显著改善等待体验

DynamicTask 在工具提交后立即闭合原 FC 轮次，并快速播报“正在查询/正在执行”，不需要让
Duplex 在十秒级工具调用期间一直等待。

这带来两个直接收益：

1. 用户马上知道请求已被接受，产品不再表现为卡住或没听懂；
2. 工具任务已经由 TaskManager 独立持有，即使等待期间出现环境声或新一轮 ASR，也不会让
   真实结果丢失。

同步版在工具 pending 期间记录到 4 次 `transcription.started` 无 completed，并多次出现旧工具
结果上行后不再续答。新 Dynamic 链路中没有工具结果因为这种等待期误触而丢失。对用户而言，
长任务已经从“沉默等待且容易断轮”变成“立即确认、完成后主动告知”，体验提升非常明显。

### 4.3 异步任务能力已经接近 v2

当前链路已经具备 v2 异步 Agent 的主要运行语义：

- 工具提交后返回任务占位；
- TaskManager 持有跨轮任务状态；
- 多个工具并发执行；
- 每个任务独立 success / cancelled；
- 根据准确 task_id 取消；
- 修改任务时取消旧目标并创建新目标；
- 成功取消后抑制迟到结果；
- 任务完成后把 observation 投影回模型上下文。

11 次真实取消全部没有迟到 backfill，连续修改只保留最终任务也已实测成功。对于 Demo 所需的
后台查询、取消和修改，能力已经足够完整。

### 4.4 原生语音体验优于 ASR + TTS 级联

Duplex 同时承担语音理解、对话推理和语音生成，因此能保留级联方案较难稳定实现的交互特征：

- 用户可以在模型说话时自然打断；
- 闲聊、唱歌、工具问答可以随时切换；
- 四川话等会话风格能够跨多个工具轮持续；
- 口语化追问能够利用前文，不必重新组织成完整指令；
- 工具结果由同一个声音和角色继续回答，交互人格更统一。

Case 01 验证了连续打断和闲聊切换；Case 12 验证了四川话、工具问答、车控、天气和唱歌在一个
长 session 内连续运行。即使第一次四川话唱歌需要用户纠正，模型也能立即恢复风格。这类体验
已经明显优于“先转文字、再调用 Agent、最后单独合成语音”的拼接感。

## 5. 当前产品边界

### 5.1 事实遵循仍受工具结果质量影响

模型已经能看到工具结果，但不保证每次都能从长、杂乱或相互冲突的内容中选出最准确结论。
目前的反例主要集中在 POI、多个数字来源和旧任务结果归属：

- Case 04 的工具明确推荐“大森”，模型却回答了结果外的“鮨政”；
- Case 08 混用了不同日期的温度；
- Case 09 没有引用真实店名，又补充了结果中不存在的距离；
- Case 10 的参数重试把 1000 错成 10000；
- Case 11 一次迟到的香港结果被按当前上海意图作答。

这些问题不再是上下文传输失败，而是输入信息密度、结构和模型选择问题。短期最有效的改进不是
继续扩充 prompt，而是优化工具输出：

- 先给唯一结论，再给必要证据；
- POI 等结构化工具只输出筛选后的少量候选；
- 对日期、价格、评分和地点提供稳定字段，不让模型从长文本中二次抽取；
- 对冲突来源在工具侧完成排序，并明确“采用结论”；
- 限制原始网页正文，把来源链接或详情留给按需展开。

这是可控且收益明确的优化方向。对于 Demo，可优先选择天气、车控、导航、内容搜索等输出稳定
的工具，并为 POI、价格类工具增加结构化摘要。

### 5.2 主动回复仍依赖本地 PCM

Duplex 暂无原生“追加外部 observation 后主动创建回复”的接口。当前实现通过播放逐工具 PCM，
让服务端产生一个新的音频轮次并读取刚更新的结果。

这条路径已经稳定工作：22 次激活全部触发推理，且没有在模型正在播放时抢断下行回复。但一次
激活大约会占用 2 秒音频窗口；这段时间用户输入不适合同时进入。Case 06 也出现过 PCM 和真人
追问合并成同一 ASR。

短期内这不是 Demo 阻塞：用户刚收到“正在查询”的反馈，结果完成时再用一句短提示恢复对话，
整体仍比同步长时间沉默更自然。工程上可以继续压缩：

- 把逐工具提示缩短为更短、更易识别的固定短语；
- 同一 question 的多个结果继续合并激活，减少 PCM 次数；
- 在前端播放、麦克风门控和用户正在说话状态之间增加更精确的调度；
- 将来厂商开放原生主动推理接口后，直接替换 PCM 激活，不影响 TaskManager 与 update 主链路。

### 5.3 Demo 使用时的轻量约束

为了获得稳定演示效果，建议：

- 取消指令带明确目标，例如“取消天气查询”，避免只说“取消任务”；
- 优先使用输出经过摘要的工具，不直接回灌超长原始网页；
- 保持回声消除或基础麦克风门控，避免扬声器内容重新进入输入；
- 不把高风险价格、医疗、法律等严格事实场景作为当前 Demo 的核心营销案例。

这些约束不会削弱 Demo 的核心卖点，反而能更集中地展示全双工和异步 Agent 的优势。

## 6. 与现有方案的产品对比

| 体验维度 | v2 ASR + Agent + TTS | Duplex StreamTask | Duplex + DynamicTask |
|---|---|---|---|
| 自然打断与声学交互 | 依赖多模块拼接 | 原生优秀 | 原生优秀 |
| 方言、唱歌、闲聊切换 | 能力割裂或需单独实现 | 原生具备 | 原生具备 |
| 工具等待反馈 | 可做，但需额外前端协议 | 通常长时间等待 | 快速占位确认 |
| 跨轮异步任务 | 完整 | 旧结果容易失去续答 | TaskManager 持有并主动回报 |
| 取消与修改 | 已具备 | 无真实取消 | 已接近 v2，11 次取消实测闭环 |
| 结果主动播报 | Agent 可直接 create response | 依赖原 FC continuation | update + PCM 主动恢复 |
| 系统复杂度 | ASR、Agent、TTS 多链路 | 最简单 | 单一语音模型 + 异步兼容层 |
| 用户感知 | 功能完整但有级联感 | 自然但不适合长任务 | 自然语音与异步任务兼得 |

DynamicTask 并不是为了替代 StreamTask 的所有场景。StreamTask 仍是最短的同步基线；当产品需要
耗时工具、继续对话、取消修改和主动通知时，DynamicTask 才提供决定性的体验提升。

## 7. Demo 建议展示流程

一段 3–5 分钟的 Demo 可以按以下顺序展示：

1. **建立人格**：要求用四川话交流，简单闲聊并在回复中打断一次；
2. **并发执行**：说“打开空调，然后导航到虹桥火车站”；
3. **长任务不等待**：发起天气或联网搜索，听到占位后立刻继续提出一个独立车控需求；
4. **主动回来汇报**：先收到车控结果，再由助手主动播报搜索结果；
5. **连续追问**：直接问“那需要带伞吗”，展示工具结果已经进入上下文；
6. **修改任务**：连续把天气地点从上海改到香港再改到贵阳，只保留最终结果；
7. **回到闲聊**：要求唱歌或继续四川话交流，展示任务和自然对话无缝切换。

对外可以概括为：

> 这不是只能一问一答的语音工具，而是一个可以边聊边办事的实时语音 Agent：任务立即确认、
> 后台并行执行、完成后主动回来告诉你，还能随时打断、修改和继续追问。

## 8. 成熟度判断与下一步

| 阶段 | 当前判断 |
|---|---|
| 技术演示 | **Ready**：核心数据流和代表场景已实测闭环 |
| 内部试用 / 客户 PoC | **Ready with guardrails**：控制工具集合和输出格式即可开展 |
| 小范围场景 Demo 产品 | **初步成熟**：全双工体验和异步任务已经形成清晰差异化 |
| 无约束生产发布 | 尚需事实摘要、取消语义和 PCM 调度继续收敛 |

短期优先级建议：

1. 为主要工具增加短、准、结构化的结果摘要；
2. 把激活 PCM 从约 2 秒压缩到最短可识别窗口，并完善用户说话检测；
3. 在 Demo 脚本和 prompt 中使用带目标的取消表达；
4. 保留 StreamTask 作为厂商原生能力基线，DynamicTask 作为默认 Demo 入口。

总体评价：**Duplex + DynamicTask 已经具备鲜明且可感知的产品价值。它把 Duplex 的原生语音
能力与异步 Agent 的任务执行结合起来，在自然交互、等待反馈、跨轮任务和主动播报上形成了比
旧级联方案更完整的体验。现阶段足以作为整体 Demo 产品推进，剩余问题属于可量化、可迭代的
质量优化，而不是需要推翻方案的基础能力缺失。**
