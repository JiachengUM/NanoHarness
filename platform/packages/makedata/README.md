# 核心概念（含数据格式详解）

数据合成的完整流程：

**Query → 测试维度 → Plan → 场景 → 用例 → 数据集**

每个概念不仅解释"是什么"，还详细说明其数据格式结构和每个字段的具体含义。

---

## 1️⃣ Query ——"你想测什么"

> **类比**：你去餐厅点菜时说"来份清淡的家常菜"

**定义**：用自然语言描述你想生成的测试场景。系统会根据这句话，自动理解你的意图并生成数据。

**示例**：
- "生成空调控制场景"
- "测试时间规律发现能力，覆盖通勤场景"
- "生成危险车控场景，验证助手拒绝能力"

> 💡 提示：描述越具体，生成结果越贴合需求。

---

## 2️⃣ 测试维度（Tag Tree）——"能力地图"

> **类比**：餐厅的完整菜单（中餐 → 川菜 → 火锅 → 麻辣火锅）

**作用**：系统内置的"能力清单"，定义了车载助手所有可被评测的能力维度。Query 输入后，AI 会从这个"地图"中选取相关的叶子标签。

### 数据格式与字段详解

```json
{
  "name": "车机助手评测测试维度",
  "description": "智能座舱语音助手能力评测",
  "children": [
    {
      "name": "车控操作",
      "description": "车辆控制相关功能",
      "children": [
        {
          "name": "空调控制",
          "children": [
            { "name": "温度直接设定", "isLeaf": true },
            { "name": "温度增减调节", "isLeaf": true }
          ]
        }
      ]
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| `name` | string | ✅ | 节点名称，如"车控操作"、"温度直接设定" |
| `description` | string | ❌ | 节点描述，说明该维度的含义和评测范围，以及给出一个例子描述 |
| `children` | array | ❌ | 子节点列表，构成树形结构。叶子节点无此字段 |
| `isLeaf` | boolean | 条件 | 标记是否为叶子节点。只有 `isLeaf: true` 的节点才能打在测试用例上 |

### 关键术语

- **叶子标签**：`isLeaf: true` 的节点，是测试维度的最末端。例如"温度直接设定"、"精确地点直达"。只有叶子标签才能出现在场景/用例的 `tags` 字段中。
- **中间节点**：有 `children` 的节点，仅用于分类组织，如"空调控制"、"车控操作"。不会直接打在测试用例上。

### 结构示例

```
车机助手评测测试维度
├── 车控操作
│   ├── 空调控制
│   │   ├── 温度直接设定
│   │   ├── 温度增减调节
│   │   └── ...
│   ├── 座椅控制
│   └── 车窗控制
├── 导航服务
├── 媒体播放控制
├── 交互体验与记忆
│   ├── 时间规律发现 ⭐️
│   ├── 长期记忆调用
│   └── 场景意图推断
└── ...
```

## 3️⃣ Plan（场景生成计划）——"作战蓝图"

> **类比**：建筑师根据你的需求（"我要个现代风格的三居室"）画出的设计图纸

**作用**：系统收到 Query 后，先不急着生成，而是先制定一个详细的 Plan：
- 分析 Query 涉及哪些测试维度
- 把你的需求改写成无歧义的、详细的任务描述
- 给出对原始 Query 的理解注解，帮你确认 AI 是否理解到位

**为什么要有 Plan？**
- ✅ **目标明确**：不盲目生成，确保覆盖你关心的测试维度
- ✅ **可干预**：你可以预览和修改 Plan（如调整要覆盖的标签、修正理解偏差）

### 数据格式与字段详解

```json
{
  "original_query": "生成导航场景",
  "task_description": "生成车载导航场景，覆盖用户常用的家和公司导航...",
  "target_tags": ["精确地点直达", "常用地点记忆", "显式意图识别"],
  "interpretation_notes": "用户希望覆盖导航发起与地点记忆两类能力，侧重日常通勤场景"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| `original_query` | string | ✅ | 用户输入的原始 Query |
| `task_description` | string | ✅ | AI 对 Query 的理解和扩展，详细的生成任务描述，无歧义，可直接用于生成和判别 |
| `target_tags` | array | ✅ | 需要覆盖的叶子标签列表（从测试维度中精选） |
| `interpretation_notes` | string | ✅ | 对原始 Query 的理解注解，帮助用户确认 AI 是否理解到位 |

## 4️⃣ 场景（Scenario）——"测什么"

> **类比**：电影剧本的故事大纲

**定义**：根据 Plan 生成的测试情境描述，回答"要测什么能力"的问题。

**包含内容**：
- 场景名称：如"导航到公司"
- 场景描述：验证助手能否正确理解用户导航意图并规划路线
- 标签：覆盖的测试维度（如 `["精确地点直达", "意图理解"]`）

### 数据格式与字段详解

```json
{
  "scenario_id": "scenario-001",
  "scenario_name": "导航到公司",
  "description": "验证助手能否正确理解导航指令并规划路线",
  "tags": ["精确地点直达", "显式意图识别"]
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| `scenario_id` | string | ✅ | 场景唯一标识符，格式通常为 scenario-XXX |
| `scenario_name` | string | ✅ | 场景名称，简洁描述测试目标（10-30字） |
| `description` | string | ✅ | 场景详细描述，说明测试目的、触发条件、预期行为（50-200字） |
| `tags` | array | ✅ | 该场景覆盖的叶子标签列表，必须全部来自测试维度的叶子节点 |

## 5️⃣ 测试用例（Case / DatasetItem）——"怎么测"

> **类比**：电影剧本的分镜脚本（具体到每一句台词）

**定义**：场景的具体实例，包含完整的对话流程和评判标准。

### 数据格式与字段详解

```json
{
  "case_id": "导航去公司首单",
  "context_config": {
    "car_info": {
      "车速": "60km/h",
      "档位": "D档",
      "当前位置": "家中"
    }
  },
  "max_round": 8,
  "user_query_lists": [
    {
      "user_query_list": [{"role": "user", "content": "导航去公司"}],
      "mock_info": { "car_info": {} },
      "mock_time": "2024-01-15 09:00:00"
    }
  ],
  "expected_script": "第一会话\n用户：导航去公司\n助手：好的，正在为您导航到公司，预计20分钟到达\n管家：验证助手是否正确识别目的地并发起导航",
  "nl_assertion": [
    "助手应正确识别目的地为公司地址",
    "助手应提供预计到达时间",
    "助手应发起导航"
  ],
  "case_description": "验证助手对明确目的地的直达导航能力；与同场景其他用例的差异：本例用户直接说出公司地址，不涉及模糊意图或地点记忆",
  "tags": ["精确地点直达", "显式意图识别"]
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| `case_id` | string | ✅ | 用例唯一标识，10字左右的中文精炼描述，能一眼看出本用例测什么（如「导航去公司首单」「周董别名点播周杰伦」），禁止使用「变体N」「用例N」等无信息量编号 |
| `context_config` | object | ❌ | 上下文配置，包含车况等背景信息 |
| `context_config.car_info` | object | ❌ | 车辆状态信息，如车速、档位、位置等 |
| `max_round` | number | ✅ | 最大对话轮数。简单场景：5-8；多轮：10-12；规律类：14-18 |
| `user_query_lists` | array | ✅ | 多轮对话记录，每个元素是一次独立冷启动 |
| `user_query_lists[]`（两种形式） | object / array | ✅ | 每个元素既可以是对象（含 user_query_list / mock_info / mock_time），也可以是更简洁的消息数组 `[{"role":"user","content":"..."}]`。非时间规律/条件规律类场景应使用简洁形式，且 mock_time 设为 null、mock_info 设为 {}，不要编造不必要的时间戳 |
| `user_query_lists[].user_query_list` | array | ✅ | 该轮的用户消息列表（通常只有一条） |
| `user_query_lists[].user_query_list[].role` | string | ✅ | 消息角色：user 或 assistant |
| `user_query_lists[].user_query_list[].content` | string | ✅ | 消息内容（用户说的话） |
| `user_query_lists[].mock_time` | string | ❌ | 模拟时间，格式：YYYY-MM-DD HH:MM:SS，仅用于时间规律/条件规律类场景，其他场景应为 null |
| `user_query_lists[].mock_info` | object | ❌ | 该轮的模拟信息，如 car_info |
| `expected_script` | string | ✅ | 预期对话脚本，描述用户说什么、助手应回什么、管家评测说明 |
| `nl_assertion` | array | ✅ | 自然语言断言（评判标准），告诉裁判如何判 Pass/Fail，每条只评助手一件事 |
| `case_description` | string | ❌ | 用例描述，说明测试目的和重点，并点出与同场景其他用例的差异点 |
| `tags` | array | ✅ | 该用例覆盖的叶子标签（必须全部来自场景的 tags） |

## 6️⃣ 数据集（Dataset）——"用例容器"

> **类比**：文件夹 / 相册

**作用**：数据集是用例的容器和管理单元。所有生成的用例最终都归属于某个数据集，方便批量管理、统计和导出。

**关键特性**：
- 所有生成的用例自动归属到你选定的数据集
- 数据集自动统计用例数量
- 支持按数据集批量导出、评测

### JSON 数据结构

```json
{
  "name": "导航场景测试集",
  "description": "2024年Q3导航功能回归测试",
  "item_count": 42
}
```

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|:----:|------|
| `name` | string | ✅ | 数据集名称，用于识别和管理 |
| `description` | string | ❌ | 数据集描述，说明用途、版本、创建背景等 |
| `item_count` | number | ✅ | 用例数量，自动计算，新增/删除用例时自动更新 |

# 🔄 概念关系总结

**Query → Plan → 场景 → 用例 → 数据集**，测试维度作为"能力地图"贯穿全程。

| 阶段 | 角色 | 回答的问题 |
|------|------|-----------|
| Query | 用户输入 | "我想测什么" |
| Plan | 作战蓝图 | "测哪些、怎么理解" |
| 场景 | 测什么 | "做什么场景" |
| 用例 | 怎么测 | "具体台词 + 评判标准" |
| 数据集 | 保存结果 | "统一管理" |

**各概念之间的关系**：
- Query 决定 Plan：你说想要什么，系统就规划怎么测
- Plan 指导生成场景：作战蓝图告诉系统要生成哪些测试方向
- 场景 派生出多个用例：一个测试方向可以变成多个具体可执行的测试实例
- 用例 归属于数据集：所有生成的用例最终都保存在一个数据集里，方便统一管理
- 测试维度 被场景和用例覆盖：每个场景/用例都对应着测试维度中的某些具体能力

**一句话串起来**：
你输入 Query（"我想测导航场景"），系统先看测试维度（有哪些能力可测），然后制定 Plan（测精确地点直达+意图理解，并附理解注解），接着生成场景（导航到公司），最后细化成用例（带具体对话台词），所有用例归属到指定的数据集方便批量管理和评测。

**具体例子**：
- **Query**："生成导航场景，测试助手能否正确识别公司地址"
- **Plan**：覆盖能力维度 `["精确地点直达", "显式意图识别"]`，理解注解说明侧重日常通勤
- **场景**：导航到公司（描述：验证助手能否正确理解导航指令）
- **用例**：导航去公司首单 — 用户说"导航去公司"，验证助手是否正确响应；这个用例属于"我的导航测试集"，是从"导航到公司"场景派生出来的

# 完整工作流程

1. **上传测试维度（一次性）**
   - 上传某个项目的评测维度

2. **创建/选择数据集**
   - 创建新数据集或选择已有数据集
   - 数据集是用例的容器，有名称、描述、用例数量统计

3. **输入需求**
   - 选择测试维度（能力地图）
   - 用自然语言描述想测什么："生成导航场景"

4. **AI 生成 Plan（场景规划）**
   - AI 分析需求，制定生成策略
   - 输出：要覆盖的测试维度、详细任务描述、理解注解

5. **确认 Plan（可选）**
   - 用户可以查看和修改计划（标签、任务描述、理解注解）

6. **生成场景（自动迭代）** ⭐️ 核心环节
   - 系统根据 Plan 自动生成一批场景
   - 自动审核场景质量、自动修复问题、自动评估覆盖度
   - **流式输出**：每生成一个合格场景就立即显示在前端
   - 循环直到覆盖度达标或达到最大迭代次数

7. **确认有效场景** ⭐️ 人工介入环节
   - 前端展示所有生成的场景列表，可进行手动增删改
   - 用户勾选/标记需要生成用例的**有效场景**
   - 未选中的场景不进入用例生成

8. **生成用例（Case）**
   - 仅对**已确认的有效场景**生成多个用例
   - 同一场景的多个用例一次性生成，便于内部协调命名与多样性
   - 同样经过自动生成 → 审核 → 修复的闭环
   - 流式输出：每生成一个合格用例就立即合并到数据集

9. **结果合并**
   - 所有合格用例直接**合并到指定数据集**
   - 可在数据集管理中查看、编辑、导出生成的用例

# 实操建议

## 1. 测试维度别从零开始，要写就写清楚

**建议**：一般来说，一个项目对应一个测试维度。而测试维度的内容直接来自于项目的产品要求。

我们有团队积累的标准测试维度（覆盖车控、导航、多媒体等常见车载助手能力），推荐直接下载这个通用版本，根据你的项目特点稍作增删改即可。

**为什么要这样？**
- 测试维度的设计需要对车载场景有较深理解，从零搭建门槛高
- 通用版本已经覆盖了 80% 的常见能力，修修补补就能满足大部分需求
- 保持团队内测试维度的一致性，方便结果对比和复用

如果你需要自定义测试维度（修改或新增节点），注意：**`description` 字段一定要写全，质量直接决定生成效果。**

一个好的 `description` 应该包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| 能力含义 | 这个标签代表什么能力 | "用户明确说出具体温度数值，要求助手调节空调温度" |
| 评测范围 | 什么情况下算这个标签，什么不算 | 属于："调到24度"、"把温度设为26"；不属于："调低一点"（这是模糊指令，一定要最简单纯粹代表这个标签的例子） |
| 具体例子 | 给出一个真实对话示例 | 用户："空调调到23度" → 助手："已为您将空调温度设置为23度" |

**对比：好 vs 坏的 description**

❌ **差的写法**：
> "温度控制相关功能"

→ 太笼统，AI 不知道什么算温度控制，生成场景会跑偏

✅ **好的写法**：
> "用户明确指定具体温度数值，要求助手将空调设定到该温度。
>
> 属于此标签：'调到24度'、'温度设为26度'、'给我调到23度'
> 不属于此标签：'调低一点'（模糊指令）、'太热了'（需要澄清）
>
> 示例对话：
> 用户：空调调到23度
> 助手：好的，已为您将空调温度设置为23度，当前车内温度28度"

**为什么要写这么详细？**
- AI 根据 `description` 来判断一个场景是否属于该标签
- 写清楚了，生成的场景边界清晰、不跑偏
- 写含糊了，会出现「明明是模糊指令却被打上精确设定标签」这类错误

> 📌 参考模板：直接下载标准测试维度文件，参考里面节点的 `description` 写法，依葫芦画瓢即可。

---

## 2. 认真审视 AI 生成的 Plan

Plan 是后续所有生成的基础，一定要在生成场景前确认它符合你的预期。

**建议检查这几项**：

| 检查项 | 说明 | 如果发现不对怎么办 |
|--------|------|------|
| 覆盖的能力维度 | Plan 选了哪些测试维度（`target_tags`）？是否包含你想测的核心能力？ | 直接编辑 Plan，增删标签 |
| 任务描述 | `task_description` 是否把你的需求改写清楚了？有没有遗漏重点或跑偏？ | 直接编辑 `task_description`，把意图写得更明确 |
| 理解注解 | 看 `interpretation_notes`，AI 是否正确理解了你的需求？ | 如果理解偏差，重新输入更明确的 Query |

> 💡 一句话：Plan 是作战蓝图，蓝图错了，后面生成的场景和用例都会跑偏。花2分钟检查 Plan，能省下后面20分钟的返工。

## 3. 善用标签组合表达复杂场景

测试维度的精髓在于组合——单个标签只描述一个原子能力，多个标签组合在一起就能表达复杂的复合场景。

**看几个例子**：

| 场景 | 标签组合 | 含义 |
|------|----------|------|
| "行驶中让助手导航去公司" | `["行驶中", "精确地点直达", "导航发起"]` | 测试行驶状态下的导航能力 |
| "用户说太热了，助手询问后调节" | `["模糊指令", "澄清追问", "温度调节"]` | 测试模糊意图识别 + 澄清 + 执行 |
| "连续三天早高峰导航到公司" | `["时间规律发现", "导航发起", "跨会话记忆"]` | 测试规律归纳和主动服务能力 |

**用好组合的关键**：
1. **选准核心能力标签**：这个场景主要测什么？
2. **加上限定条件标签**：模糊？多任务？多轮对话？涉及记忆？……

**什么时候用组合？**
- ✅ 想测试某个能力在特定条件下的表现（如"行驶中的车控"）
- ✅ 想测试多个能力的协同（如"模糊意图识别 + 澄清 + 执行"）
- ✅ 想覆盖边界情况（如"危险车控 + 助手拒绝"）

> 💡 提示：组合的标签之间最好有逻辑关联（如"模糊指令"+"澄清追问"是天然流程），不要硬凑无关标签，否则生成的场景会很生硬。

## 4. 生成场景后，先审核再生成用例

根据 Plan 生成场景后，系统会暂停，等你确认。这个环节很重要，不要为了赶进度跳过。

**建议检查清单**：

| 检查项 | 看什么 | 怎么处理 |
|--------|--------|----------|
| 是否符合预期 | 这些场景是不是你想测的？有没有偏离你的初衷？ | 发现跑偏的场景，直接删除 |
| 覆盖是否全面 | 生成的场景是否覆盖了你关心的所有能力维度？有没有遗漏重要的测试点？ | 如果缺失少量关键场景，直接在前端手动添加或修改；如果缺失较多，可以重新生成 |
| 是否有重复 | 多个场景描述相似，只是换了说法？ | 保留最有代表性的1-2个，删除冗余 |
| 是否合理可行 | 场景描述的车载场景是否符合常识？用户真的会这么说吗？ | 删除明显不合理或罕见的场景（如"在行驶中打开车门"） |
| 场景粒度 | 场景是不是太笼统（如"测试导航功能"）或太细碎（如"导航到A街道和导航到B街道算两个场景"）？ | 太笼统的细化拆分，太细碎的合并 |

**为什么要在用例生成前做这个审核？**
- 场景是骨架，用例是血肉。骨架歪了，血肉再多也站不稳
- 删除一个不合理场景，等于避免生成 5-10 个无效用例
- 人工审核只需要几分钟，但生成的无效用例后续需要大量时间清理

> 🗣️ 操作口诀：宁可少而精，不要多而杂。删除不犹豫，补充不凑合。
