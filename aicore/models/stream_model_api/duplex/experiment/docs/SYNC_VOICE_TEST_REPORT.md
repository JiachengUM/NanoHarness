# Duplex StreamTask 同步版语音实验测评报告

## 1. 测评范围

- 测试日期：2026-08-12。
- 12 个测试场景，14 次独立 session；Case 10、Case 11 各录制两次。
- 入口：`StreamTaskToolRunner`，`tool_call_mode="sync"`。
- 原始日志：[`../test_log/sync/`](../test_log/sync/)。
- 对照输入：[`VOICE_TEST_CASES.md`](VOICE_TEST_CASES.md)。

测试发生在 2026-08-12，但同步入口的 system prompt 仍硬编码“今天是 2026 年 8 月 6 日”。
日志中的多数天气 FC 实际使用了 8 月 12 日，但日期型问题仍存在配置混杂，不能把所有事实差异
单独归因于执行策略。

这里的“同步”只描述 **FC 结果回传策略**：同一 FC 组全部执行完成后，将真实
`role=tool` output 一次性上行。它不代表 WebSocket、麦克风或多个本地工具被串行阻塞；
日志证明工具 pending 期间仍可接收新语音并创建新的 FC。

本报告只判断模型回复是否忠实于本次工具 output，不判断搜索结果所描述的外部世界是否
绝对真实。

## 2. 与 DynamicTask 对齐的 R1-R8

两种模式使用相同的上层检查维度，但 R3、R4 按各自协议能力定义，不能拿 DynamicTask
特有的占位、observation 和 PCM 要求同步版。

| 编号 | 检查项 | StreamTask 同步版通过条件 |
|---|---|---|
| R1 | ASR 与轮次 | 每个真实输入有完整转写，关键意图和轮次归属未丢失 |
| R2 | FC 决策 | 工具名、参数和 schema 正确；同轮独立子意图在一个 FC 组内并发提交 |
| R3 | 工具生命周期 | 每个 FC 都进入唯一终态；同组全部完成后，所有 `call_id` 对应的真实 output 一次上行 |
| R4 | 结果续推理 | 不需要占位或 PCM；output 上行后，服务端能自动继续原请求并完整回答，不静默丢结果 |
| R5 | pending / 取消 / 修改 | 执行中追问不重复调用；取消或修改的口头状态与工具真实状态一致，旧结果不串台 |
| R6 | 事实约束 | 名称、数字、日期、地点和状态均能在对应 tool output 中找到 |
| R7 | 音频与收音时序 | 不抢断已有回复；工具等待期间的环境声不应额外触发残缺 ASR 轮次 |
| R8 | 回复质量 | 简短自然、不泄露内部信息；会话风格和工具历史陈述准确 |

状态：✅ 通过；⚠️ 部分通过、覆盖不完整或存在环境混杂；❌ 明确违反；— 不适用。

## 3. 可机械核对的链路结果

| 指标 | 结果 | 结论 |
|---|---:|---|
| 独立 session | 14 | Case 10、11 各重复一次 |
| ASR started / completed | 50 / 46 | 4 次 started 无 completed，均发生在工具 pending 期间 |
| FC 事件 / FC 调用 | 31 / 36 | 5 个事件包含同组并发 FC |
| 本地已启动任务 | 35 | 35/35 最终 `task.success` |
| schema 失败 | 1 | Case 10 酒店 POI 参数错误，作为 tool error output 返回 |
| tool output 上行 | 31 个事件 / 36 个 item | 36/36 `call_id` 均有对应 `role=tool` item |
| 同组结果攒批 | 31/31 | 每个 FC 组只在全组闭合后上行一次；并发组未分批回传 |
| 占位 / observation / PCM 激活 | 0 | 符合同步版设计，不经过异步兼容层 |

因此，**同步版的本地执行与上行传输是完整的**。后续失败不能归因于“工具没执行”或
“FC output 没发给 Duplex”。

但“成功上行”不等于“用户收到结果”。按交互窗口分类：

- 13 个没有新用户轮次插入的独立 FC 组，结果上行后 13/13 自动续推理并开始回复。
- 18 个处于跨轮重叠窗口的 FC 组，结果虽然全部上行，但 0/18 在结果到达后自动续答；
  后续通常需要用户再问一次，并可能触发重复或错误查询。

这里的“跨轮重叠”指：旧 FC 尚未闭合时，服务端已经完成了一个新的真实用户 ASR 轮次。

## 4. Case 逐项结论

### Case 01：无工具、多轮与人工打断

- 三轮真实输入都得到正确 ASR；未产生 FC。
- 用户两次在播放期间插话，服务端进入新回复；最后一轮正常说明能力。
- 前两段没有记录 `output_audio.done/canceled`，只能确认行为上被新一轮取代，不能从日志
  单独证明显式取消终态。

结论：无工具和人工插话主目标通过。

### Case 02：车控与导航并发

- 同一个 FC 事件发出 `car_control` 和 `navigation`，两个本地任务同时开始。
- 车控先完成，系统等待导航完成，再用一个 `conversation.item.create` 上行两个 tool item。
- 服务端随后回复“已打开空调，开始导航到上海虹桥火车站”。

结论：并发分组、攒批、自动续答和事实均通过，是同步版标准成功链路。

### Case 03：台风与预警

- 一次 `websearch`，没有重复调用。
- output 上行后自动回复；“白海豚停止编号但有残余影响”“大风、暴雨预警”等结论均可在
  output 中找到。
- 搜索材料内部存在“当前暂无预警”和区级预警新闻的来源冲突，但最终回复没有创造来源外事实。

结论：工具链路和事实约束通过。

### Case 04：只推荐一家日料店

- POI 参数包含城市、地址、范围、日料、人均 200 和高评分，但没有把“只推荐一家”保留到
  `criteria`。
- 最终先推荐符合预算的“大森の大众食堂”，但又补充人均 201 元的“大牛寿喜烧”。
- 名称、评分和价格来自 output；问题是 FC 约束遗漏和回复未遵守单店要求，不是传输错误。

结论：事实通过，显式约束和回复质量部分失败。

### Case 05：黄霄云最新合唱歌曲

- 实际只录制了第一轮，没有执行原计划的《空心》日期追问。
- 模型在第一次 output 后又发起第二次 `websearch`，两次链路都正常自动续答。
- 最终称《空心》7 月 17 日是“最新”，但第二份 output 中存在日期更晚的《野心家》7 月 25 日；
  “官方音源”也没有明确依据。

结论：生命周期通过，事实判断失败；因缺少追问，不能评价完整 Case。

### Case 06：天气与歌曲同组并发

- 实际只录制了第一轮，没有执行后续台风追问和“白海豚”纠错。
- `websearch` 与 `QQ音乐单曲搜索` 同组并发，等待二者完成后一次上行。
- 最终选择黄霄云《锈》7 月 31 日，并正确概括白海豚影响；对应内容都在 output 中。
- 音乐 output 首项混入王铮亮《答案》，属于工具排序瑕疵；模型正确过滤。

结论：已录首轮通过，但不能代替完整 Case 通过。

### Case 07：pending 时插入独立车控

- 香港天气搜索 pending 时，服务端正常接收“打开空调”并创建车控 FC；同步版没有阻塞麦克风。
- 车控先完成并自动回复。原香港搜索随后完成，output 正常上行，却没有自动回复。
- 用户问“天气查到了吗”后，模型错误新搜上海；再次说明“之前查香港”后才重复搜索香港。
- 最后模型说调用过 3 次工具，实际是 4 次。

结论：跨轮执行与传输都成立，但旧结果续答归属丢失，后续发生错搜、重搜和历史计数错误。

### Case 08：pending 结果上的依赖追问

- 上海后天天气 pending 时，用户追问是否带伞；模型没有挂接原任务，而是创建第二次 websearch。
- 两个 output 分别上行，均未自动回复；用户再问“查到了吗”后才回答。
- 降雨和带伞有依据，`26-34℃` 不是 output 对目标日期的清晰主结论。
- 工具 pending 期间出现 1 次 started 无 completed 的 ASR。

结论：同步版无法表达 pending 依赖，控制和自动续答失败，事实部分通过。

### Case 09：取消天气与修改 POI 预算

- 本次实际只说“算了，不用查”，没有录到“改查下次台风”，与 DynamicTask 输入不完全一致。
- 模型口头说不查，但原 websearch 继续完成并上行。
- 人均 100 与人均 200 的两个 POI 都继续执行；旧请求没有取消或 supersede。
- 最终回复的“平成屋日式料理”不在任一 POI output 中。
- 工具 pending 期间出现 1 次 started 无 completed 的 ASR。

结论：取消、修改、结果续答和事实均失败。

### Case 10：多 pending 任务下的模糊取消

- 三组双工具请求都在同一个 FC 事件内并发；同步攒批行为 3/3 正确。
- 用户说“不用查”或“取消任务”后，模型都口头声称已取消，但全部任务仍执行并上行。
- 第一条酒店 POI 的 `criteria` 错传字符串，schema error 与天气结果仍作为同一批 tool output 返回。
- 结果上行后均未播报。

结论：批处理通过；取消状态不真实、无澄清、跨轮结果不续答。Dynamic 与同步版都没有满足
模糊取消的产品语义。

### Case 11：连续修改 pending 天气

- 第一份录制的三次目标、第二份录制的五次目标都各自创建新 websearch；旧任务从不取消。
- 所有工具均完成并上行，但用户需要手动追问才能得到最终回答。
- 第一份录制中，上海真实 output 还没上行，模型已经回答上海，构成抢答。
- 第二份录制能正确说出调用 5 次，但把“上海明天”叙述成“上海今日”；最终温度和风向也不符
  output 的主要结果。
- 两次录制各有 1 次 started 无 completed 的 ASR。

结论：不具备任务修改或旧任务抑制语义，且存在抢答和事实偏移。

### Case 12：四川话、长工具等待与独立任务插入

- 清洁的一问一答中，成都天气、成都电影和车控均在 tool output 后自动回复；天气、电影事实
  能在对应 output 中找到。
- 长工具等待期间有一次回复退回普通话，用户随后明确指出。根据本次人工听感，只能判定方言
  持续性不稳定。
- 上海演唱会 pending 时插入车控；车控先完成并回复，演唱会 output 后到但没有自动回复。
- 后续“演唱会信息”被 ASR 严重误识别，触发新的泛化搜索；最终答案依据的是第二次 output，
  原上海演唱会结果仍未播报。
- 本次没有说“不要搜电影”，因此不评价电影取消。

结论：独立轮次事实通过；跨轮旧结果仍丢失。方言不稳定，但 DynamicTask 没有在相同条件下
复测，不能据此推导模式差异。

## 6. 根因分层

### 6.1 已验证稳定的本地机制

1. FC schema 到本地工具执行再到 `role=tool` output 的映射闭环，36/36 有结果。
2. 同一个模型事件中的多个 FC 可以并发执行，并严格等同组全部终态后一次上行。
3. WebSocket 下行消费不被本地工具阻塞；pending 时仍能处理新语音和新 FC。
4. 清洁的一问一答场景不需要额外 PCM，真实 output 足以触发服务端自动续推理。

### 6.2 同步模式的确定边界

旧 FC pending 时只要形成新的用户语音轮次，旧 output 后续虽然仍被服务端接收，却不再自动
产生对应回复。日志无法证明服务端内部实现，但行为上可表述为：**新用户轮次取代了旧 FC 的
续答归属**。

这会连锁产生三个问题：

1. 用户不知道旧任务已经完成；
2. 手动追问无法直接消费刚才的 tool output，容易再次调用工具；
3. 多次修改只会生成多份独立工作，缺少“旧任务已被替换”的可执行状态。

### 6.3 与执行策略无关的问题

- POI 和音乐工具自身可能召回或排序不理想。
- Duplex 仍可能违反事实、约束或风格要求。
- 环境噪音会在工具等待窗口触发 ASR started。本轮同步日志在 Case 08、09、11、11_02 各有
  1 次 started 无 completed，但测试中途改变了麦克风操作方式，不能用数量证明同步模式比
  DynamicTask 更差或更好。

## 7. 结论

StreamTask 同步版适合 **严格的一问一答、用户等待工具结束后再继续说话** 的场景：协议最短，
传输闭环清楚，原生 tool output 的事实遵循也相对更好。

它不适合目标中的异步全双工任务：工具 pending 时虽然还能接收新请求，但旧结果失去主动播报
能力，也没有真实取消、修改和 pending 依赖语义。这个限制不在本地 runner 的并发能力，而在
Duplex 对“跨用户轮次的旧 FC 结果如何重新启动推理”缺少稳定原语。
