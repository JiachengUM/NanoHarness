# Input Ingestion

输入预处理环节。将项目方提供的各种原始文件转化为结构化中间产物，供后续环节消费。

## 核心理念

项目落地时，输入几乎从来不是干净的结构化文档，而是各种乱七八糟的文件：巨大的 Excel 表、格式随意的 Word、半成品的飞书导出……这些文件里往往同时混杂着：

- 🏷️ **标签线索**：类似标签树的结构（功能分类表、能力清单、评测维度）
- 📋 **已有case**：测试用例、对话示例、评测条目（格式与我们的 TestCase 不同）
- 📄 **需求描述**：产品功能描述、能力边界说明
- 🗑️ **无关内容**：项目管理信息、进度表、人员分工

本环节的职责是**从混乱中提取结构化信息**，与环节1（从结构化信息构建标签树）关注点完全不同。

```
各种原始文件（Excel/CSV/Word/PDF/...）
       │
       ▼
  ┌──────────────────────────────────────────┐
  │  环节0: 输入预处理                          │
  │                                            │
  │  1. 文件发现与分类                           │
  │  2. 大文件分块读取                           │
  │  3. 内容分类提取（标签线索/case/需求/噪声）    │
  │  4. 格式归一化（→ 统一中间格式）              │
  │  5. 合并去重                                │
  │  6. 人工确认                                │
  │                                            │
  └──────────────────────────────────────────┘
       │
       ├─→ extracted_tag_hints.json     ← 标签线索
       ├─→ extracted_cases_raw.json     ← 已有case（原始）
       ├─→ extracted_requirements.md    ← 需求描述
       └─→ extraction_report.md        ← 提取报告
```

## 输入

### 原始文件（用户手动放入 `<P>/inputs/raw/`）

| 文件类型 | 常见内容 | 处理策略 |
|---------|---------|---------|
| Excel (.xlsx/.xls) | 评测用例表、功能清单、能力矩阵 | 按Sheet+行数分块 |
| CSV (.csv) | 导出的评测数据、标注结果 | 按行数分块 |
| Word (.docx) | 产品需求文档、评测方案 | 按章节/段落分块 |
| PDF (.pdf) | 产品手册、技术规格 | 按页分块 |
| Markdown (.md) | 飞书/Confluence导出 | 按标题分块 |
| 纯文本 (.txt) | 邮件、聊天记录 | 按长度分块 |

**约定**：
- 用户将所有原始文件放入 `<P>/inputs/raw/`，文件名不限
- 所有文件统一由本环节处理，不再区分"干净"和"原始"文件

### 上游产物（增量提取时读取）

| 输入 | 目录 | 何时需要 |
|------|------|---------|
| 已有提取结果 | `<P>/inputs/extracted/` | 增量提取时，避免重复提取已处理文件 |

## 输出

| 产物 | 目录 | 说明 |
|------|------|------|
| 标签线索 | `<P>/inputs/extracted/extracted_tag_hints.json` | 从原始文件中提取的标签体系线索 |
| 已有case | `<P>/inputs/extracted/extracted_cases_raw.json` | 从原始文件中提取的已有评测用例 |
| 需求描述 | `<P>/inputs/extracted/extracted_requirements.md` | 从原始文件中提取的需求描述 |
| 提取报告 | `<P>/inputs/extracted/extraction_report.md` | 提取过程摘要，供人工确认 |

## 执行流程

### 第一步：文件发现

1. 扫描 `<P>/inputs/raw/` 目录，列出所有文件
2. 按文件类型分类，记录文件大小和预估内容量
3. 检查 `<P>/inputs/extracted/` 是否已有提取结果
   - 有 → 对比文件列表，只处理新增/修改的文件（增量提取）
   - 无 → 全量提取
4. 向用户展示文件清单和提取计划

### 第二步：分块读取与内容提取

对每个文件，按类型选择分块策略：

| 文件类型 | 分块方式 | 每块大小 |
|---------|---------|---------|
| Excel | 按Sheet，每个Sheet按行 | ≤200行/块 |
| CSV | 按行 | ≤200行/块 |
| Word | 按标题层级（H1/H2） | ≤3000字/块 |
| PDF | 按页 | ≤5页/块 |
| Markdown | 按标题层级 | ≤3000字/块 |
| 纯文本 | 按段落/长度 | ≤3000字/块 |

对每个分块，使用 LLM 做内容分类和提取：

```
输入：一个文件分块的原始内容
输出：
  - content_type: tag_structure / test_cases / requirements / noise / mixed
  - extracted: 按类型提取的结构化内容
  - confidence: 提取置信度（高/中/低）
  - notes: 需要人工确认的模糊点
```

### 第三步：内容分类

每个分块的内容分为四类：

| 分类 | 判据 | 举例 |
|------|------|------|
| **标签线索** | 包含能力分类、功能层级、评测维度等结构化分类信息 | Excel里有"功能模块→子功能→评测点"的层级；Word里有"能力域"章节 |
| **已有case** | 包含具体的用户输入、预期输出、评测条目 | Excel每行是一个测试用例；文档里有"测试场景"表格 |
| **需求描述** | 描述产品功能、能力边界、使用场景 | "本系统支持XXX""不支持XXX""在XX场景下应YY" |
| **无关内容** | 与评测数据集构建无关 | 项目进度表、人员分工、版本历史、会议纪要 |

**混合内容处理**：一个分块可能同时包含多种类型。此时分别提取，保留来源映射。

### 第四步：格式归一化

将提取出的内容转为统一中间格式：

#### 标签线索 → `extracted_tag_hints.json`

```json
{
  "source_files": [
    {"filename": "客户A_评测用例_v3.xlsx", "processed_at": "2026-05-28"}
  ],
  "tag_hints": [
    {
      "name": "空调控制",
      "type": "category",
      "description": "空调相关控制能力",
      "source_ref": "客户A_评测用例_v3.xlsx#Sheet1!A3",
      "children": [
        {
          "name": "空调开关",
          "type": "leaf",
          "description": "可正确打开或关闭空调",
          "source_ref": "客户A_评测用例_v3.xlsx#Sheet1!A4"
        }
      ]
    }
  ],
  "coverage_notes": "原始文件覆盖了车控和导航两大域，缺少记忆和通用对话能力"
}
```

- `type`：`category`（中间节点）或 `leaf`（叶子节点，可评测的具体能力点）
- `source_ref`：来源定位，便于追溯和人工确认
- `coverage_notes`：对原始文件覆盖范围的总体评价

#### 已有case → `extracted_cases_raw.json`

```json
{
  "source_files": [
    {"filename": "客户A_评测用例_v3.xlsx", "processed_at": "2026-05-28"}
  ],
  "cases": [
    {
      "raw_id": "TC-001",
      "source_ref": "客户A_评测用例_v3.xlsx#Sheet1!R5",
      "user_input": "打开空调",
      "expected_response": "已为您打开空调",
      "tags_hint": ["空调开关"],
      "context": "用户在车内，空调处于关闭状态",
      "assertion_hint": "助手应确认空调已打开",
      "notes": "原始格式为表格行，字段名可能不完全对应",
      "conversion_confidence": "high"
    }
  ],
  "field_mapping_notes": "原始Excel列名：测试编号→raw_id, 用户输入→user_input, 预期回复→expected_response, 功能标签→tags_hint"
}
```

- 字段尽量对齐 TestCase schema，但允许缺失和偏差
- `conversion_confidence`：转化置信度，低置信度的case需人工确认
- `field_mapping_notes`：原始字段到中间格式的映射说明

#### 需求描述 → `extracted_requirements.md`

标准 Markdown 格式，按功能域组织，保留来源引用：

```markdown
# 提取的需求描述

> 来源：客户A_产品需求文档.docx

## 车控操作

### 空调控制
- 支持打开/关闭空调
- 支持温度调节（16-32度）
- 不支持分区温控

## 导航服务
...
```

### 第五步：合并去重

多个文件可能包含重叠信息。合并策略：

| 场景 | 策略 |
|------|------|
| 同一标签线索在多个文件中出现 | 保留描述最完整的版本，其他作为补充 |
| 同一case在多个文件中出现 | 去重，保留字段最完整的版本 |
| 需求描述有矛盾 | 全部保留，标注矛盾，交由人工在环节1确认 |
| 不同文件的标签粒度不同 | 全部保留，标注粒度差异，交由环节1决定 |

### 第六步：生成提取报告

`extraction_report.md` 包含：

1. **文件处理摘要**：处理了哪些文件，每个文件提取了什么
2. **标签线索统计**：提取了多少标签线索，覆盖了哪些域，与基础标签树的重叠/差异
3. **已有case统计**：提取了多少case，字段完整度分布，转化置信度分布
4. **需求描述摘要**：提取了哪些功能域的需求
5. **需要人工确认的问题**：模糊分类、矛盾信息、低置信度转化等
6. **与基础标签树的快速对比**：哪些标签线索在基础树中已有，哪些是新增的

👤 **人工确认提取结果**：检查分类是否正确、提取是否遗漏、矛盾信息如何取舍。

## 分块读取策略

### 大文件处理原则

1. **不尝试一次性读取整个文件**：超过 500 行的表格或 10000 字的文档必须分块
2. **保持分块的语义完整性**：按自然边界（Sheet、章节、页）切分，不在表格行中间断开
3. **表头传播**：表格分块时，每块都携带表头，避免丢失列语义
4. **跨块引用**：如果一块的末尾和下一块的开头有语义关联（如一个case跨两行），合并处理

### Excel 特殊处理

- 每个 Sheet 独立处理
- 第一行作为表头，自动识别列语义（"测试用例""功能点""用户输入"等）
- 合并单元格展开后处理
- 空行跳过，不作为分块边界

### 迭代提取

对于超大文件（如 5000+ 行的 Excel），可以分批提取：

```
第1批：前200行 → 提取 → 人工确认提取质量
第2批：201-400行 → 提取 → ...
...
最后：合并去重
```

第一批提取后，人工确认提取质量。如果质量满意，后续批次可自动处理；如果质量不满意，调整提取策略后重试。

## 与后续环节的衔接

### → 环节1（构建标签树）

环节1现在有两个输入源：

| 输入源 | 优先级 | 说明 |
|--------|--------|------|
| `<P>/inputs/extracted/extracted_tag_hints.json` | 参考对比 | 从原始文件提取的标签线索，与基础标签树做diff |
| `<P>/inputs/extracted/extracted_requirements.md` | 直接消费 | 从原始文件提取的需求描述 |

环节1的增量识别流程变为：
1. 读取基础标签树
2. 读取 `extracted_tag_hints.json`，与基础标签树做 diff → 识别 +/-
3. 读取 `extracted_requirements.md` → 补充增量
4. 交叉验证：标签线索和需求描述是否一致

### → 环节2/4（写case）

| 输入源 | 用途 | 说明 |
|--------|------|------|
| `<P>/inputs/extracted/extracted_cases_raw.json` | 风格参考和种子 | 已有case可作为"这个项目之前怎么写case"的参考，但不直接使用 |

已有case的价值：
- **风格参考**：了解项目方的用户画像、语言风格、关注重点
- **场景灵感**：已有case覆盖的场景可以作为新case的灵感来源
- **标签验证**：已有case的标签标注方式可以辅助理解标签语义
- **不直接复用**：格式不同、质量未知、可能不符合我们的写作原则

## 迭代模式

### 自回溯

- 新文件放入 `raw/` 后，增量提取，不重新处理已有文件
- 提取结果不满意时，可删除对应提取结果，重新提取
- 人工可直接编辑 `extracted/` 下的文件，添加 `"manually_edited": true` 标记

### 跨环节回溯

| 触发场景 | 回溯方式 |
|---------|---------|
| 环节1发现标签线索提取不完整 | 回到环节0重新提取或人工补充 |
| 环节2发现已有case的风格参考有价值但提取质量不够 | 回到环节0调整提取策略 |
| 项目方提供了新的原始文件 | 回到环节0增量提取 |

### 人类编辑保留

- 人工编辑 `extracted/` 下的文件后，添加 `"manually_edited": true` 标记
- 增量提取时不覆盖带该标记的内容
- 如需更新，提示用户确认

---

## 完成标准

- `raw/` 下所有文件均已处理（提取报告中有记录）
- 标签线索提取完整（提取报告中无"未分类"的高置信度标签线索）
- 已有case提取完整（转化置信度分布合理，低置信度case已人工确认）
- 需求描述无遗漏（提取报告中无"未处理"的需求相关分块）
- 👤 人工已确认提取报告

## 经验教训

1. **第一批提取后必须人工确认**：LLM 对文件格式的理解可能有偏差，第一批确认后后续才能批量处理
2. **表头识别是关键**：Excel 的列名决定了提取的语义，识别错误会导致整列数据错位
3. **不要过度提取**：无关内容（项目进度、人员分工）不要强行归类，标记为 noise 即可
4. **保留原始来源**：`source_ref` 是追溯和验证的基础，不可省略
5. **矛盾信息不要自行消解**：不同文件的矛盾需求全部保留，交由环节1的人工确认
6. **已有case不要直接复用**：格式不同、质量未知，只作参考和灵感
7. **大文件分批提取**：第一批确认质量后，再批量处理后续批次
8. **增量提取**：新文件只处理新增部分，不重新处理已有文件
