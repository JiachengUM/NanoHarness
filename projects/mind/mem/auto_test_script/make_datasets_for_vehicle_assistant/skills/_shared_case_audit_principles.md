# 用例审核通用原则

所有涉及用例审核的环节（环节5/6）共享的审核原则。审核原则与写作原则（`_shared_case_writing_principles.md`）是同一知识体系的两种视角：写作原则是"应该怎么写"，审核原则是"检查是否违反"。

> **优先级**：本文件是**通用审核原则**。各项目可在项目级审核补充原则（如奔驰项目 `case_audit_supplements.md`）中定义项目特有审核规则。**项目级原则优先于通用原则，冲突时以项目级为准**。

---

## A. 用户台词 = 演员照读的口语

用户行里出现的每一个字，都是演员要照着念的台词。因此：

### A1. 不能夹带导演/评测/标注意图

本质：演员念不出括号尾巴和出题说明，念出来也不像人话。

举例：(概括)/(补充)/(模糊指代)/(仅两字提示)/(专辑名口述)/(报案口径)/(playlist)/(口语就行)/(别替我断言)/(类型识别清楚)/(对比两条ETA)——全是导演话，不是车主话

### A2. 不能有UX研究员腔

本质：车主对车机是短句吩咐，不会做"口头预判实验"。

举例："你结合我之前几次帮我口头预判""用我自己的话说一遍你听懂了什么"

### A3. 冷启动首条必须能独立听懂

本质：冷启动没有上文，悬空指代让听者无法理解。

举例："这款食用油"→ 哪款？"竞争对手"→ 谁家？"那人"→ 谁？"那个敏感事件"→ 哪个？应改成具体名称

### A4. 记忆边界控制题：用户不能替agent做"记/不记"决定

本质：测的是agent主动判断，用户说了"记住/别记"就变成测遵嘱。

举例：测"高敏信息不自动记录"时用户说了"别记"→ 测的不是主动判断

### A5. 记忆消费轮不能泄题

本质：消费轮验证助手能否自主调用记忆。用户台词里已包含答案，就绕过了要测的能力。

举例：生产轮"进地库插电"，消费轮又说"进地库插电"→ 助手不需要记忆就能答；消费轮说"按习惯/之前/复盘"→ 暗示有历史，助手被剧透

### A6. 规律/证据累积类末轮：只能弱托付，不能复述执行口令

本质：末轮验证助手是否从模式推断出应执行的动作。用户复述口令=绕过推断。

举例：前几轮固定关窗，末轮又说"关窗"→ 绕过了推断；应改为"照旧/你知道咋办吧/懂了呗"

### A7. 问题复盘类验证轮：不能把改进方向念出来

本质：验证助手是否自己记住了吐槽并改进。用户念出改进方向=剧透。

举例：第二会话说"别推这么燥的"→ 应改为重复同一简问，让助手自己体现改进

### A8. 条件规律发现类：用户台词不能泄露car_info中的条件变量

本质：条件规律发现测的是助手能否自己从car_info/mock_time中的条件变量+用户多轮偏好归纳出「条件→偏好」的规律。用户台词里泄露条件变量=把规律直接告诉助手=绕过归纳能力。这与A5消费轮泄题、A7念出改进方向是同一本质：用户替助手做了本该由助手自己完成的事。

举例：car_info写了天气=晴，用户说"晴天听钢琴"→ 泄露了天气条件，助手不需要自己归纳；用户说"外面下雨了""天气预报说暴雨""今天晴天"→ 条件变量泄题；正确写法：用户只说偏好（"放点钢琴轻音乐"），条件变量留给car_info

### A9. 能力泄题：用户不能直接要求助手展现本该主动展现的能力

本质：与A5记忆泄题、A7念出改进方向、A8条件泄题是同一本质——你测的是助手"主动"做某事的能力，用户直接说了就变成测命令遵循。典型场景：

- 测"拒绝后替代建议"时，用户说"给我替代方案"→ 绕过了测试助手是否会主动给替代方案的能力；正确写法：用户只提出一个应拒绝的请求，不说要替代方案，看助手是否主动给
- 测"无结果替代建议"时，用户说"给我其他选择"→ 同上

判断标准：问自己"这个case要测的能力，是否要求助手主动展现？如果是，用户台词里有没有直接要求助手做这件事？"如果有，就是能力泄题。

## B. 断言 = 导演的判分条，只评助手

nl_assertion是导演勾Pass/Fail的条文，导演从录音和车机log（助手执行结果+屏幕推送内容）核对助手行为。因此：

### B1. 只评助手行为，不评"用户该怎么念"

本质：断言是判分条，不是出题规范。

举例："用户台词须干净""裁判判分时请关注"——这些是出题规范，不是断言

### B2. 必须可从录音或车机log核对

本质：导演看不到记忆库/检索侧/内部状态/后台工具调用过程；但能看到助手执行结果和屏幕推送内容的车机log。

举例："写入长期记忆/检索侧命中"→ 导演看不见记忆库；"通过车控工具调用"→ 导演看不见工具调用过程，但能从log看到执行结果；应改为"助手须执行XXX并给出可核对结果"等可从口头反馈或执行结果log核对的行为（如'已将空调调至22度'，或log显示空调温度已设为22度）

### B2b. 管家括号块不得强制助手口头详细反馈

本质：`expected_script` 的"管家：（…）"括号块是预期动作描述，给裁判和演员参考。现在裁判能看到车机log（助手执行结果+屏幕推送内容），执行结果由log核对，**不强制助手口头详细反馈**。若括号块里写"须明确反馈""须明确告知""须明确说明""须详细说明"等强制口头反馈措辞，会让裁判误以为助手只说"好的"就算不通过——这与新感知边界冲突。

**审核判据**：
- 若 case 的 `expected_script` 里"管家：（…）"括号块中出现"须明确反馈""须明确告知""须明确说明""须明确回答""须明确回复""须详细说明"等强制口头反馈措辞，**判不通过**
- issue 的 principle 填「B2b」，dimension 填「管家括号块强制口头反馈」，severity 填「MAJOR影响评测」
- suggestion 填改写后的括号块内容（删除口头反馈措辞，只保留核心动作描述）

**修复必须执行**：审核修复 LLM 修复 case 时，必须删除"管家：（…）"括号块里的"须明确反馈/须明确告知/须明确说明/须明确回答/须明确回复/须详细说明"等措辞及配套的期望台词示例（如"如'已为您调到22度'"），只保留核心动作描述（"须执行XXX""须追问XXX"等）和禁止性约束（"不得XXX"）。

### B3. 必须有明确执行标尺

本质：无法勾Pass/Fail的空话不是断言。

举例："不应忽略XX语境支撑"→ 怎么勾？应改为具体的可核对标准

【违法/危险请求的断言规则】当case测试"应拒绝"能力且用户请求涉及违法/危险行为时（如破解车门、偷窥、暴力），断言只须要求助手明确拒绝+说明原因，不得要求助手给出"可执行替代建议"——因为违法请求没有合法替代方案，要求替代建议反而无判定标尺。

【断言不得冗余重复】nl_assertion中不同断言之间不得存在语义重复。若两条断言的判定结果完全一致（即Pass/Fail条件相同），应合并为一条。

### B3b. 每条断言必须在本case的录音里有唯一的判定结果

本质：导演听完录音后要能逐条勾Pass/Fail。nl_assertion应包含两层：①通用底线约束——对车载助手的基本要求，允许存在；②case专属断言——必须有，用于区分本case的评测标准。B3b违规的判断标准不是"有通用断言"，而是"只有通用断言、没有case专属断言"或"通用断言占主导、case专属断言缺失"。

【有意义的通用底线 vs 无意义的废话断言】通用底线约束允许存在的前提是它对车载助手场景有实际意义、导演能据此勾Pass/Fail。以下区分：

✅ 有意义的通用底线（允许保留）：导演能明确判断Pass/Fail，且对车载助手场景有实际约束力。如"助手不得答非所问"（导演能判断助手是否偏题）、"助手不得口出污言秽语"（明确的行为底线）、"助手不得仅给出无实质内容的礼貌性回复"（能判断是否有实质信息）。

❌ 无意义的废话断言（必须删除）：看似在提要求，实则不知所云、空无实际意义、导演无法据此勾Pass/Fail。如"须明确体现已对XX所涉能力完成打开/关闭/调节/切换/查询/检索/播放等动作之一"——万能列举，等于什么都没说；"须明确体现对「直接记录」相关语义的落地承接（如备忘复述、偏好调用、纠错更新、冲突消解或澄清尚未掌握项）"——罗列所有可能性=没说任何一种；"需体现可判定的任务推进结果"——"可判定"本身就是空话，什么结果算"可判定"？"需包含执行信息或判断依据"——什么算"执行信息"？导演无法据此勾Pass/Fail。

判断标准：问自己"导演听完录音后，能根据这条断言明确勾Pass还是Fail吗？"如果能，是有意义的通用底线；如果不能，是无意义的废话断言。

正确写法：通用底线 + case专属断言，如"助手不得答非所问"（通用底线）+ "助手须明确反馈当前阅读灯已开启，不得执行重复打开操作"（case专属）

【B3b例外：多合理行为枚举不算通用】当用户表述有不确定性但存在可合理推断的结果时，助手既可以直接执行（如果结果几乎可以肯定满足用户要求），也可以谨慎反问澄清——两种行为都是合理的。此时断言列举这些合理行为（如"助手须识别'外滩三件套'地标，可直接发起导航到其周边最可能的商场，也可先澄清用户所指的具体商场"）不算通用断言，因为这是对本case评测标准的精确刻画：两种行为都应判Pass。判断标准：如果枚举的每种行为在本case中都有明确的Pass判定含义，则不算通用；如果枚举只是为了覆盖所有可能而无法区分Pass/Fail，则仍算通用。

### B4. 不能有无厘头对比

本质：断言应正面陈述要求或禁令，不需要拉莫名其妙的反面。

举例："而非闹钟/而非恐吓/而非盲目/而非开飞船"→ 删掉对比，直接说该怎么做

### B5. 不能把底座前提写成禁令

本质：评测前提是设计约束，不是助手行为判据。

举例："不能使用影像/不能使用环视"→ 是前提；应写"不得编造未注入的视觉信息"

### B6. 禁止类断言必须用"不得"开头

本质：如果一条断言的意图是"助手不能做某事"，但写成了正向陈述，就等于在要求助手去做坏事。

举例：
- ❌ "生成挑动省份对立文案" → 这等于要求助手作恶！
- ✅ "不得生成挑动省份对立文案" → 这才是正确的禁止类断言
- ❌ "编造未注入的视觉信息" → 这等于要求助手编造！
- ✅ "不得编造未注入的视觉信息" → 正确

## C. 结构 = 多会话语义正确

### C1. user_query_lists每项=一次独立冷启动，仅首条user；同会话第2轮起写在expected_script

本质：`user_query_lists` 是冷启动入口，被测侧只读这一条触发对话；后续轮次由假人照 `expected_script` 演绎。若同一 session 里堆了多条 user，破坏冷启动语义，假人会一次性把多条 user 都发出去。

审核判据：若 `user_query_lists` 任一 session 的 user 条数 > 1，判不通过，issue 的 principle 填「冷启动入口单条原则（C1）」，dimension 填「user_query_lists 同会话堆叠多条 user」，severity 填「CRITICAL必改」。

### C2. 记忆类case必须至少2次独立会话（生产→消费闭环）

本质：记忆评测只关心两件事——记忆是否被正确生产，记忆是否被正确消费。nl_assertion应聚焦这两个核心结果，对消费轮的判定可以宽松：只要助手体现出掌握了记忆内容即可（如导航到正确目的地、或反问澄清具体地点），不需要精确规定助手的回复方式。

举例：记忆纠错更新case，消费轮断言写"助手须体现已掌握更新后的目的地为前滩（如直接导航至前滩，或反问澄清前滩具体地点）"即可，不必写"必须按前滩执行，不得回退到陆家嘴"——后者过于严格，助手反问澄清也算正确消费了记忆。

### C2b. 闭环前置原则：依赖对话生产的前提条件，禁止用car_info预设

**本质**：所有依赖「用户偏好/历史记忆/当前媒体状态/当前车辆任务状态/已建立的任务上下文」等前提条件的 case，**必须通过对话生产前提条件**，再在后续轮次或后续会话中消费并验证。**禁止用 car_info 预设来代替对话建立前提**。

**为什么**：
- car_info 是车辆/环境的**客观初始状态**（位置、时间、档位、车速、温度、硬件状态、已安装应用等），不应承载"用户偏好""当前媒体""已记忆事实""已启动的任务"等需要通过对话建立的状态
- 用对话生产前提条件，能完整测试助手的「记忆生产→记忆调用」「指令执行→状态查询」「偏好建立→偏好应用」闭环能力，而不是只测后半段
- 用 car_info 预设会跳过前半段被测能力，case 评测覆盖不全

**适用范围**（必须用对话生产前提的场景）：

1. **媒体状态类**：询问当前歌曲/歌手/播放内容、收藏、切歌、暂停、音量调节、播放模式切换、播放进度控制等
   - 反例：`car_info: 当前媒体：陈奕迅 - 《十年》（播放中）` + `用户：这是什么歌？` ❌
   - 正例：第一轮 `用户：我想听陈奕迅的歌` → 第二轮 `用户：这是什么歌？` ✓

2. **用户偏好/记忆类**：调用用户喜欢的颜色/歌手/食物等偏好、引用历史对话事实等
   - 反例：`car_info: 用户记忆：喜欢蓝色` + `用户：帮我把氛围灯调成我喜欢的颜色` ❌
   - 正例：第一次对话 `用户：你记住我喜欢蓝色` → 第二次对话 `用户：帮我把氛围灯调成我喜欢的颜色` ✓

3. **任务上下文类**：基于已建立的任务状态进行追问/修改/取消/状态查询等
   - 反例：`car_info: 当前导航：去天安门` + `用户：还有多久到` ❌
   - 正例：第一轮 `用户：导航去天安门` → 第二轮 `用户：还有多久到` ✓

**两种实现结构**：

1. **单会话多轮前置**（前提与消费在同一会话）：适用于媒体状态、任务上下文、短期记忆调用
   - `user_query_lists: [[前提指令, 消费指令]]`
   - expected_script 同会话内多轮

2. **多次多轮前置**（前提与消费跨会话）：适用于长期记忆、用户偏好、跨会话事实调用
   - `user_query_lists: [[前提指令], [消费指令]]`
   - expected_script 用 `（重启新的对话……）` 分隔两次会话

**car_info 仅用于客观硬件/环境状态**：位置、时间、档位、车速、车外/车内温度、蓝牙/USB/已安装应用等不依赖用户对话的初始环境信息。

**审核判据**：若 case 的 user_query_lists 仅含消费指令，但 car_info 里出现了「当前媒体：XX（播放中）」「用户记忆：XX」「当前导航：XX」等本应通过对话生产的前提状态，判不通过，issue 的 principle 填「闭环前置原则」，dimension 填「前提条件未通过对话生产」，severity 填「CRITICAL必改」。

**【voice 模式分模式例外】**：本数据集同时支持 api（接口测试）和 voice（语音测试）两种模式。case 设计不绑定测试方式，演员适配由 `test_mode` 参数注入假人/裁判 prompt 实现（详见写作原则§14b.0）：
- **api 模式**：上述审核判据照常生效，前置构建轮必须显式写在 expected_script 里。
- **voice 模式**：可语音发起的任务型前置（导航/播放/放新闻等）允许省略——voice 模式下假人会在 prompt 指引下自主构建这类前置；车辆状态类前置（车速/档位等）仍须放 car_info；记忆类前置仍须多会话构建。
- **审核时默认按 api 模式判**（因为 case 要同时兼容两种模式，api 模式要求更严格）。若 case 在 api 模式下前置完整，则在 voice 模式下也兼容（假人会照剧本演已有的前置轮，不冲突）。

### C2c. 功能操作型指令须先构建任务态

**本质**：存在一类"功能操作型指令"——它们本身不发起任务，而是对**已运行任务**做操作/查询/设置。如果冷启动直接说这类指令，被测助手面对的是"无任务进行中"的状态，操作无对象，评测不可复现。与 C2b 闭环前置原则同类——功能操作型指令的"操作对象"是消费端，必须在本 case 内先"生产"（建立任务）。裸操作 = 操作对象悬空。

**典型表现**（以导航为例，其他域同理）：

| 操作类型 | 裸指令（❌ 缺前置） | 问题 |
|---|---|---|
| 路线操作 | "刷新路线" | 没有导航在进行，刷新哪条路线？ |
| 地图视角 | "放大地图""2D车头朝上" | 没有地图在导航中，视角操作无意义 |
| 播报设置 | "切换为详细播报" | 没有导航在播报，切什么？ |
| 路况开关 | "打开实时路况" | 没有导航路线，路况显示在哪？ |
| 途经点操作 | "删除第一个途经点" | 没有途经点，删什么？（且"第一个"需要≥2个途经点才有区分度） |
| 沿途查询 | "下一个收费站多远""前方堵车吗" | 没有导航路线，无"前方"可言 |
| 目的地查询 | "目的地是哪里""到目的地多远" | 没有导航在进行，无目的地可查 |

**通用原则**：凡是对"已运行任务"做操作/查询/设置的指令，必须在前序轮次先构建任务态（发起任务），再发起操作指令。完整生命周期为：构建任务态 → [按需补充操作对象] → 验证操作 → 恢复原状。

**导航域具体要求**：
- 路线操作/地图视角/播报设置/路况开关/沿途查询/目的地查询类指令 → 前序轮次须先"导航到XXX"建立导航任务
- 途经点操作类指令 → 前序轮次须先"导航到XXX" + "添加YYY为途经点"（删除"第一个/第二个"类需要≥2个途经点才有区分度）

**其他域同理**：
- 媒体控制类（"切歌""暂停""音量调大"）→ 前序须先播放
- 导航中途车控（"打开座椅通风"在导航中）→ 前序须先导航
- 任务状态查询（"当前播放什么""导航到哪了"）→ 前序须先建立对应任务

**审核判据**：若 case 的冷启动台词（user_query_lists[0]）是功能操作型指令，但 expected_script 前序轮次（或 user_query_lists 前序 session）未先构建对应任务态，判不通过，issue 的 principle 填「功能操作型指令须先构建任务态」，dimension 填「操作对象悬空/裸操作无前置任务」，severity 填「CRITICAL必改」。途经点删除类若途经点不足2个导致"第一个/第二个"无区分度，dimension 填「途经点数量不足无法区分」，severity 填「CRITICAL必改」。

**【voice 模式分模式例外】**：与 C2b 同理（详见写作原则§14b.0）：
- **api 模式**：上述审核判据照常生效。
- **voice 模式**：可语音发起的任务态构建（如先"导航到XXX"再"刷新路线"中的"导航到XXX"）允许省略，假人会自主构建；但途经点删除类等"测试设计层面的特定前置"仍须显式写。
- **审核时默认按 api 模式判**。

**修复方向**：在 expected_script 前序轮次补上任务建立过程（如先"导航到XXX"再"刷新路线"），并在末尾补恢复轮（如"退出导航"，见 C2d）。

### C2d. 状态恢复闭环（生产→消费→恢复）

**本质**：一次完整的 case 生命周期是"构建前提条件 → 消费验证 → 恢复原状"。对于会改变车上软硬件长期状态的 case（媒体播放/导航任务/车控操作/定时任务等），expected_script 末尾须增加"恢复轮"，通过自然口语指令尝试恢复原状，避免残留状态污染后续 case 的测试环境。

**为什么**：虽然每个 case 在对话层面是独立冷启动，但**车机软硬件状态是跨 case 持续存在的**。如果 case A 播放了音乐没暂停、发起导航没退出、调了车控没复原，case B 启动时这些残留状态会：(1) 干扰语音识别（背景噪音）；(2) 污染测试前提（case B 本应是静默状态）；(3) 导致不可预测的行为（助手可能基于残留状态做不同响应）。

**需要恢复轮的类别**：

| 类别 | 残留状态 | 恢复指令示例 |
|---|---|---|
| 媒体播放 | 音乐/新闻/有声书在播 | "暂停播放"/"先别放了"/"停一下" |
| 导航任务 | 导航进行中 | "退出导航"/"取消导航"/"不导了" |
| 车控操作 | 空调/车窗/座椅/氛围灯状态改变 | "关掉空调"/"车窗关上"/"氛围灯关了" |
| 定时任务 | 提醒已设置 | "取消刚才的提醒" |

**不需要恢复轮的类别**：纯查询类（查天气/查新闻/查赛况/查胎压，不改变任何软硬件状态）、S2S闲聊/成语接龙（已退出，对话结束即恢复）、拒识类（助手无响应无状态改变）、记忆类（记忆持久化是测试点本身，不在 case 内删除）。

**恢复轮写法要求**：
1. 用户台词须自然口语，不得说"为了不影响下一个测试""为了恢复初始状态"等导演话——应说"暂停播放""先别放了""退出导航"等自然短句
2. 恢复轮不计入核心 nl_assertion 判据（核心验证已在前序轮次完成）
3. 恢复失败可接受（状态恢复是"尽力而为"，助手没执行恢复指令不影响本 case 判定）
4. max_round 须为前序核心轮次 + 恢复轮 + 重试余量

**审核判据**：若 case 会改变软硬件长期状态（媒体播放/导航任务/车控操作/定时任务），但 expected_script 末尾没有恢复轮，**不判不通过**，只在 issues 中标注提醒（便于人工 review 时补全），issue 的 principle 填「状态恢复闭环」，dimension 填「缺恢复轮致残留状态污染后续case」，severity 填「MINOR建议」。**恢复轮缺失/失败不影响 case 通过判定**——case 通过与否只看核心验证点（用户意图是否被正确理解+执行+反馈），恢复轮属于测试工程层面的完整性建议，不是被测能力的评测点。

### C3. 规律发现/证据累积类必须至少3次独立会话

### C4. 多次冷启动之间不能写成同一聊天线程的衔接

本质：冷启动之间没有连续transcript，用户不能假装还在同一个聊天里。

举例："附上/再加/把我刚才/接着刚才"→ 应各自独立完整，或改为单会话多轮

## D. 标签 = 与题干主轴一致

### D1. 只打叶子节点，不打中间节点

本质：中间节点是分类用的，不是评测用的。只有叶子节点才对应可评测的具体能力。

【程序化校验结果】以下标签和结构问题已由代码严格校验，直接采纳：
{{TAG_VALIDATION_INFO}}
你只需在此基础上做语义判断（D2/D3）。若校验结果包含【Schema结构校验】问题，该case必须判不通过，issue的principle填"Schema"，dimension填"数据结构不合法"，severity填"CRITICAL必改"。

### D2. 每个标签必须有对应case内容支撑，不能凑覆盖

【标签粒度混淆高频错】以下标签对语义不同，必须严格区分：

- "温度增减调节"（调高/调低几度）vs "温度直接设定"（设到具体温度值）——用户说"调低2度"→增减调节；用户说"调到26度"→直接设定
- "风量增减调节"（调大/调小几档）vs "风量直接设定"（设到具体档位）——同上逻辑
- "氛围灯开关"（开/关）vs "氛围灯模式切换"（换颜色/换模式）——用户说"换个颜色"→模式切换
- "精确地点直达"（用户给了明确具体地址直接导航）vs "结果可直接导航"（从搜索结果中选一个导航）——用户说"导航到万达"→结果可直接导航；用户说"导航到南京西路1266号"→精确地点直达
- "精确地点直达"（用户直接说出目的地名称）vs "地标特征找地点"（用户通过外观/周边特征推理目的地）——用户说"导航去人民广场"→精确地点直达；用户说"去江边那个像帆船的酒店"→地标特征找地点。已记忆的口语别名调用也不属于地标特征找地点
- "应拒绝"（请求本身不合法/不安全）vs "应降级处理"（请求合法但当前条件不满足）——用户说"破解车门"→应拒绝；用户说"座椅按摩不能用给我替代"→应降级处理
- "需澄清"（case需要用歧义/模糊来考验助手是否能够及时针对歧义/模糊来追问用户明确意义才能完成任务）vs "可完成"（用户意图明确可直接执行）——用户说"调空调"但没说调什么→需澄清；用户说"空调调到26度"→可完成。注意：如果用户直接下达了明确指令，不需要助手追问澄清就能完成任务，则不应打"需澄清"
- "直接记录"（用户明确说"记住"时准确记录）vs "长期稳定偏好记录"（从多次对话行为中归纳长期偏好，无需用户明确指令）——用户说"记住：不要香菜"→直接记录；用户多次选周杰伦后助手总结偏好→长期稳定偏好记录
- "改口纠错恢复"（同会话内用户即时改口纠正）vs "记忆纠错更新"（跨会话纠正已写入长期记忆的信息）——用户同会话说"我说错了，是1001号"→改口纠错恢复；用户下次会说"你记错了，我不吃辣"→记忆纠错更新
- "场景意图推断"仅适用于用户未直接说出任务目标、需助手从情境推断潜在意图的场景。用户已明确完整表达需求时，不得打此标签
- "执行前确认"仅适用于高风险或可能误操作的场景。当car_info已明确满足安全条件（如已驻车P档）且用户已确认安全状态时，不得打此标签

【标签树覆盖缺口处理】当用户诉求在标签树中没有完全匹配的叶子标签时，应选择语义最接近的标签，不得因此判定标签错误。例如用户说"风速稳住别嗡嗡的"——标签树没有"风量稳定"标签，选择"风量增减调节"是合理的（因为本质是在调节风量使其稳定），不应判定为标签乱打。

【互斥标签硬约束】评测结果预期标签（可完成/需澄清/应拒绝/应降级处理）之间互斥，一个case只能选其一。若case设计导致结果不确定，应拆分为两个独立case

【标签覆盖完整性】case中涉及的每个核心动作/功能点都应有对应的产品功能叶子标签覆盖。若用户请求包含多个独立功能操作（如开启+档位调节），不得只标其中一个而遗漏另一个

### D3. 主轴是什么域就打什么域的叶

本质：标签是评测覆盖的统计口径，错标会污染子树导出。

举例：POI题不打联网叶，音乐题不打地点叶，车控题不打媒体叶

【联网查询域漏标】当case核心诉求包含查询公网时效资讯（限行规则、天气、油价、政策等）时，必须打联网信息查询子树下的叶子标签，不得仅打导航/地点类标签而遗漏联网查询域

【复合型case是常态】真实车载场景中，绝大多数case都是复合型的——一个case同时涉及记忆+导航、车控+媒体、短期记忆+地点直达等是正常的。审核时不得因为case涉及多个域的叶子就判定标签错位，应关注的是：每个标签是否有对应case内容支撑、标签是否与用户意图的主轴一致。

## E. 场景 = 座舱可信 + 感知边界

### E1. 优先车内合理场景，case设计必须贴近真实车载场景

本质：评测对象是车机助手，case的一切设计——用户台词、car_info、expected_script——都应像真实车主在车上的场景。不能为了凑标签而造出过于生硬、无厘头的case。

举例：报税/工位/法院等非车场景应改写为停车场/收费站/车内口述等；又如"拒绝后替代建议"标签，不应造一个用户让助手做明显与车载无关的事然后被拒绝的生硬case，而应造一个真实的车载场景：如黑夜行驶中用户要求关闭外部大灯（助手应拒绝并解释安全风险，建议保持大灯开启）——这才是车主真正可能提出、助手真正需要拒绝的请求。

判断标准：问自己"一个真实车主在车上真的会这么说/这么要求吗？"如果不会，case设计就违反E1。

### E2. 默认无车载视觉

本质：助手不能看环视影像，不能编造未注入的视觉信息

## F. expected_script格式

### F1. 用户行只有纯台词，不能有括号或导演说明

### F2. 导演说明全放管家括号块或独立括号块

### F3. expected_script必须支撑case设计的完整交互闭环，管家括号块不能是万能模板套话

本质：管家是被测对象，剧本不能命令它做什么，只能写「期望助手xxx」。如果case设计要求助手追问/澄清，expected_script里必须有一行用户回答来接住助手的追问，否则交互链断裂——助手追问后没人回答，case无法走完。管家括号块写的是期望，不是命令。

【管家期望不得无中生有】管家括号块中的期望内容，若涉及具体的品类/类型/选项（如"中餐外卖""川菜馆"），必须有用户台词或car_info中的明确依据，不得无中生有。若信息不足，管家期望应为"询问具体类型"而非自行指定。

举例：case_id是"追问具体门店"，但expected_script里第一会话只有一轮用户台词，没有「用户：（回答助手常去的咖啡店）」来接住追问，交互链断裂；又如：管家括号块写"完成写入/删除/复盘/偏好声明等生产侧内容"——万能描述，换任何case都适用，既没说期望助手追问还是记录，也没有用户行接住追问；正确写法：管家行写「（期望助手追问具体店名或品牌）」，紧接着用户行写「（回答助手常去的咖啡店，如星巴克淮海中路店）」

### F4. 项目特有先导段是合法前导段，审核/修复不得删除

本质：各项目可在项目级写作原则中定义**项目特有的强制先导段**（如奔驰项目的重试先导段——以"管家可能耳背"开头、含"你好奔驰"唤醒词，定义假人重试的演绎规则；写作侧定义见写作原则§7.3.7及各项目写作原则，奔驰项目为 §2.1.7）。这类先导段是合法的人设/规则前导段。

**审核不得报错**：审核时不得把项目特有先导段误判为"格式错误""非用户：/管家：格式的杂段""多余说明"。先导段是 `expected_script` 的合法组成部分。

**修复必须保留**：审核修复 LLM 修复 case 时，必须原样保留项目特有先导段，不得删除、改写、压缩。修复后的 `expected_script` 必须仍包含该先导段。

**审核判据**：若 case 的 `expected_script` 包含项目特有先导段，审核**不得**因此报 F1/F2/F3 类问题。只有当先导段之后正文出现 F1/F2/F3 问题时才报。

### F4b. 演员应变规则（盲选第一个 + 简洁回复承接，自动测试必备前导）

本质：自动测试中假人演员和裁判**能看到车机log（助手执行结果 + 屏幕推送内容）**，不再是"只能聆听语音通道"。但实际执行中仍有两类需要演员应变的情况：助手让选列表 → 假人逐一念候选名再选浪费时间且可能选错；助手只说"好的"没说具体做了什么 → 演员无需追问，裁判直接从log核对执行结果。因此写作原则§7.3.8强制要求所有 case 的前导部分必须额外包含「盲选第一个」和「简洁回复承接」两条应变规则（若项目定义了其他先导段如重试先导段，则应变规则接在其后）。

**审核不得误判**：审核时不得把这两段应变规则误判为"格式错误""非用户：/管家：格式的杂段""多余说明"。它们是 `expected_script` 的合法组成部分，和先导段一样受 F4 保护。

**审核判据**：
- 若 case 的 `expected_script` 前导部分包含「盲选第一个」和「简洁回复承接」两段规则，审核**不得**因此报 F1/F2/F3 类问题
- 若 case 缺少这两段规则（前导部分只有其他先导段或人设前导，没有盲选与简洁承接），判不通过，issue 的 principle 填「演员应变规则缺失（F4b）」，dimension 填「前导段缺失应变规则」，severity 填「warning建议补充」
- 若 case 的 max_round 未留足裕量（用户台词轮数较多但 max_round 仅勉强等于台词轮数），可在同一 issue 中一并提示

**修复必须保留**：审核修复 LLM 修复 case 时，必须原样保留这两段规则，不得删除、改写、压缩。修复后的 `expected_script` 必须仍包含盲选规则与简洁承接规则。

**标准文案参见**：写作原则 [_shared_case_writing_principles.md](./_shared_case_writing_principles.md) §7.3.8

### F4c. 超长多轮剧本的轮次序号（≥10轮强制）

本质：多轮剧本台词轮数较多（≥10）时，裁判报告问题轮、修复脚本定位、人工 review 都需要共同坐标。写作原则§7.5强制要求 ≥10 轮的单次多轮剧本必须给每一轮的"用户："和"管家："行加行内序号 `[N]`（从 `[1]` 递增）。

**审核不得误判**：审核时不得把 `[N]` 行内序号误判为"格式错误""非用户：/管家：格式的杂段"。序号是 `expected_script` 的合法组成部分，和先导段一样受保护。

**审核判据**：
- 若 case 的 `expected_script` 中出现 `[N] 用户：xxx` / `[N] 管家：（…）` 行内序号，审核**不得**因此报 F1/F2/F3 类问题
- 若单次多轮 case 的用户台词轮数 ≥10 但**未加** `[N]` 序号，判不通过，issue 的 principle 填「超长多轮剧本缺轮次序号（F4c）」，dimension 填「可定位性缺陷」，severity 填「warning建议补充」
- 若出现 `第N轮：用户：xxx` / `轮次N：` / `1. 用户：xxx` 等章节式或列表式序号，判不通过，issue 的 principle 填「序号格式错误，应改为 [N] 行内序号（F4c）」，dimension 填「格式错误」，severity 填「error必须修复」

**修复必须保留**：审核修复 LLM 修复 case 时，必须原样保留 `[N]` 序号，不得删除、重排、改写。

**标准格式参见**：写作原则 [_shared_case_writing_principles.md](./_shared_case_writing_principles.md) §7.5

### F5. 电话类 case 不应纳入自动测试集（通话态阻塞原则）

本质：电话类 case（涉及拨打电话的 case）**无法自动测试**。被测助手拨通电话后进入通话态，麦克风采集的用户语音被切到电话通道，被测助手无法聆听后续指令，假人说"挂断"也传不到助手（写作原则§7.4）。因此电话类 case 不应出现在 `vehicle_assistant_cases.json`（自动测试集）中。

**审核判据**：若 `vehicle_assistant_cases.json` 中出现电话类 case（user_query_lists 或 expected_script 中出现"打电话""拨打""拨号""呼叫"等拨打意图），判不通过，issue 的 principle 填「电话类case不可自动测试（F5）」，dimension 填「电话类case误入自动测试集」，severity 填「CRITICAL必改」。

**处理方式**：电话类 case 应从自动测试集中移除，单独存档到 `phone_cases_manual_only.json` 供人工测试。

**不要用挂断台词绕过**：加"用户：挂了吧"台词无效——通话态下挂断指令传不到助手。审核不得要求"补挂断收尾轮"作为修复方式。

### F6. 地址必须真实存在，禁止编造

本质：case 中出现的所有地址/地名/地标/POI 必须**真实存在**，不得编造。LLM 生成地址时常见的错误模式是"真实路名+编造门牌号"或"真实城市+编造路名"——这种地址看起来像真的但实际不存在，会导致导航/POI测试时助手实际找不到精确地址，case预期与现实不符（写作原则§8.1）。

**审核判据**：
- 若 case 中出现具体门牌号地址（格式如"XX路N号"）且**不是白名单已验证地址**，判不通过
- 若 case 中出现路名但该路名在城市中不存在，判不通过
- 若 case 中出现地标名但该地标不存在，判不通过
- issue 的 principle 填「地址编造（F6）」，dimension 填「地址不真实」，severity 填「MAJOR影响评测」
- suggestion 填改写后的地址（从白名单选取或改为泛指地点）

## 审核方法论

先审查case设计意图：问自己"这个case要测的核心能力是什么？这个能力是否要求助手主动展现？"如果是，检查用户台词里有没有直接要求助手做这件事——如果有，就是A9能力泄题。

逐条审查nl_assertion：先判断整体结构——nl_assertion是否同时包含通用底线约束和case专属断言？如果只有通用断言、没有case专属断言，或通用断言占主导而case专属断言缺失，整体判B3b违规。然后逐条检查：对每条断言问"导演能根据这条断言明确勾Pass/Fail吗？"如果能且它是通用底线约束（如"不得答非所问""不得仅给出无实质内容的礼貌性回复"），允许保留，但必须有case专属断言配合；如果导演无法据此勾Pass/Fail（如"需体现可判定的任务推进结果""打开/关闭/调节/切换等动作之一"），则是无意义的废话断言，违反B3b。通用结构约束（如"第一会话须完成第一段意图""第二会话为独立冷启动"）导演也无法据此勾Pass/Fail，同样违反B3b。不要只抓最明显的一条，每条无意义的废话断言都要单独报一条issue。

逐块审查expected_script：对每个管家括号块，问自己"这段描述换到同标签的其他case还适用吗？"如果适用，它就是万能模板套话，违反F3。然后检查：如果case设计暗示助手应追问/澄清，expected_script里是否有对应的用户行来接住？如果没有，交互链断裂，同样违反F3。

审查标签时注意：复合型case是常态，一个case同时涉及多个域的叶子标签是正常的。不要因为case涉及多个域就判定标签错位，应关注每个标签是否有对应case内容支撑。
