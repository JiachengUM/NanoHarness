## 🔧 这些数字怎么来的？我们做了什么

简单说，我们给车载助手测试装了**两个AI引擎**，把过去"靠人"的环节换成"靠AI"，人只做最后的判断。

### 引擎一：AI自动造测试用例

过去测试人员要一条条手写用例（问什么、怎么算过、前提条件……），费时且靠个人经验。

**原理一览：**

```
客户需求（PRD + 必过case表）
            ↓
   ┌──────────────────┐
   │  ① AI理解沉淀     │  测试维度
   │                  │  例：导航、车控、多轮记忆……形成标签树
   └──────────────────┘
            ↓
   ┌──────────────────┐
   │  ② AI规划         │  计划
   │                  │  例：要测单轮导航、多轮导航、打断改目的地……
   └──────────────────┘
            ↓
   ┌──────────────────┐
   │  ③ AI想象         │  场景
   │                  │  例：导航过程中改目的地、跨轮追问之前说过的地点
   └──────────────────┘
            ↓
   ┌──────────────────┐
   │  ④ AI编写         │  用例
   │                  │  例：前提条件+用户台词+助手应答+通过标准
   └──────────────────┘
            ↓
   ┌──────────────────┐
   │  ⑤ AI质检 + 人审   │  入库
   │                  │  例：筛掉重复/不合格的，人确认后入库
   └──────────────────┘
```

一句话：**人把需求喂给AI，AI把用例造出来，人只做最后审核。**

先解释几个后面会用到的词：

**测试维度**

这个项目到底该测哪些方面，标准示例是什么样的——相当于测试的大纲+标准示例。

例：导航、车控、多轮记忆、跨轮上下文、打断改目的地……每个维度还附带一条标准示例在描述里（如"导航维度"的标准示例可能是"导航到上海市浦东新区世纪大道1号"）。

**计划（Plan）**

AI对用户需求的理解和拆解，说清楚"这次要测什么、覆盖哪些维度、需求该怎么理解"。

例：用户一句话说"帮我测一下导航功能"，AI理解后给出计划：要测单轮导航、多轮导航、导航打断改目的地、跨轮目的地追问四个方向，每个方向大概测什么。

**场景**

一个具体的测试情境，一句话就能说清楚。

例："导航过程中改目的地""多轮对话后追问之前说过的地点"——这些都是场景。

**用例**

基于场景写成的完整测试脚本，包含前提条件、用户说什么、助手该怎么回、怎样算过。

例：针对"导航过程中改目的地"这个场景，一条用例长这样：

- 前提条件：车速60km/h，正在导航去公司
- 剧本：`用户：改去机场 → 管家：（把目的地改成机场，开始导航）→ 用户：还有多久到 → 管家：（播报剩余时间和距离）`
- 通过标准：助手把目的地改成机场、播报剩余时间、导航任务不被中断

现在我们做了什么：

**项目理解沉淀**

把客户PRD、必过case表喂给AI，AI提炼出"这个项目该测哪些**测试维度**"，形成一棵标签树，团队共用，不用每个人都重新理解一遍。

**自动规划**

用一句话描述需求（如"测多轮记忆下的导航场景"），AI自动生成一份**计划（Plan）**，把模糊需求理解清楚、拆成要覆盖哪些方向。

**批量造场景**

大模型基于计划自动想象并生成几十上百个具体**场景**，人只需扫一眼业务合不合理。

**自动写用例**

基于场景自动生成完整的测试**用例**（用户说什么、助手该怎么回、怎样算过，合理前提条件配置），测试人员从"写用例"变成"审用例"。

**质量自动把控**

系统自动评估生成的用例质量和覆盖率，重复的、不合格的自动筛掉，人再做最终确认。

**沉淀成资产**

所有用例统一入库，新项目可复用，一次性结果变成长期企业资产。

> **举例：奔驰项目客户丢过来80条必过case + 产品丢过来PRD，一个上午发生了什么？**
> 1. **理解项目**（过去：资深测试花2-3天逐页啃PRD、逐条理解case，靠脑子记项目要测什么 → 现在：把PRD和case喂给AI，半小时提炼出测试维度标签树，团队共用，谁来都能看懂）
> 2. **规划要测什么**（过去：靠人绞尽脑汁规划，但人的水平参差不齐，对车载助手场景和项目要求理解深浅不一，规划质量全看个人 → 现在：一句话说"测多轮记忆下的导航"，AI给出计划：单轮导航、多轮导航、打断改目的地、跨轮追问四个方向，扫一眼就知道全不全，不依赖个人水平）
> 3. **造场景**（过去：测试人员绞尽脑汁一个个想场景，一天想不出几十个 → 现在：AI基于计划自动想象生成几百个场景，测试人员只需扫一眼业务合不合理）
> 4. **写用例**（过去：10分钟只能憋出5条，而且憋不出复杂的用例，只能大量堆简单单轮用例，多轮、跨轮、带前提条件的复杂场景根本写不动 → 现在：AI基于场景自动写出完整用例，10分钟产出200+条，复杂多轮跨轮用例一样能写，测试人员从"写"变成"审"）
> 5. **质量把控**（过去：靠人逐条检查，漏了没人知道 → 现在：系统自动评估质量和覆盖率，重复的、不合格的自动筛掉，人只做最终确认）
> 6. **沉淀成资产**（过去：用例散落在各人电脑的Excel里，换个人就接不上 → 现在：统一入库，新项目可直接复用，一次性结果变成长期企业资产）
> **一个上午，几百条高质量高覆盖率用例到手，测试2-3小时抽审完即可用。过去同样的事要一周。**（一个项目大概2000条语音测试用例，合成规模可按需调整）

### 引擎二：AI自动跑测试

过去测试人员要坐到车机前，一条条念台词、等回复、人脑判断过没过、手动记结果，一天跑不了多少条，晚上下班车机就闲置。

**原理一览：**

```
一批用例（AI造好的）
            ↓
   ┌──────────────────┐
   │  ① 假人AI         │  按剧本念台词 + 随机应变追问
   │                  │  例：假人说"改去机场"，车机没听清就换种说法再说一遍
   └──────────────────┘
            ↓
        真实车机
            ↓
   ┌──────────────────┐
   │  ② 裁判AI         │  逐条对照标准评判，给通过/失败+理由
   │                  │  例：标准"改成机场"，车机回"已导航到机场"→通过
   └──────────────────┘
            ↓
   ┌──────────────────┐
   │  ③ 自动留痕       │  对话历史 + trace + 视频 + log
   │                  │  例：假人说啥、车机回啥、裁判判啥，全留痕
   └──────────────────┘
            ↓
   ┌──────────────────┐
   │  ④ 人复核（按需）  │  多人并行对着视频log审，给人工评价
   │                  │  例：重要交付前，多人分工复核AI评判结果
   └──────────────────┘
```

一句话：**假人AI替人念台词，裁判AI替人判对错，全程留痕，人只做按需复核。**

先解释几个后面会用到的词：

**用例（Case）**

一条完整的测试剧本——包括前提条件（如车机当前在导航中）、假人该说什么（可带前导段指导假人怎么演）、助手该怎么回、怎样算过，相当于一份给假人和裁判的"考试题+评分标准"。

例：`前提条件：车机当前正在导航去公司；用户：改去机场；通过标准：助手把目的地改成机场并开始导航`。

**假人（FakePerson）**

AI扮演的"虚拟测试员"，像真人一样跟车机说话——会按剧本演绎（剧本前导段相当于导演指导，告诉假人该怎么演：行为模式、重试规则、唤醒词、应答策略等），也会随机应变追问、根据车机回复决定下一句说什么。

例：剧本里写"用户说改去机场"，假人就会真的开口说"改去机场"；如果车机没听清回"没听懂"，假人会像真人一样换种说法再说一遍（这正是前导段教它的重试规则）。

**裁判（Judge）**

AI扮演的"阅卷老师"，每跑完一条用例，对照"怎样算过"的标准判定通过或失败，并给出理由。

例：用例标准是"助手把目的地改成机场"，车机实际回复"已为您导航到机场"，裁判判定**通过**；如果车机回"导航到公司"，裁判判定**失败**，并给理由"目的地未改成机场，仍是公司"。

**过程轨迹（Trace）**

测试过程中每一步的记录——假人说了什么、车机回了什么、中间发生了什么、裁判判了什么，全留痕可追溯。

例：`第1轮：假人说"改去机场" → 车机回"已为您导航到机场" → 第2轮：假人说"还有多远" → 车机回"还有15公里" → 裁判判定：通过（目的地已改+距离播报正确）`。

现在我们做了什么：

**AI嘴替自动对话**

AI替代人跟车机对话，按预设剧本演绎，也能随机应变应对多轮沟通。

**24h无人值守**

白天人上班，夜里AI继续跑，车机资源吃满，不再"人等机、机等人"。

**Case级AI裁判**

每条用例都有自己的"怎样算过"标准，AI逐条评判，不再所有case共用一把尺子。

**结果平台统一管**

对话历史、过程轨迹、通过率、视频、日志全留在平台，随时查看、导出、人工复核。

**浏览器即开即用**

任何能上网的设备打开浏览器就能测，不用装软件、不用同步资料。

> **举例：奔驰项目2000条语音用例，一个晚上发生了什么？**（1台车机一晚约跑540条，4台车机一晚跑完）
> 1. **开跑**（过去：测试人员坐车机前，一条条念台词、等回复、人脑判断过没过、手动记结果，一天跑不了几十条，晚上下班车机就闲置 → 现在：下班前在平台一键启动4台车机并行，假人AI替代人跟车机自动对话，裁判AI逐条评判，夜里车机没人也能跑）
> 2. **多轮对话**（过去：人得记剧本上下文，长对话容易忘、容易错，复杂多轮场景根本测不动 → 现在：假人AI按剧本演绎还能随机应变，跨轮记忆、打断改任务、带前提条件的复杂场景一样能跑）
> 3. **评判通过与否**（过去：人脑判断+手动记录，即使是有限的自动判断，所有case也共用一把笼统的尺子，细场景分不清 → 现在：每条用例都有自己的"怎样算过"标准，裁判AI逐条评判并给出理由，不再共用一把尺子）
> 4. **留存证据**（过去：人工拉ADB日志、手动录屏，一条条操作，容易漏 → 现在：对话历史、过程轨迹、视频、日志case级自动留存，不用人管）
> 5. **看结果**（过去：Excel手动填结果，翻视频翻日志找问题 → 现在：第二天上班直接看平台汇总，通过率、失败项、理由一目了然）
> 6. **人工复核**（过去：人必须守在车机前当场跑一条评一条，人下班车机就停，8小时之外全浪费，而且审核也只能一个人卡在一台车机前串行干 → 现在：AI先跑完留痕并已给出AI评判结果，人和车机解耦——车机24h吃满不受人上下班影响；第二天上班如需人工复核，一大群测试人员可分工并行在平台上对着视频和log复核、给出人工评价，审核效率成倍提升。日常迭代通常只需看AI评判结果和未通过项，重要交付前的最终测试才需要全面人工复核）
> 7. **分流给研发**（过去：靠人回忆、翻记录描述问题，研发还得自己复现 → 现在：点开失败项直接看对话历史、过程轨迹、裁判理由、视频log，研发精准定位问题）
> **一个晚上（4台车机并行），2000条用例自动跑完、自动评判、自动留痕。第二天上班测试人员看AI评判结果和失败项，如需人工复核可分工并行，失败项直接分流给研发。**

### 人做什么？

> 人从"从头干到尾的苦力"，变成"**只做关键判断的审核者**"——判断AI造的用例对不对、AI跑的测试结果准不准，**只在需要时对着视频和log人工复核、给出人工评价**。其余全自动。

积累大量行业通用高质量测试用例集，新项目可快速复用，**确保交付的智能体高质量**。

### 6. 反哺产品标准化 🎯

基于通用用例形成车载助手标准产品，接新项目时直接甩出高质量方案，**降低被客户牵着鼻子走的风险**，极大降低定制化成本。

### 7. 行业地位与融资 💰

适当时机开源行业通用评测，**形成行业标准，占领行业地位**，非常有利于融资。

# 不同人员/场景下的应用情景与价值

## 测试团队：标准项目交付测试

### 应用情景故事：

> **奔驰项目交付测试，一个工作日发生了什么？**
> 1. **接到需求**（过去：客户丢过来PRD+80条必过case，资深测试花2-3天逐页啃、逐条理解，靠脑子记项目要测什么 → 现在：把PRD和case喂给AI，半小时提炼出测试维度标签树，团队共用）
> 2. **合成用例**（过去：测试人员绞尽脑汁手写，10分钟憋出5条简单单轮用例，复杂多轮场景写不动，2000条要好几周 → 现在：一个上午AI合成出2000条高质量高覆盖率用例，复杂多轮跨轮用例一样能写，资深测试2-3小时抽审完）
> 3. **跑测试**（过去：测试人员坐车机前一条条念，一天跑不了几十条，晚上下班车机闲置，2000条要十数人日 → 现在：下班前一键启动4台车机并行，夜里AI自动跑完2000条，裁判AI逐条评判）
> 4. **看结果**（过去：Excel手动填结果，翻视频翻日志找问题 → 现在：第二天上班直接看平台汇总，通过率、失败项、AI裁判理由一目了然）
> 5. **人工复核**（过去：全靠人一条条过，量大审不完，且只能一个人卡一台车机前串行 → 现在：如需复核，一大群测试人员分工并行对着视频和log复核，只看关键项和失败项）
> 6. **分流给研发**（过去：靠人回忆描述问题，研发还得自己复现 → 现在：点开失败项直接看trace+裁判理由+视频log，研发精准定位）
> **结论：通用标准车载智能体助手基本满足该项目要求，只需再抠一些细节改进即可交付。过去同样的事要数周。**

### 价值：

> **测试团队可互不干扰地并行多个交付项目的测试工作**，并且极大提升了工作效率，从而降低团队招聘需求减少成本，以及让团队少加班。

## 研发团队：项目车载助手调试

### 应用情景故事：

> **研发开发多轮记忆功能，调试一个跨轮上下文延续的问题，发生了什么？**（用非语音的内容层自动测试，高并发跑批，不占车机、不依赖语音）
> 1. **要测的功能**（过去：研发写完代码，要等测试排期给用例，或自己手写几条简单单轮用例凑合测，复杂多轮场景根本没法测 → 现在：直接打开平台，选一个相关数据集，或自己一句话让AI合成一批多轮用例）
> 2. **跑测试**（过去：研发只能跑简单单轮用例，复杂多轮、记忆类、跨轮上下文的用例根本没法跑，这些恰恰是最容易出bug的地方 → 现在：在工位上建个跑批任务，内容层AI自动测试高并发跑完几百条，复杂多轮记忆类用例一样能跑，不占车机、不依赖语音，几分钟出结果）
> 3. **定位问题**（过去：没有详细trace积累，不清楚通过标准、也不知道为何没通过，难以定位根因 → 现在：某条多轮用例没过，点开对话历史和trace，AI裁判给出理由：第三轮追问时助手丢了上一轮的目的地，通过标准一目了然）
> 4. **修复验证**（过去：改完代码要重新排队跑车机，验证周期长 → 现在：定位到记忆槽位回收逻辑问题，改完代码再跑一遍跑批，几分钟验证修复生效）
> **结论：随测随改，精准定位。不占车机、不依赖语音，高并发跑批几分钟出结果。过去调试一个多轮问题要大半天甚至几天，现在几十分钟搞定。**

### 价值：

> **研发人员有强大调试工具加持，可以精准定位问题**，极大提升研发效率，降低团队招聘需求减少成本，以及让团队少加班。

## 售前团队：客户POC演示

### 应用情景故事：

> **客户明天来做POC，售前准备演示，发生了什么？**
> 1. **准备演示**（过去：售前临时背台词、怕现场念错，手忙脚乱准备脚本 → 现在：打开平台，挑出维护好的「导航」「车控」「多轮记忆」演示Case，一键启动语音自动测试）
> 2. **现场演示**（过去：售前亲自念台词，紧张容易出错，顾着念就顾不上观察客户 → 现在：车机和AI自动对话，售前腾出手观察客户反应、随时讲解）
> 3. **应对临场需求**（过去：客户现场临时想试某个刁钻场景，售前根本没法当场造出符合的用例来演示，只能口头说"后续可以支持" → 现在：售前熟悉用例结构的话当场手改一条用例再跑，几秒出结果；再不行，直接用数据合成当场合成一批）
> 4. **留存证据**（过去：演示完没留痕，客户想要证据得重新跑 → 现在：结果和录像已存平台，可直接作为车机表现良好的证据给客户看）
> **结论：先进的自动对话工具本身就是一张「AI原生公司」名片。过去售前演示提心吊胆，现在从容应对。**

### 价值：

> **先进的自动对话工具本身就是一张「AI原生公司」名片**——从公司文化、研发工具到产品都贯彻AI原生理念，更容易赢得客户信任打动客户，**提升获客成功率**。

## 任何人：产品/管理层/来访客户直观体验

### 应用情景故事：

> **产品、管理层、来访客户想直观体验车载助手，发生了什么？**
> 1. **想看体验**（过去：想看助手效果，简单场景还能靠人念几条，但想随心所欲造各种简单或复杂的用例马上测根本不可能，只能等测试人员有空配合 → 现在：任何人打开语音自动测试页面，预设典型示例一字排开，一键选中即可，想测什么当场造当场跑）
> 2. **跑场景**（过去：想看多轮/车控/记忆类复杂场景，得靠测试人员提前准备用例、人念台词配合，临时起意根本测不了 → 现在：点哪个跑哪个，AI替代人和车机把对话跑完，多轮、车控、记忆类复杂场景都行，当场造当场跑）
> 3. **看结果**（过去：只能靠感官判断，没有客观结论，看完心里还是没底 → 现在：跑完直接看对话历史和AI评判结论，几分钟建立第一手直观认知）
> 4. **对齐认知**（过去：各人理解不一，沟通没有共同基础，决策靠想象 → 现在：管理层看完有底，产品看完对齐认知，客户看完信任度提升，后续沟通决策都建立在"亲眼见过"的基础上）
> **结论：任何人不懂技术也能一键获得第一手直观体验。过去想看个效果要协调半天，现在几分钟搞定。**

### 价值：

> **任何人不懂技术也能一键获得第一手直观体验**——提升所有人对产品的直观认知，快速对齐认知，方便后续沟通和决策。
