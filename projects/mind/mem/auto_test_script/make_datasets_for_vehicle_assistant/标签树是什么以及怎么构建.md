# 标签树：车载助手评测的"能力地图"——定义、用处与构建方法

> 本文面向所有参与车载助手测试的同事。读完你应当能回答四个问题：
> 1. 标签树是什么？
> 2. 没有它会怎样？（它到底解决了什么问题）
> 3. 一棵合格的标签树长什么样？（构建标准与原则）
> 4. 给一个新项目，我从哪开始、按什么思路把它建出来？

---

## 1. 一句话定义

**标签树是一棵树状的能力目录：叶子是"可直接判对错的具体测试点"，树枝是能力域和功能模块的分组。它把"这个助手该会什么"变成了一份可勾选、可统计、可追溯的清单。**

用一张真实现成的图感受一下（奔驰项目标签树，局部）：

```
车机助手评测标签树
├── 产品视角标签子树                      ← 按业务功能组织
│   ├── 车控操作
│   │   ├── 空调操作
│   │   │   ├── 空调开关            [叶子]
│   │   │   ├── 温度调节
│   │   │   │   ├── 温度增减调节    [叶子]
│   │   │   │   └── 温度直接设定    [叶子]
│   │   │   ├── 风量调节
│   │   │   │   ├── 风量增减调节    [叶子]
│   │   │   │   └── 风量直接设定    [叶子]
│   │   │   └── ...
│   │   ├── 座椅操作 ...
│   │   └── 车窗天窗遮阳帘操作 ...
│   ├── 导航服务 ...
│   ├── 媒体播放控制 ...
│   └── 联网信息查询 ...
└── 通用对话Agent视角标签子树              ← 按对话能力组织
    ├── 意图理解 ...
    ├── 对话推进 ...
    ├── 鲁棒性与恢复 ...
    ├── 安全与合规 ...
    └── 评测结果预期
        ├── 可完成 / 需澄清 / 应拒绝 / 应降级处理   [叶子，四选一互斥]
```

两个关键约定，先记住：

- **只有叶子可以打标**。每条测试用例（case）的 `tags` 字段只能填叶子标签——"空调操作"这种中间分组节点不能出现在 tags 里。
- **全树节点名全局唯一**。不同分支下也不允许重名，否则打标时会产生歧义（"你说的是哪个'开关'？"）。

## 2. 它到底有什么用？——没有标签树的世界

想象你要评一个车载助手，有 2000 条测试用例，但没有任何分类体系。你会立刻撞上四堵墙：

| 没有标签树的世界 | 有标签树之后 |
|---|---|
| **出题靠灵感**："今天再想几条 case……测点歌吧。"想到什么测什么，测了一年发现"驻车空调控制"一条都没测过。 | **出题按地图**：先看标签树哪些叶子是覆盖空洞，对着空洞定向出题。 |
| **每条 case 是孤岛**：这条测空调的 case 和那条测空调的 case 有什么关系？说不清。 | **每条 case 有坐标**：case 打上叶子标签后，天然归入能力域，可按域检索、去重、组合。 |
| **覆盖度靠感觉**："我们测得挺全的吧？"没人能证伪。 | **覆盖度可计算**：402 个叶子，已覆盖 300 个，覆盖率 74.6%，空洞清单如下——一句话说清。 |
| **case 写得对不对没标准**：这条 case 到底测没测到它声称测的东西？ | **审核有硬依据**：审核会做硬校验——tags 必须全是叶子、标签语义要被剧本实际支撑（打了"需澄清"，剧本里就得真的有歧义触发追问）。 |

再加第五个用处——**组合出题**。标签树让我们可以做"叶子组合采样"：比如抽出（副驾座椅加热 × 隐喻表达 × 多轮）这个组合，定向生成一条"副驾有点冷"的 case。复杂 case 的多样性不是靠运气，是靠标签的组合空间撑起来的。

一句话总结：**标签树是整个评测体系的坐标系。出题、打标、审核、覆盖统计都建立在它之上。坐标系歪了，后面全歪。**

## 3. 构建标准：一棵合格的标签树长什么样

### 3.1 结构标准：双子树

一棵完整的车载助手标签树有**两个视角的子树**，缺一不可：

**（1）产品视角标签子树**——"助手作为车载产品会什么"

按 `能力域 → 功能模块 → 评测点` 三层组织，例如：

| 能力域 | 功能模块 | 评测点（叶子）举例 |
|---|---|---|
| 车控操作 | 空调操作 | 空调开关、温度增减调节、温度直接设定 |
| 导航服务 | 目的地设置 | 精确地点直达、模糊需求追问 |
| 媒体播放控制 | 播放控制 | 暂停播放、切歌、倍速调节 |

**（2）通用对话Agent视角标签子树**——"助手作为对话Agent会什么"

这是行业层面的评测视角，**不会出现在任何需求文档里**，必须由标签树自带：

- 意图理解（显式指令、隐喻表达、场景意图推断……）
- 对话推进（追问澄清、多轮承接、改口纠错……）
- 鲁棒性与恢复（口误容忍、耳语重试……）
- 安全与合规（各类违规内容拒绝……）
- 交互结构与难度（单轮/多轮、并发多指令……）
- 评测结果预期（可完成 / 需澄清 / 应拒绝 / 应降级处理，四选一互斥）

为什么必须两个视角？因为只看产品视角，你测出来的是一份"功能清单核对表"，测不出"用户说'副驾有点冷'时它到底懂不懂"这种对话能力；反过来只测对话能力，会漏掉驻车空调、4D音效这类具体功能点。

### 3.2 叶子标准：可判对错的具体测试点

这是最核心的一条。**每个叶子必须是一个"能写出断言的具体测试点"**，不是抽象品质词。

| ❌ 不合格的叶子 | 为什么不合格 | ✅ 合格的叶子 |
|---|---|---|
| 结果可用性 | 什么叫"可用"？无法写断言 | 导航结果可直接导航 |
| 明确关键词优先 | 描述实现策略，不是测试点 | （删掉，或拆成具体行为） |
| 空调控制 | 太粗——开关/温度/风量/风向是不同能力点，失败原因各不相同 | 空调开关 / 温度增减调节 / 温度直接设定 / 风向调节（拆开） |

**粒度判断口诀：这个叶子挂了，能不能独立归因？** "空调挂了"归因不到具体模块；"温度直接设定挂了"能。

反过来也不要拆过细——"温度直接设定到偶数""温度直接设定到奇数"没有评测意义，是同一个能力点。

### 3.3 命名标准（硬规则）

1. **用车载业务通用语言**，不用具体项目的英文工具名/接口名。工具名随车型/项目变更，标签要用"风量调节"而不是"setFanSpeed"。
2. **简短名词化**，2-6 字优先："切歌"而不是"用户在播放过程中要求切换到下一首歌的能力"。
3. **子树节点名不带父级前缀**："车控操作→空调操作→空调开关"，不写"车控空调开关"。
4. **全局唯一**，全树任何层级不允许重名。
5. **数量维度分区间**：途经点不设"途经点控制"一个叶子，而是"1个途经点 / 2-3个途经点 / 4个及以上"——因为不同数量的复杂度差异大，是不同的测试点。
6. **互斥的评测结果预期叶子四选一**：一条 case 只能是可完成/需澄清/应拒绝/应降级处理之一；若 case 设计导致结果不确定，应拆成两条 case。

### 3.4 内容边界标准：只收"内容层面"的能力

标签树只描述**用户可从对话中感知**的能力（"助手说了什么、做对了没有"），以下一律不进标签树：

- ❌ 技术实现（调了什么 API、用了什么模型）
- ❌ 性能指标（响应延迟、吞吐量、SLA）
- ❌ UI/UX 规格（布局、动画）
- ❌ 部署运维、业务运营指标（DAU、转化率）

**判据一句话：用户在车上能不能感知到这个点做没做对？能感知的才配成为叶子。**

## 4. 构建思路：领域常识为主体，需求文档只提供增量

这是新手最容易走偏的地方。拿到一份 200 页的 PRD，很多人会从零开始逐页提炼标签——**不要这样做**。

**正确的心智模型：**

```
车载助手项目大同小异。标签树的主体来自领域常识（基础标签树），
需求文档只提供增量：多了什么、少了什么、粒度有什么不同。

基础标签树（领域能力图谱，随行业认知缓慢演进）
    │
    ├─ + 新增：需求里有但基础树没有的（"支持手势控制天窗"→ 新增叶子）
    ├─ - 排除：基础树有但本项目明确不支持的（"不支持座椅位置调节"→ 删叶子）
    └─ ~ 调整：粒度或命名与基础树不同（"风量只有3档"→ 调整粒度）
    │
    ▼
项目标签树
```

为什么这么做：

1. **需求文档是产品视角的，不是评测视角的**。PRD 写"支持空调控制"，但评测需要知道"温度增减和温度直接设定是两个测试点"——这个拆分需求文档不会告诉你，领域常识才有。
2. **通用对话Agent视角（隐喻、改口、追问、鲁棒性）永远不会出现在需求文档里**，因为产品经理默认助手"当然要听得懂人话"。这部分只能由基础标签树自带。
3. **从零构建不可复用也不可比较**。每个项目各造各的树，跨项目的覆盖度、失败率就没法对齐。

## 5. 构建步骤：给一个新项目，五步建出标签树

以奔驰项目的真实构建过程为例：

### 第一步：盘点输入

| 输入 | 说明 |
|---|---|
| 基础标签树 | 领域通用起点（我们是 `base_vehicle_assistant_case_tag_tree.json`，约 250 叶子） |
| 需求文档 / PRD | 项目特有能力与边界（"支持哪些车控""明确不支持什么"） |
| 已有测试用例（如有） | 从"他们测了什么"反推标签体系，交叉验证 |
| 产品/研发的口头输入 | 对话中确认能力边界（"座椅按摩能调吗？""不能"） |

### 第二步：做增量 diff，产出 +/-/~ 清单

把需求文档的能力点与基础标签树逐项对照，输出三张清单：

- **新增清单**：本项目有、基础树没有的能力 → 挂到对应功能模块下
- **排除清单**：本项目明确不支持的能力 → 从树中删除（这条同样重要——给不支持的能力出题，助手拒答是正确行为，测了也是白测）
- **调整清单**：粒度/命名的差异 → 对齐项目实际

**注意**：识别增量的过程同样要过"内容层面过滤"（§3.4），技术实现、性能指标在此就被丢掉。

### 第三步：对话迭代打磨

拿 diff 清单和相关方（产品、研发、测试）逐域确认：

1. 能力域覆盖全不全？有没有整个缺失的域？
2. 每个功能模块下的叶子合理吗？有没有要补充或拆分的？
3. **车主视角拷问**："你在车里会怎么跟助手说？有没有你觉得它应该能做但没列出来的？"
4. **能力边界拷问**："哪些是明确不支持的？"（决定排除清单）
5. 叶子命名是否口语化、无歧义、全局唯一？

### 第四步：同步打标指南（和标签树同等重要！）

标签树 JSON 只是骨架，**每个叶子还必须在打标指南（guideline）里写清两件事**：

- **详情**：这个标签到底测什么，边界在哪
- **例子**：真实车主的说法示例

为什么这一步不能省：打标的人和审核的人看到"风量直接设定"五个字，理解未必一致。指南就是消除歧义的说明书。经验上，**高频打标错误几乎都源于指南里两个叶子的边界没写清**（例如"应拒绝"vs"应降级处理"、"精确地点直达"vs"结果可直接导航"），边界要写成对照表放进指南。

### 第五步：验证与记录

- 结构校验：树可解析、无环、叶子名全局唯一（我们有脚本做硬校验）
- 数量 sanity check：叶子总数是否合理（奔驰项目 402 叶；突然暴涨通常意味着拆得过碎）
- 在树根记录迭代信息（版本、日期、changelog），标签树是**持续演进**的产物，不是一次性交付物

## 6. 怎么构建得更科学：几条深层原则

### 6.1 树是活的：在使用反馈中演进

标签树不是建完就锁死的交付物，而是**在使用中被检验、在反馈中修订**的活文档。每一次下游使用都在考验树的质量，发现问题就回溯到树本身：

- 写 case 时发现某叶子粒度不合理（挂了标签却写不出有区分度的断言）→ **回到树拆分/合并叶子**
- 审核时发现标签定义模糊（审核员频繁误判两个相近叶子）→ **回到树精化语义和指南**
- 覆盖统计发现缺口需要新标签 → **回到树补标签，再继续推进**

一个实际的例子：奔驰项目最初 245 个叶子，对照客户 Excel 的 919 个功能三元组后扩展到 402 个——这次扩展正是覆盖统计发现缺口后回溯修订标签树的产物，并且产出了扩展报告（每个新增叶子挂在哪个模块下、为什么加）。

### 6.2 覆盖度是唯一.truth 的进度指标

有了标签树，"测试做得全不全"从感觉变成数字：

- **按叶子统计**：402 叶子中多少叶子至少有一条 case 覆盖？空洞清单是什么？
- **按组合统计**：核心功能叶子 × 对话能力叶子（如"空调直接设定 × 隐喻表达"）的组合覆盖了多少？
- **反过来警惕**：错标一个叶子 = 整条 case 进错桶。所以覆盖度报告的前提是打标准确，这就是审核时要硬校验 tags 的原因。

### 6.3 别让标签树变成需求文档的复印件

需求文档的粒度是**产品交付粒度**（"空调控制：支持开关/温度/风量"），标签树的粒度是**评测归因粒度**（"温度增减调节"和"温度直接设定"要分开，因为失败原因不同）。前者到后者需要一次**评测视角的再加工**，这是构建标签树时真正需要动脑子的地方，也是自动化工具帮不上忙的地方。

### 6.4 宁可结构稳定，不可标签膨胀

- 中间节点（能力域、功能模块）是**分组**，不是能力本身，不要打标
- 新增叶子前自问：它和现有叶子的失败模式能区分开吗？区分不开就先不拆
- 死叶子（一年没有任何 case 覆盖、也不在出题计划里）定期清理，树的规模失控会直接抬高打标和审核的成本

### 6.5 打标一致性是树的质量的最终检验

一棵设计良好的标签树，应当让两个不同的人（或 LLM）给同一条 case 打标时得到相同结果。如果做不到，问题通常不在打标的人，而在树：

- 两个叶子语义有重叠 → 拆分边界没切干净
- 叶子名有歧义 → 命名违反了 §3.3
- 指南里没有对照表 → 补"易混标签对"的区分标准

## 7. 常见误解 FAQ

**Q1：标签树不就是需求文档的功能列表复制一遍？**
不是。三个差别：①多了通用对话Agent视角（需求文档没有）；②粒度按评测归因重新拆分（见 §6.3）；③排除了不支持项（需求文档列的是"要做的"，标签树是"该测的"）。

**Q2：为什么评测结果预期（可完成/需澄清/应拒绝/应降级处理）也做成标签？**
因为它把"这条 case 期望的正确行为"变成可统计的字段。统计"应澄清的 case 里助手有多少次直接硬干了"，比逐条读剧本高效得多。

**Q3：一条 case 可以打多个叶子标签吗？**
可以且应该。典型组合：至少 1 个产品视角功能叶子 + 1 个通用对话能力叶子 + 1 个结构/难度叶子（+ 风险 case 补安全合规叶子）。标签的组合正是复杂 case 设计的素材。

**Q4：中间节点（如"空调操作"）能出现在 tags 里吗？**
不能。只有叶子可以打标，审核时会做硬校验，非叶子标签直接判不通过。

**Q5：树建好之后还能改吗？**
能，而且应该改——树在使用反馈中持续演进（§6.1）。改完记得同步打标指南并 bump 版本记录。

**Q6：新项目要不要从基础树开始？能不能直接抄上一个项目的树？**
推荐路径仍是"基础树 + 本项目增量"。直接抄兄弟项目的树会把别人项目的排除项和粒度差异也抄过来。如果两个项目确实高度相似，可以先 diff 两棵树再决定。

## 8. 术语速查

| 术语 | 含义 |
|---|---|
| 标签树（Tag Tree） | 树状能力目录，评测体系的坐标系 |
| 叶子 / 叶子标签 | 树的末端节点，唯一允许写入 case.tags 的标签 |
| 中间节点 / 分组节点 | 能力域、功能模块等分组，只用于组织，不可打标 |
| 基础标签树 | 领域通用能力图谱，各项目共用起点 |
| 项目标签树 | 基础树 + 项目增量后的产物 |
| 打标 / 打标签 | 给 case 的 tags 字段选择叶子标签 |
| 打标指南（guideline） | 每个叶子的"详情+例子"说明书，消除打标歧义 |
| 覆盖度 / 覆盖空洞 | 已有 case 的叶子占比 / 没有任何 case 覆盖的叶子清单 |
| 组合采样 | 从多个叶子标签的笛卡尔组合中抽样定向出题 |
| 评测结果预期 | 可完成 / 需澄清 / 应拒绝 / 应降级处理（四选一互斥叶子） |

---

## 9. 更高一层：任何测试都需要一棵"标签树"

前面所有内容都以车载语音助手为例。但标签树不是车载测试的专利——**只要你用"一批测试样本来衡量一个系统"，你就需要一棵标签树，无论测的是接口、页面、模型还是智能体。** 这一节把前面的知识提升到通用层面，供任何做测试的人使用。

### 9.1 本质定义（脱离车载语境）

剥掉车载的外衣，标签树的本质是两件事：

1. **被测能力的分类体系**：一棵树（或任何分类结构），把"系统该会什么"从含糊的整体拆解为可枚举、可归组的测试点；
2. **样本到分类的挂载关系（打标）**：每条测试样本都挂到至少一个测试点上。

任何基于数据集的测试都是三元组：

```
样本（case） × 分类体系（标签树） × 判定（断言）
   测了什么情境      属于什么能力         怎样算过/挂
```

**没有第二项，样本再多也只是"一堆测试"，不是"一份评测"**——因为你回答不了"测全了吗""哪里弱""这条和那条是什么关系"这三个问题。

### 9.2 传统测试里你早就见过它

传统接口测试、功能测试中，标签树一直存在，只是换了名字：

| 你熟悉的形态 | 它其实就是标签树 |
|---|---|
| 需求追溯矩阵（RTM）：需求 ↔ 用例双向追溯 | 需求条目就是叶子，追溯关系就是打标 |
| 测试平台里"产品 → 模块 → 功能点"三级目录 | 能力域 → 功能模块 → 评测点，同构 |
| 等价类划分 + 边界值分析 | 就是在**定义叶子**：每个等价类/每个边界是一个可独立判定的测试点 |
| 冒烟集 / 回归集 / 全量集的划分 | 用标签给样本分桶，一批样本多个视图 |
| 缺陷按模块归因统计、按版本对比 | 失败样本沿分类树回滚到能力域，才能回答"哪块弱、比上版好了没" |
| 代码覆盖率工具（语句/分支/路径） | 在代码结构这棵"树"上统计覆盖——覆盖度从来都依赖某个分类坐标系 |

所以本文的原则可以逐条翻译到你的领域：

| 本文的原则 | 在传统测试里的对应 |
|---|---|
| 叶子必须可判对错 | 测试点必须有明确预期结果——等价类要划边界，就是为了让"落在边界内/外"可判定 |
| 粒度 = 能否独立归因 | 一个参数校验错误和一个业务规则错误要分成两个测试点，因为修复的人和路径不同 |
| 需求文档只提供增量 | 测试设计从来不是抄需求：把交付语言（"支持空调控制"）翻译成可测点（"温度增减"和"温度设定"分开），正是测试分析（test analysis）的经典工作 |
| 覆盖度可计算 | 需求覆盖率、代码分支覆盖率、等价类覆盖率——全部同构 |
| 在使用反馈中演进 | 缺陷逃逸分析发现某类场景没测到 → 回补分类和用例，而不是只补这一条 |

### 9.3 对话式智能体测试多出来的一维

传统接口测试的被测对象行为确定性强（输入可枚举、输出可断言），所以"能力分类"基本就是"功能清单"。

智能体测试多出来的难点在于：**同一意图有无数种表达**（隐喻、口语、改口、多轮指代、被打断），表达能力本身就是被测能力的一部分。这就是为什么车载标签树要有第二棵子树（通用对话Agent视角）——**不是理念不同，是被测对象的性质不同**。测传统系统时，这个维度退化消失，你只需要功能那一棵子树。

同理迁移到其他领域，问自己："我的被测对象，除了功能清单，还有没有第二个正交的能力维度？"

- 安全关键系统 → 失效模式
- 多端产品 → 兼容矩阵
- 推荐/搜索系统 → 相关性档位
- 大模型 → 技能 × 安全 × 鲁棒性

### 9.4 迁移到你的测试领域：三个问题

如果你测的不是车载助手，按这三问把本文迁移过去：

1. **我的"叶子"是什么？**——找到你能独立归因的最小测试点（接口的参数边界？页面的控件状态？模型的技能维度？）。判据照旧：这个点挂了，能不能独立归因。
2. **我的"第二棵子树"是什么？**——功能视角之外，被测对象有没有正交的能力维度？没有就只用一棵，有就建两棵。
3. **我的覆盖度从哪算？**——把样本挂到叶子上，覆盖率和空洞清单就自动出来了。如果今天你说不清"测全了吗"，缺的往往不是用例，是那棵树。

---

## 10. 一句话总结

**标签树把"这个系统该会什么"从一份感觉，变成一张地图：叶子是可判对错的测试点，出题按地图找空洞，打标按地图给坐标，覆盖按地图算进度。构建它的正确姿势是"领域常识打底、需求增量微调、指南消除歧义、随评测演进"——而不是把需求文档抄一遍。这套东西不专属于车载助手：任何用数据集来测试的系统，都需要这么一棵树。**
