# Duplex DynamicTask（update 版）语音实测报告

- 测试日期：2026-08-13
- 日志：[`../test_log/dynamic/`](../test_log/dynamic/)
- 场景：12 个 Case、14 个独立 session；Case 10、11 各录两次
- 详细逐事件规则审计：[`RULE_EVALUATION_REPORT.md`](RULE_EVALUATION_REPORT.md)
- 实际输入定义：[`VOICE_TEST_CASES.md`](VOICE_TEST_CASES.md)

## 1. 结论先行

真实工具结果通过`conversation.item.update` 写回任务发起时的用户 question，并在 PCM 激活后参与后续推理。

可以直接由日志证明：

1. 25 个成功结果全部发出 update，25 个全部收到 `conversation.item.updated`；没有传输丢失。
2. 36 个 accepted 业务任务全部终态闭环：25 success + 11 cancelled；成功取消后无迟到结果。
3. Case 05 的《空心》日期在后续两轮无新 FC 的情况下仍被正确读取，证明 update 内容进入了
   可持续会话上下文。
4. Case 07 的车控和迟到天气分别获得激活与回复，旧版“后结果被吞”问题本轮已消失。
5. Case 12 的天气、电影、演唱会、车控+温度连续四个工具轮都主动回复并有结果依据，长会话
   连续性良好。

但“结果写入成功”不等于“模型一定遵守结果”：Case 04 仍完整编造 POI；Case 06 出现 PCM
与真人语音混合；Case 10、11 仍暴露取消授权、错误 task_id、旧结果归属和任务历史计数问题。

## 2. 本轮真实数据流

```text
用户音频 -> Duplex ASR -> function calls
                     -> Dynamic runner 返回占位，原 FC 轮次闭合
                     -> TaskManager 后台执行
                         -> success: 原问题 + 累计结果 -> conversation.item.update
                                     -> conversation.item.updated
                                     -> 等待下行播放完成 -> PCM 激活 -> Duplex 回复
                         -> cancel: task.cancelled，不再回灌
```

同一 question 的多个结果不是分别创建新 user message，而是按完成顺序保存在本地 shadow，
每次用完整文本替换更新。Case 02、12 均验证了第二次 update 会保留第一次结果，最终一次激活
可以覆盖两项。

## 3. 机械统计

| 指标 | 结果 |
|---|---:|
| ASR completed | 68：46 纯用户 + 21 纯 PCM + 1 混合轮 |
| FC | 51：38 业务 + 13 cancel_task |
| 业务 FC | 2 个 schema 拒绝；36 个进入 TaskManager |
| accepted 任务终态 | 25 backfill + 11 cancelled |
| cancel_task | 11 成功 + 1 已结束 + 1 错 task_id |
| update / ACK | 25 / 25 |
| activation | 22，全部得到 completed ASR |
| 多结果合并激活 | 3 组 |
| 成功取消后迟到 backfill | 0 / 11 |

22 次 activation 少于 25 次 update，是三组同 question 多结果被合并激活，并非漏发。

## 5. 分维度结论

### 5.1 update 可见性：通过

- 25/25 update 收到 ACK。
- retrieve 日志能看到原 question 已被替换为“原问题 + 工具结果”。
- Case 05 在激活结束后继续追问，无新工具仍可读取《空心》7 月 17 日。

因此，旧报告中“Duplex 可能只复述 system prompt、没有看到 observation”的结论对本轮无效。

### 5.2 并发与累计结果：通过

- Case 02：导航和车控几乎同时完成，两次 update 累计保存，合并激活一次回答两项。
- Case 12：车控先完成、天气后完成，同一 question 第二帧同时包含两项，一次回答完整。
- Case 06：后续两次 websearch 也能累计后一次激活。

两种 runner 都能并发 FC；Dynamic 的差异是结果可以脱离原 FC 轮次，在 TaskManager 完成时
按 question 回写并重新激活。

### 5.3 pending、取消和修改：机制通过，语义不稳定

- Case 07/08 证明 pending 时能继续接收独立需求或依赖追问，且不会重复原工具。
- 11 次成功取消均无迟到结果，TaskManager 的取消终态可靠。
- Case 09 的明确取消、Case 11_02 的四次 supersession 正常工作。
- 但 Case 10 对同一句“取消任务”一条澄清、两条取消全部；Case 11 还生成了不存在的 task_id。

因此问题已不在 cancel worker，而在模型如何解析授权范围、引用 task_id 和陈述任务历史。

### 5.4 事实遵循：明显改善，但不是强约束

有依据的主要场景：02、03、05、06 主体、07、09 天气、10 天气、11 最终天气、12 全部工具轮。

明确失败：

- Case 04：结果唯一推荐“大森”，却完整回答另一个不存在的实体。
- Case 08：带伞有依据，但温度混用来源。
- Case 09：POI 不报结果店名，编造距离和步行时间。
- Case 10：POI 参数已漂移到 10000，模型仍声称满足原 1000 预算。
- Case 11：香港迟到结果激活后，模型按当前意图回答成上海。

这说明 update 已解决“模型拿不到事实”，没有解决“模型如何选择、归属和忠实表达事实”。

### 5.5 音频调度：下行不抢断，真人输入仍会竞争

22 次 PCM 都在此前下行音频结束后启动，没有激活 PCM 抢断正在播放的回复。Case 07 的快照
策略也让 activation 期间到达的新结果保留为待激活。

但上下行是独立流：Case 06 的第二个 PCM 与用户追问同时进入服务端，被合并成一个 ASR。
本地只等待“模型当前没在播”，无法保证“用户此刻没有开始说话”。这是兼容层不能仅靠结果队列
彻底消除的竞态。

### 5.6 Case 12：本轮最完整正例

- 成都天气：晴到多云、37/23℃和防暑建议有结果依据。
- 电影：《奥德赛》《逃出绝命街》《汪汪队立大功大电影3》《欢迎来龙餐馆》和公益场
  《万里归途》均能在结果中找到。
- 演唱会：回复“这两天没有正在开的场次”，并引用已结束的凤凰传奇和汽水音乐节。
- 空调+温度：一次回答开空调、徐汇 26–29℃和降雨，覆盖同轮两个结果。
- 语言风格：长对话保持四川话语气；第一次唱歌仍是普通歌词，用户纠正后恢复四川话版本。

本次 Case 12 没有在电影 pending 时取消，也没有在演唱会 pending 时插入车控。因此它能证明
顺序长会话与同 question 多结果连续性，不能替代旧时序的取消/抢占实验。

## 6. 最终判断

DynamicTask update 版已经形成可工作的异步兼容闭环：占位、后台任务、累计 update、主动激活、
精确取消和跨轮追问都得到真实样本支持。旧 create 版关于 observation 不可见、Case 07 结果
被吞以及 Dynamic 全面事实失败的结论，应全部撤销。

当前剩余风险按优先级是：

1. PCM 与真人语音竞争，以及混合轮的 question 归属；
2. 旧结果激活时模型可能优先回答当前意图；
3. 模糊取消授权、task_id 引用和任务历史自述；
4. 长工具结果中的事实抽取与严格约束遵循。

所以本轮应评价为：**工程数据流闭环，跨轮连续性显著改善，Case 12 表现良好；模型语义层仍有
明确反例，不能把“update 成功”写成“所有工具事实都可靠”。**
