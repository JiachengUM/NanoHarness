# Tag Tree From Requirements

从产品需求到标签树的构建环节。

## 核心理念

车载助手项目大同小异，标签树的**主体来自领域常识**，而非某个项目的需求文档。需求文档只提供**增量**（多了什么、少了什么、粒度差异）。通用对话Agent视角是行业层面的评测视角，不会出现在需求文档中，由基础标签树自带。

```
基础标签树（base_vehicle_assistant_case_tag_tree.json）
       │
       ├─ + 提取产物中的标签线索（环节0从原始文件提取的标签体系，主要输入）
       ├─ ~ 提取产物中的需求描述（环节0从原始文件提取的需求增量）
       ├─ + 需求文档中的增量（跳过环节0时的回退路径）
       ├─ - 需求文档中的排除（这个项目明确不支持的）
       ├─ ~ 需求文档中的调整（粒度/命名差异）
       ├─ ~ 对话中的用户反馈调整
       │
       ▼
项目标签树（vehicle_assistant_case_tag_tree.json）
```

## 输入

### 基础标签树（领域能力图谱）

| 文件 | 目录 | 说明 |
|------|------|------|
| `base_vehicle_assistant_case_tag_tree.json` | `artifacts/tag_tree/` | 基础标签树，车载助手领域通用，随行业认知演进缓慢更新 |
| `base_vehicle_assistant_case_tagging_guideline.md` | `artifacts/tag_tree/` | 基础打标指南 |

基础标签树是本 Skill 的起点，**运行时从文件读取**，不在 SKILL.md 中硬编码。这样做的好处：
- 基础标签树更新时只需改文件，无需同步 SKILL.md
- JSON 文件是唯一事实来源，避免 SKILL.md 与实际标签树不一致
- 基础标签树可独立演进，项目标签树可独立调整

### 外部输入（用户手动放入 `artifacts/inputs/`）

| 输入 | 目录 | 是否必须 | 说明 |
|------|------|---------|------|
| 环节0提取产物 | `artifacts/inputs/extracted/` | 推荐 | 从原始文件提取的标签线索、需求描述、已有case；环节0预处理后的结构化产物，是本环节的主要输入源 |
| 对话式输入 | 无需文件 | 可选 | 用户直接在对话中描述需求差异 |

### 上游产物（自动从 `artifacts/` 读取）

| 输入 | 目录 | 何时需要 |
|------|------|---------|
| 现有项目标签树 | `artifacts/tag_tree/` | 迭代更新时 |

### 输入发现策略

1. 读取 `artifacts/tag_tree/base_vehicle_assistant_case_tag_tree.json` 作为基础标签树
2. 检查 `artifacts/tag_tree/vehicle_assistant_case_tag_tree.json` 是否已有项目标签树
   - 有 → 以项目标签树为起点，进入迭代更新
   - 无 → 以基础标签树为起点，进入首次构建
3. 检查 `artifacts/inputs/extracted/` 是否有环节0的提取产物
   - 有 → 读取 `extracted_tag_hints.json`，与基础标签树做 diff，识别增量
   - 读取 `extracted_requirements.md`，补充需求增量
   - 读取 `extracted_cases_raw.json`，从已有case反推标签体系（交叉验证）
   - 无 → 直接展示标签树，通过对话让用户确认和调整

## 输出

| 产物 | 目录 | 说明 |
|------|------|------|
| `vehicle_assistant_case_tag_tree.json` | `artifacts/tag_tree/` | 项目标签树 |
| `vehicle_assistant_case_tagging_guideline.md` | `artifacts/tag_tree/` | 项目打标指南 |

> 注意：`base_*` 文件是基础标签树，不应被本环节修改。如需更新基础标签树，应单独进行并经过充分评审。

## 执行流程

### 第一步：读取并展示基础标签树

1. 读取 `artifacts/tag_tree/base_vehicle_assistant_case_tag_tree.json`
2. 读取 `artifacts/tag_tree/base_vehicle_assistant_case_tagging_guideline.md`
3. 解析标签树结构，提取所有一级子树和叶子标签清单
4. 向用户展示标签树概览（一级子树名称 + 叶子标签数量）

### 第二步：读取项目增量

从环节0提取产物读取增量。

从 `artifacts/inputs/extracted/` 读取环节0的提取产物：

1. 读取 `extracted_tag_hints.json`，与基础标签树做 diff → 识别 +/-/~
2. 读取 `extracted_requirements.md`，补充需求增量
3. 读取 `extracted_cases_raw.json`，从已有case反推标签体系（"他们测了什么能力？"），交叉验证增量识别
4. 交叉验证：标签线索和需求描述是否一致，矛盾处标注交由人工确认

增量类型说明：

| 增量类型 | 说明 | 示例 |
|---------|------|------|
| **+ 新增** | 提取产物中提到但基础标签树没有的能力点 | 「支持手势控制天窗」→ 新增叶子 |
| **- 排除** | 基础标签树有但本项目明确不支持的 | 「不支持座椅位置调节」→ 删除对应叶子 |
| **~ 调整** | 粒度或命名与基础标签树不同 | 「风量只有3档」→ 调整风量相关叶子粒度 |

将识别出的增量整理成清单，展示给用户确认。

### 第三步：对话迭代打磨

无论是否有需求文档，都通过对话与用户确认：

1. **能力域确认**：这些能力域是否覆盖了本项目？有没有遗漏或不需要的？
2. **逐域细化**：对每个能力域，叶子标签是否合理？有没有需要补充或拆分的？
3. **车主视角**：你在车里会怎么跟助手说？有没有什么场景觉得助手应该能做但没列出来？
4. **开发者视角**：系统有哪些能力边界？哪些是明确不支持的？
5. **命名打磨**：叶子标签命名是否口语化、无歧义、全局唯一？
6. **总结确认**：展示完整标签树，让用户最终确认

### 第四步：同步打标指南

对每个叶子标签写明：
- `详情`：该标签测什么
- `例子`：真实车主说法示例

### 第五步：验证

- 运行 `scripts/tag_tree/preview_tag_tree.py` 可视化标签树
- 确认叶子标签总数合理
- 确认双子树结构完整
- 确认所有叶子名称全局唯一

## 内容层面过滤原则

本数据集从**内容层面**评测被测助手——即评测「助手说了什么、做对了没有」，而非评测技术实现、性能指标、UI规格等。从需求文档提取增量时，必须严格过滤非内容层面的信息。

**判据：一个标签是否属于内容层面？**

| 维度 | 属于内容层面 ✅ | 不属于内容层面 ❌ |
|------|---------------|-----------------|
| 用户可感知 | 助手说了什么、做了什么 | 后台怎么实现的 |
| 可从对话文字核对 | 从对话文字能判断对错 | 需要看日志/监控才能判断 |
| 与输出内容相关 | 回复的准确性、完整性、安全性 | 响应速度、系统稳定性 |
| 与理解能力相关 | 是否理解了用户意图 | 用了什么模型理解 |

**过滤规则**：

1. 只提取「助手对用户说了什么/做了什么」的能力点
2. 丢弃技术实现细节（API调用、模型选型、架构设计等）
3. 丢弃性能指标（响应延迟、吞吐量、可用性SLA等）
4. 丢弃UI/UX规格（布局、动画、交互细节等）
5. 丢弃部署/基础设施相关内容
6. 丢弃纯业务运营指标（DAU、转化率等）
7. 对模糊内容用「用户能否从对话中感知」做最终判断

## 迭代模式

标签树是持续演进的产物，每次运行应基于当前状态增量改进，而非从零重建。

### 自回溯

本环节的输出（项目标签树 + 打标指南）可作为下次运行的输入：
- 如果 `vehicle_assistant_case_tag_tree.json` 已存在，以它为起点进入迭代更新
- 人类可直接编辑标签树 JSON 和打标指南 MD，下次运行时保留这些修改
- 增量模式：只处理新增/删除/调整的标签，不动已确认的部分
- 全量模式：用户明确要求时，从基础标签树重新构建

### 跨环节回溯

| 触发场景 | 回溯方式 |
|---------|---------|
| 环节2发现标签粒度不合理 | 回到环节1拆分/合并叶子标签 |
| 环节6审计发现标签定义模糊 | 回到环节1精化标签语义和 guideline |
| 环节7发现覆盖缺口需要新标签 | 回到环节1补充标签，再沿流水线推进 |

### 人类编辑保留

- 人类手动编辑标签树后，在根节点添加 `"manually_edited": true` 标记
- 运行时检测到该标记，提示用户确认是否保留手动修改
- 不覆盖人类已修改的节点，只处理新增/调整部分

### 迭代记录

在标签树 JSON 根节点记录：
```json
{
  "iteration": 2,
  "last_updated": "2026-05-28",
  "changelog": ["第2轮：新增手势控制天窗叶子，删除座椅位置调节"]
}
```

## 命名硬规则

1. 不用具体项目的英文工具名/接口名，用车载业务通用语言
2. 叶子标签必须是明确可测的测试点
3. 子树节点名不带父级前缀
4. 标签名简短名词化（2-6字优先）
5. 标签名全局唯一，不同分支下不允许重名
6. 数量维度分区间（如途经点分1个/2到3个/4个及以上）

## 经验教训

1. **不要用具体项目的英文工具名**：具体实现名可能随项目/车型变更，标签应使用车载业务通用语言
2. **叶子必须是可测测试点**：「结果可用性」「明确关键词优先」等抽象词必须替换成可写断言的表达
3. **能力边界要对齐真实系统**：只标系统真正具备的能力（如车载助手无法调节座椅位置，但可切换座椅模式）
4. **交互体验子树不可少**：记忆生产/消费/规律归纳/问题复盘等是车载助手的核心能力维度
5. **去冗余前缀**：`业务能力_` 等前缀应去掉
6. **粒度要拆到可独立测试**：风量调节和风向调节是不同能力点，应拆为独立叶子
7. **数量维度要分区间**：不同数量途经点的复杂度差异大，应分区间设标签
8. **需求文档只提供增量**：不要指望需求文档包含所有评测角度，通用对话Agent视角等行业层面内容由基础标签树自带
9. **基础标签树是文件不是文档**：领域能力图谱存储在 `base_vehicle_assistant_case_tag_tree.json` 中，运行时读取，不在 SKILL.md 中硬编码
