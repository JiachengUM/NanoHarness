语义泛化
语义拒识
在人机交互过程中，为了保障自然流畅的语音交互体验，有些语音输入需要被响应，有些语音输入不需要被响应，不需要被响应的就需要进行拒识处理。结合大模型（含端侧多模态大模型）的理解泛化能力，可以对拒识场景进行补充完善，例如结合上文判断、多模信号输入判断等等。
本章节需要定义清楚拒识的场景，明确在智能座舱场景中，哪些情况需要被拒识。
1. 人工干预/FAQ
人工干预和FAQ配置的内容会优先召回，不会被拒识。
2. 非人机指向
可通过逻辑判断， 并非人与车机的对话，作拒识处理。
示例说法：
你晚上别老是和孩子玩太晚！
你今天开会的时候为什么不回答客户的需求？
前方200米有限速60拍照，请注意车速
3. 非通顺对话
不通顺的没有实际语义的话，作拒识处理。
示例说法：
嗯嗯呀罢了巴拉
继续防晒要走
4. 上下文插入无关Query
下文的【主体】、【对象】、【动作】、【描述】是否和上文中涉及的【主体】、【对象】、【动作】、【描述】不相关时，作拒识处理。
示例说法：
User：这台车的功能怎么样
Bot：这台车的具有xxxx的功能
User：这个拒识效果还行 （拒识）
User：再讲讲别的功能
5. 异常CASE识别和处理
意图/多意图识别（含云端仲裁）
意图识别是自然语言处理（NLP）中一项非常重要的任务，它可以帮助我们更好地理解用户的需求和意图，从而为用户提供更加智能和高效的服务。它通常被视为一个分类问题，即通过将输入语句分类到预定义的意图类别中来识别其意图。这些类别可以是执行类的、查询类的、搜索类的。不同的意图类别，后续的处理方式也不同，可以是提槽以便执行具体结果，也可以是调用其他插件，进行完整的服务闭环。
1. 主意图
表格是字节已定义的所有意图类别，下游链路是字节推荐的标准配置
如果项目不遵循标准配置，支持意图接入自有插件、映射意图、或者直接兜底处理。
自有插件：识别到意图后，舍弃字节下游链路结果，采纳自行链路结果（云云/端云对接处理方式有区别）
映射意图：如将POI搜索类的给联网处理，可将美食、景点、娱乐、住宿，通过工程映射给闲聊/联网
兜底处理：识别到意图后，直接返回兜底话术，告知用户暂不支持此功能（云云/端云对接处理方式有区别）
在车控领域，意图识别支持隐式表达理解
如Q=“前面路看不清了”，意图结果=车控，FC会选择车内可以解决路看不清的功能，如近光灯
隐式车控包含：温度、空气质量、明暗、氛围、舒适度、开车安全等维度的感受表达
除此之外，其余存在二义性或者表达不明确的意图会给到闲聊进行二次澄清
意图识别支持多轮理解
如Q1=“帮我找一个附近评分4分以上的茶餐厅”，意图结果=美食；Q2=“有没有附近5公里以内的”，意图结果=美食；Q3=“导航去第一个”，意图结果=导航
如Q1=“周杰伦最近有没有什么新歌”，意图结果=联网；Q2=“播放第一首吧”，意图结果=媒体
支持最多5轮（滚动式）的上下文理解
2. 自定义意图
在主意图之外，支持项目进行意图自定义，如能为用户规划行程的“行程助手”、能为用户讲故事画绘本的“儿童陪伴助手”等。前提是：和主意图的定义不冲突。意图优先级上高于闲聊/联网，低于主意图其他意图。
目前仅支持项目提供功能定义和示例说法（正例&负例），字节完成评估后，再提供开发支持。并未提供开放能力至项目自行定义、配置和生效。
上下文理解
历史信息记录与学习
记录用户与大模型的全量交互历史，基于历史信息学习用户习惯、偏好及常用需求，为后续交互提供个性化支撑，同时辅助大模型持续优化回复准确性与适配性。
需确认历史数据存储的技术方案（如本地存储 / 云端存储、存储容量限制），确保符合座舱设备的性能要求；
用户喜好等数据存储和来源依赖火山主线的记忆数据库；
需遵循 SVW 关于用户数据收集、存储、使用的合规要求，明确历史信息的使用范围，避免隐私风险。
落域仲裁
若需求属于传统语音技能的覆盖范围（如基础车控指令、固定话术查询），则分发至传统语音技能模块处理；若需求需要大模型的理解、生成能力支撑（如开放式问答、多轮复杂交互、跨领域需求），则分发至大模型技能模块处理。
说明：需明确传统语音技能与大模型技能的边界范围，由火山主线与项目方共同确认分发判断的核心规则，确保分发逻辑准确、无遗漏，但也无法避免低质量的Query导致仲裁失败而对用户无响应的情况出现。

大模型标识提示
针对大模型生成内容进行标识，参考 V-Mate GPT 生成内容的标识方式，让用户清晰区分大模型生成内容与传统语音技能的固定回复。
法规要求：
标识样式需统一且清晰可见，建议采用 “【AI 生成】” 前缀或专属标识图标形式，嵌入回复内容的起始位置（语音播报时可前置简短提示音 + 语音说明 “以下是 AI 生成内容”）；
标识仅针对大模型主动生成的内容添加，传统语音技能的固定回复无需添加；
标识不影响回复内容的可读性与语音播报的流畅性，UE 层面需评审确认标识的呈现形式与位置。

内容生成质量评价
支持用户对大模型所有功能板块生成内容进行评价，采用点赞 / 点踩的简化交互方式实现，覆盖车书问答、向导服务、多媒体推荐、闲聊等所有大模型参与的功能场景。
核心说明：
评价触发时机：大模型每轮生成内容输出完成后，在回复下方同步展示点赞、点踩按钮；
评价关联范围：用户的点赞 / 点踩操作将与当前轮次的生成内容、用户原始需求强关联；
无评价交互处理：若用户未进行评价操作，不影响后续对话的正常进行，评价为可选交互项。

用户反馈学习
基于用户对大模型生成内容的点赞 / 点踩评价，建立闭环的反馈优化机制，持续提升大模型生成内容的质量。优化流程遵循既定 SOP，核心通过修复 badcase（用户点踩的内容）实现持续反馈与运营优化。
核心逻辑：
数据收集：汇总用户评价数据，筛选出点踩对应的 badcase；
分析优化：运营团队结合 SOP 对 badcase 进行分析，明确优化方向（如参数增减，优化对应逻辑等）。

内容重新生成
仅支持用户对大模型的回答内容（例如查询百科知识，查询历史人文等）发起重新生成请求，UE 评审确认无需额外设置物理按键，当前通过语言指令触发重新生成。
核心规则：
触发方式：用户可通过自然语言指令触发，示例话术：“重新回答一下”“换一种说法”“这个回答不满意，再生成一次”；
生成约束：重新生成的内容需规避上一轮回答的问题（如重复、不准确等），同时保持与用户原始需求的关联性，不偏离核心问题；

文本、图片安全校验
核心作用是检测交互过程中的敏感词及违规内容，防止违规对话、违规图片的输入与输出，保障座舱交互的安全性与合规性。
校验范围与逻辑：
输入校验：对用户输入的文本、语音转写文本、上传 / 拍摄的图片进行校验。若检测到敏感词或违规内容（如违法信息、低俗内容、辱骂性语言等），则触发风险管控逻辑，不进入后续的技能处理或内容生成环节；
输出校验：对大模型生成的文本、图片内容进行校验，若检测到违规内容，实现拦截输出

快速干预
支持通过热更新方式对大模型生成内容进行调整，核心满足 SVW 针对大模型回复的快修需求，确保问题内容能及时修复并上线。干预能力主要通过干预规则配置与FAQ 补充两种方式实现。
核心说明：
干预场景：适用于大模型生成内容出现错误、不符合品牌调性、违反车企要求等紧急情况，需快速修正的场景；
实现方式：
干预规则配置：通过后台配置干预关键词及对应修正后的回复内容，从而输出配置的修正回复，覆盖原生成逻辑；
FAQ 补充：对新增的必答问题、需统一口径的问题，通过热更新补充至 FAQ 库，FAQ 内容优先级高于大模型的常规生成内容，确保回复一致性；

文字语音图片输入
支持用户通过文本、语音、图片三种核心方式输入信息，覆盖不同交互场景下的用户需求，提升交互的灵活性与便捷性。
核心能力说明：
文本输入：支持用户通过座舱触控屏输入框手动输入文本信息（如搜索关键词、问答内容）；
语音输入：支持用户通过语音唤醒后直接口述输入，系统完成语音转文字后进行后续处理，兼容中文、英文等常用语言；
图片输入：支持用户通过座舱内置摄像头拍摄图片输入，适用于相关问答等场景（如 “前方车辆是什么牌子”）；
输入处理：不同输入方式的处理链路统一，均先经过安全校验，再由落域仲裁模块进行分发。

图片文字声音输出
支持以图片、文字、声音播报四种方式输出信息，根据用户需求类型及交互场景，自动匹配最优的输出形式，提升信息传递的效率与体验。（视频仅POI魔方展示，属于工程配置，不是基础能力）

区分不同功能标签（车书、向导、多媒体、闲聊等）
当前大模型的服务场景，通过文字tab和Avatar 动效两种方式区分不同功能板块（车书、向导、多媒体、闲聊等），提升用户对服务类型的认知度。方便用户在不同需求类型情况下进行快捷切换对应Tab进行查看。

高质量内容多端同步
支持将大模型生成的高质量内容通过二维码扫描分享的方式，实现多端查看（如用户手机、平板等设备）。

处理数据类型
支持对文本、音频、图像以及视频等多种数据类型进行计算处理，为多模态交互提供基础能力支撑，覆盖大模型所有功能板块的核心数据处理需求。

数据混合处理
支持对不同数据类型进行混合处理，即同时接收并处理多种数据类型的输入，结合多类型数据的信息进行综合分析与内容生成，提升大模型对复杂需求的理解与响应能力。

流式语义
这是一个识别的基本过程（用户说话的内容传递给大模型，大模型将进行（逐词 / 逐句）进行语义解析），主要体现在用户说了半句话或简短的指令也尽可能理解是正确的或错误，或者拒识；当缺乏最小可执行指令要素的Query内容时，可能会被当作不理解的指令或拒识，避免车内聊天或不明确指令引起误操作。

Hints引导词生成
人机对话过程中，Hints引导词的定位是引导用户进一步和车机进行对话，营造更加智能的对话体验。
一个好的Hints需要具备哪些要求：
与用户Query强相关：强相关可以定义两种类型，一种是横向的，即同类Query的推荐；一种是纵向的，即推荐更深入一级的推荐；
适合用户用语音输入：适合用户用语音输入的意思是说，长度不宜太长，一般在10字长度较好；
1. Hint生成规范
不要与历史QA中已经提问或者回答过的内容重复，历史QA为前4轮对话内容。
hint可以是问题，也可以是陈述句指令。
每轮对话生成2条hint，每条不超过20字。【Hints生成的条数支持灵活配置】
hint应该是现有系统有能力回答的问题。现有系统能力包括人设chat、web检索、车书问答、互动新闻等，不在系统能力内的典型问题例如“帮我点个外卖”。
不能生成会诱导触犯安全策略
的hint，安全策略包括通用安全策略、车企安全策略以及字节跳动暴露安全策略。车企安全策略，例如“XX汽车自燃的原因是什么“、”XX汽车质量差的原因是什么“、”XX汽车和供应商的关系如何“。字节跳动暴露安全策略，例如”字节跳动训练了你吗“、”你是如何被训练的呢“、”你的开发者是谁“。
hint应该与最后一轮的回复紧密相关，并可以引发进一步的讨论。
风险管控
在座舱产品的正常使用过程中，需要避免一些在道德或法律层面的风险内容输出，以避免对用户或者企业形象造成负面影响。为了规避这些问题，需要在输入端和输出端进行头尾控制，中间节点也可进行多轮工程化的约束。
1. 通用风险
输入：通用风险的Query输入会落入“风险”意图，基础模型进行针对性回复，不会作拒识处理；
输出：输出内容的积极正向性由总结回复模型进行约束；
2. 车厂定制风险
涉及到车厂负向类的Query输入，也会落入“风险”意图，基础模型进行针对性回复，不会作拒识处理；也支持通过人工干预的方式进行定向标准化的风险管控。
以上风险同样会在输入侧和输出侧都进行管控。
3. 非文本类风险
除文本类的输入输出风险外，对于图片、音频等类型的内容输出，同样会基于火山主线能力按照上述管控标准进行管控。
生成内容质量反馈
生成内容的用户评价反馈属于系统级的能力，火山主线提供接口能力。
用户端/界面端呈现的形式即为点赞/点踩的形式。
