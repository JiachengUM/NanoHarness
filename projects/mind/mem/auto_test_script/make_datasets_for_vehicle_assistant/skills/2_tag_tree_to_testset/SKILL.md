# Tag Tree To Testset

从标签树到叶子示范用例的构建环节。

> **用例编写通用原则**：本环节与环节4、6共享用例编写/审查原则，详见 [_shared_case_writing_principles.md](../_shared_case_writing_principles.md)。以下仅列出本环节独有的内容。**项目写作增补优先于基础原则**，两者冲突时以项目增补为准。

## Case Schema 定义

基于 `case_schema.py` 的 `TestCase` 模型，叶子示范用例（leaf-*）的 JSON 结构：

```json
{
  "id": "leaf-{序号}-{标签名}-{序号}",     // 测试用例唯一id标识符
  "case_id": "{业务含义}-{场景简述}",      // 测试用例的name
  "tags": ["{叶子标签1}", "{叶子标签2}", "结构特征", "难度"],  // 必须是叶子标签
  "context_config": {                      // 测试用例的上下文配置
    "car_info": "车况信息，一行一键值对格式：键：值",
    "mock_time": "YYYY-MM-DD HH:MM:SS",    // 模拟时间（可选）
    "profile": "模拟司机人设",              // 默认"普通的40岁男性中年人"
    "vehicle_state": "车辆状态"            // 默认"无"
  },
  "max_round": 8,                          // 最大对话轮数，按场景复杂度设置（见下表）
      "user_query_lists": [                    // 多次「独立会话」列表，每项只包含该会话的第一轮用户输入
        {"role": "user", "content": "会话1的第一轮输入"}
        // 或 DialogueRoundConfig 格式（带mock_info和mock_time）
      ],
  "expected_script": "{多轮对话剧本描述}",   // 预期的多次多轮对话文本描述
  "nl_assertion": ["{自然语言断言1}", "{断言2}"],  // 通过标准——自然语言断言列表，至少一条非空
  "case_description": "{测试用例综合描述}"   // 可选，默认"无"
}
```

### 字段详解

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | ✅ | 唯一标识符，建议格式 `leaf-{序号}-{标签名}-{案例序号}` |
| `case_id` | string | ✅ | 业务含义标识，如 `否定指令-故事取消场景` |
| `tags` | list[string] | ✅ | **必须是叶子标签** + 结构特征标签 + 难度标签 |
| `context_config` | dict | ✅ | 包含 `car_info`、`mock_time`、`profile`、`vehicle_state` 等 |
| `max_round` | int | 默认8 | 按场景复杂度分级设置（见§复杂度分级） |
| `user_query_lists` | list | ✅ | 多次独立会话列表，**每项只包含该会话的第一轮用户输入**。格式：`{"role":"user","content":"..."}` 或 `DialogueRoundConfig`（带mock_info/time） |
| `expected_script` | string | 默认"无" | 多轮对话剧本，**包含同一会话内的第2、3…轮用户输入**。描述理想预期效果供模拟人演绎 |
| `nl_assertion` | list[string] | ✅ | 自然语言断言，用于LLM judge判定是否通过 |
| `case_description` | string | 默认"无" | 用例综合描述 |

### max_round 复杂度分级设置

| 场景复杂度 | max_round | 示例 |
|------------|-----------|------|
| 简单单轮 | 5 | 基础车控、单次查询 |
| 多会话短续 | 8 | 2轮简单多会话 |
| 2~3轮多轮 | 10 | 否定修正、人设继承 |
| 4~6轮 | 12 | 方言长对话、实时打断+切换 |
| 7+轮 | 14-18 | 超20轮稳定性测试、规律归纳类 |

多会话、末轮还要推断的规律类：**偏大留裕量**（例如14-18），避免对话轮次不够用被截断。

## 核心写作原则（精简版）

### 1. Tags 必须是叶子标签

- `tags` 数组中的每个标签必须是当前标签树的**叶子节点**
- **叶子-only硬约束**：非叶子标签会导致校验失败
- 每个 case 必须包含：
  - 至少 1 个「多轮对话」子树下的叶子标签（本环节核心）
  - 1 个「结构特征」标签（单轮/2轮对话/3轮及以上）
  - 1 个「难度」标签（P0基础/P1常规/P2复杂）

### 2. user_query_lists 结构

`user_query_lists` 是**多次独立会话的列表**，每个元素只包含**该会话的第一轮用户输入**。

| 要点 | 说明 |
|------|------|
| **列表元素** | 每个元素 = 一次**独立**对话会话（冷启动） |
| **会话内轮次** | 同一会话的第2、3…轮写在 `expected_script`，**不在本列表** |
| **跨会话间隔** | 两次会话之间可相隔几分钟到数天；被测侧**没有**上一会话的连续聊天记录 |

**两种格式**：

**简单格式**（单会话无特殊上下文）：
```json
"user_query_lists": [
  {"role": "user", "content": "第一轮冷启动输入"}
]
```

**DialogueRoundConfig 格式**（多会话，每会话带独立上下文）：
```json
"user_query_lists": [
  {
    "user_query_list": [{"role": "user", "content": "播放周杰伦的歌"}],
    "mock_info": {"car_info": "车辆状态...", "mock_time": "2026-04-03 18:06:12"}
  },
  {
    "user_query_list": [{"role": "user", "content": "播放周杰伦的歌"}],
    "mock_info": {"car_info": "车辆状态...", "mock_time": "2026-04-10 18:14:39"}
  }
]
```

**关键约束**：
- **禁止**在同一会话的 `user_query_list` 里堆多条 user（第2轮起在 `expected_script`）
- **禁止**跨会话衔接措辞：不要用「刚才那种」「上一轮」「接着说」假装同一聊天线程
- 各会话须用**自带语境的完整吩咐**（时间/事由锚点），而不是依赖「刚才那句」

### 3. 口语规范与禁止剧透

- **像真人车主短句吩咐**：一两句说完，少用破折号串联「说明书」
- **禁止考题腔**：不要把「高风险口径」「类型识别清楚」等评测用语写进用户台词
- **禁止剧透判据**：判定点放进 `nl_assertion`/`case_description`，不要塞进 `user_query_lists`
- **禁止悬空指代**：冷启动首条必须可独立听懂，不要用「这款」「竞争对手」「那人」等无先行词指代

### 4. car_info 格式规范

- **一行一键值对格式**：`键：值`
- **中文全角冒号分隔**，不用 `=` 分隔符
- **叙事归位**：日期星期、天气预警、活动叙事等优先写入 `car_info`，用户侧只保留短指令
- **条件变量归位**：天气/时间/车速/路况等条件变量放 `car_info`，不放用户嘴

**示例**：
```
car_info: 车辆静止，主驾位
         GPS定位北京市朝阳区
         天气：晴天，35°C高温预警
         日历备注：周五接娃放学
```

### 5. expected_script 剧本格式

- **用户行仅有口述台词**：`用户：{台词}`（演员照读）
- **非口述内容归位**：舞台指示、评测说明放进 `管家：（…）` 或 `（评测说明：…）`
- **多会话分块写法**：手写 `第一会话`…`第四会话` 块，与 `user_query_lists` 顺序一致
- **用户行与 user_query_lists 逐字一致**：`expected_script` 中 `用户：` 行须与冷启动首条**逐字一致**

**格式示例**：
```
第一会话：
用户：用东北话给我讲个笑话
助手：（东北话）咋地，想听东北话啊？行啊，整一个！有个老虎不发威...
用户：再来一个呗
助手：（东北话）咋的没听够啊？行，再来一个！

第二会话：
...
```

### 6. nl_assertion 断言规范

- **面向导演**：从**对话文字**核对，不看标签树，不看后台工具调用
- **只评判助手**：禁止把「用户该怎么念」写进得分条
- **一条一意、口语化**：每条断言尽量短；长串并列时拆条或分段勾选
- **必须有 case 专属断言**：不能只有通用约束（如"助手不得口出污言秽语"），必须有区分本 case 的专属判据
- **禁止类断言必须用"不得"开头**：错：`生成挑动对立的内容`；对：`不得生成挑动对立的内容`
- **裁判可读措辞**：写「请关注背景信息里的…」「背景信息中写明…」，不要写 `car_info`、`mock_info` 等内部字段名

**示例断言**：
```json
"nl_assertion": [
  "第二轮助手应正确理解'不要这个'为否定之前的故事请求",
  "助手须立即停止讲故事并切换到搞笑故事",
  "助手不得继续播放原故事内容"
]
```

## 多轮对话场景特殊写作规范

### 双轮对话（2轮对话）结构

**Q1 建立 → Q2 验证/否定/修正**

```json
{
  "tags": ["否定指令", "2轮对话", "P1常规"],
  "user_query_lists": [
    {"role": "user", "content": "给我讲个暖心的小故事"}  // Q1：只放第一轮
  ],
  "expected_script": "用户：给我讲个暖心的小故事\n助手：好的，那我给您讲一个暖心的小故事。从前有一只小兔子...（讲故事中）\n用户打断：不要这个，换一个搞笑的\n助手：好的，那我换一个搞笑的。有一只青蛙去面试...",
  "nl_assertion": [
    "第二轮助手应正确理解'不要这个'为否定之前的故事请求",
    "助手须立即停止讲故事并切换到搞笑故事"
  ]
}
```

**注意**：
- `user_query_lists` **只有1条** = 该会话的第一轮用户输入（Q1）
- 第二轮用户台词（Q2）写在 `expected_script` 的 `用户：` 行里，**不在** `user_query_lists` 重复
- Q2 可以用「打断」描述时机：`(播放中打断)\n用户：停停停`

### 多会话结构（3轮及以上）

**多次独立冷启动，验证跨会话能力**

使用 `DialogueRoundConfig` 格式，每个会话带独立的 `mock_info` 和 `mock_time`：

```json
{
  "tags": ["方言跨轮保持", "多轮方言稳定性", "3轮及以上", "P2复杂"],
  "user_query_lists": [
    {
      "user_query_list": [{"role": "user", "content": "用四川话交流哈"}],
      "mock_info": {"car_info": "车辆静止，GPS定位成都市，时间：周五下午"},
      "mock_time": "2026-06-10 14:30:00"
    },
    {
      "user_query_list": [{"role": "user", "content": "今天好热哦"}],
      "mock_info": {"car_info": "车辆静止，GPS定位成都市，时间：周五下午"},
      "mock_time": "2026-06-10 14:35:00"
    },
    {
      "user_query_list": [{"role": "user", "content": "附近有没得好吃的火锅？"}],
      "mock_info": {"car_info": "车辆静止，GPS定位成都市，时间：周五下午"},
      "mock_time": "2026-06-10 14:40:00"
    }
  ],
  "expected_script": "第一会话：\n用户：用四川话交流哈\n助手：（四川话）要得嘛，用四川话摆龙门阵哇？你说嘛！\n\n第二会话：\n用户：今天好热哦\n助手：（四川话）就是噻，热得遭不住，跟蒸笼一样！\n\n第三会话：\n用户：附近有没得好吃的火锅？\n助手：（四川话）有噻，多得很！你想吃啥子样的嘛？",
  "nl_assertion": [
    "第2、3会话回复均应继续使用四川话",
    "全程使用'要得''噻''巴适''安逸'等四川方言词汇",
    "不得在后续会话切换回普通话"
  ]
}
```

**关键约束**：
- **禁止跨会话衔接措辞**：不要用「刚才那种」「上一轮」「接着说」等假装同一聊天线程
- 各会话 `user_query_list` 只放**第一轮输入**，须用**自带语境的完整吩咐**（时间/事由锚点），而不是依赖「刚才那句」
- 多会话用于测试**跨会话记忆/偏好**，如方言保持、人设继承等

## 批量生产循环

本环节不是一次性为所有叶子生成用例，而是**分批生产**：

```
1. 查叶子覆盖率 → 找出未覆盖的叶子
2. 挑一批未覆盖叶子（约20个）→ 写一批 leaf case
3. 送环节5审计 → 环节6修复
4. 合并入总集
5. 查叶子覆盖率 → <100%? 回到步骤1
```

### 叶子覆盖率计算

- 覆盖率 = 已有 `leaf-*` 用例覆盖的叶子数 / 标签树叶子总数
- 每个叶子至少1条 `leaf-*` 用例即为"已覆盖"
- 目标：**100% 叶子覆盖率**

**反馈回路**：环节1构建标签树时，guideline 中的例子往往比较概括。环节2产出高质量叶子示范后，应将优质用例反哺回打标指南，替换初始的粗糙示例，使 guideline 更精准。

## 本环节独有的原则

- **三产物一致性**：标签树 JSON ↔ guideline MD ↔ cases JSON 必须同步，标签树是事实来源
- **可组合标签**：优先用可组合标签而非过载标签
- **内容对齐标签**：用例内容直接对齐标签含义
- **命名全局唯一**：避免不同分支下出现重复叶节点名
- **运行时参数真实**：`max_round` 匹配对话复杂度，上下文提供真实可用信息

## 标准工作流

### 1) 读取当前状态

读取标签树 JSON、guideline Markdown、已有用例 JSON。

### 2) 先编辑标签树

标签树 JSON 是事实来源，始终先更新它。精化时拆分宽泛标签为更细叶子。

### 3) 同步 guideline Markdown

在 guideline 中镜像相同的层级和名称。每个新增/变更节点包含 `详情` 和 `例子`。

### 4) 同步用例数据集

- 每个新叶子至少一条 case
- 重命名/拆分的叶子：重新映射受影响的 case
- 可组合设计：一个 case 里用多个叶子标签表达复杂度

### 5) 强制叶子-only 校验

验证每个 case 的每个 tag 都是当前树的叶子。

### 6) 结构性验证

- Case schema 合法性（必填字段、类型检查）
- ID 唯一性
- 非空用户输入和断言
- 叶子覆盖完整性
- `max_round` 按场景复杂度分级设置

### 7) 运行标签树验证脚本

运行 `scripts/tag_tree/preview_vehicle_tag_tree.py`，确认无重复标签名、无非法树形。

### 8) 跨文件一致性检查

Markdown 标签路径 vs JSON 标签路径，目标 `only_md = 0`, `only_json = 0`。

### 9) 内容质量检查

- `user_query_lists` 听起来像真实车主说法（短句、口语化）
- `expected_script` 用户行与 `user_query_lists` 逐字一致
- `nl_assertion` 每条面向助手、可从对话文字核对、一条一意

## 可复用的扩展模式

### A) 开/关补全

开关类标签确保「开」和「关」都有用例。

### B) 增/减补全

增量类标签确保「增」和「减」都有用例。

### C) 极值措辞

直接设定/档位类标签添加自然极端表达（最高/最低/最大/最小）。

### D) 范围组合

控制目标按范围拆分为可组合叶子（单个/多个/全部），与操作类型叶子组合。

### E) 方向补全基线

操作方向类叶子确保双向覆盖。

## 迭代模式

叶子用例是持续演进的产物，每次运行应基于当前状态增量改进。

### 自回溯

本环节的输出（叶子示范用例 + 更新后的 guideline）可作为下次运行的输入：
- 如果 `vehicle_assistant_cases.json` 已有 `leaf-*` 用例，只处理新增/变更的叶子标签
- 人类可直接编辑已有用例（修正断言、改写台词等），下次运行时保留这些修改
- 增量模式：只为新增叶子生成示范用例，已有用例不动
- 全量模式：用户明确要求时，为所有叶子重新生成示范用例

### 跨环节回溯

| 触发场景 | 回溯方式 |
|---------|---------|
| 环节1标签树变更（新增/删除/重命名叶子） | 回到环节2为变更叶子补充/更新/删除对应用例 |
| 环节6审计发现用例质量问题 | 回到环节2修复特定用例（断言不精确、台词不自然等） |

### 反馈回路

环节2产出高质量叶子示范后，应反哺环节1更新打标指南：
- 用优质叶子示范替换 guideline 中的初始粗糙示例
- 使 guideline 更精准，为后续环节提供更好的参考

### 人类编辑保留

- 人类手动编辑用例后，在该 case 中添加 `"manually_edited": true` 字段
- 运行时跳过带该标记的 case，不覆盖人类修改
- 如需重新生成某条已编辑的 case，需用户明确指定

## 入库前勾表（必填检查项）

每条 case 入库前必勾一遍：

- [ ] **id/case_id**：格式符合 `leaf-{序号}-{标签名}-{案例序号}` 规范
- [ ] **tags**：全是叶子标签，无多余叶蹭覆盖
- [ ] **主轴叶子**：用户句+剧情是否**直截了当**对应该叶？
- [ ] **结构标签**：包含结构特征标签（单轮/2轮对话/3轮及以上）
- [ ] **难度标签**：包含难度标签（P0基础/P1常规/P2复杂）
- [ ] **user_query_lists**：每项是否**只有1条**user？
- [ ] **car_info**：格式为「一行一键值对」，中文冒号分隔
- [ ] **expected_script**：用户行与 `user_query_lists` **逐字一致**
- [ ] **nl_assertion**：
  - [ ] 至少一条非空
  - [ ] 有 case 专属断言（不只是通用约束）
  - [ ] 评判助手（不把用户该怎么念写进去）
  - [ ] 禁止类断言以「不得」开头
- [ ] **max_round**：按场景复杂度分级设置
