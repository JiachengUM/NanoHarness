# Jev Lab — 决策模型快慢分工实验

> Jev 是 TypeSafe AI 的 System One 决策模型：**不生成文字，直接输出类型化的概率决策**。
> 本目录验证它在本项目车载语音 Agent 架构中的落点——替代 LLM 做高频、原子化的"快判断"。

## 一句话理解 Jev

LLM 路由 = 生成结构化结果，再交给程序消费；可使用 JSON Schema 约束格式，实际速度与判断质量需要测量。
Jev 路由 = 一次 API 调用直接返回**强类型 + 校准概率**的判断结果：

```
route            = "car_control"     ← 选哪个（Choice）
confidence       = 1.00              ← 分布有多收敛
needs_reasoning  = 0.04              ← 是否需要慢思考（Noul，0-1 概率）
risk             = 0.10              ← 错误执行后果（Score，3 档量表）
```

代码可以直接消费类型化答案，但类型正确不等于判断正确。概率校准是训练目标；业务阈值仍需用领域数据验证，不能把单次返回值当成可靠性证明。下方 demo2 实测展示了速度与输出差异。

## 三个原语

| 原语 | 干什么 | 返回 | 车载场景例子 |
|------|--------|------|--------------|
| **Choice** | 单选（≤255 项） | 选中项 + 完整概率分布 + confidence | 工具路由、枚举槽位（温度档/模式） |
| **Noul** | 是非判断 | 0-1 概率（≈0.5 = 证据对半） | "是否简单意图"、"是否需确认" |
| **Score** | 有序量表（2-10 档） | 加权分数 + 档位分布 + confidence | 风险等级、情绪程度 |

按[官方接口说明](https://docs.typesafe.ai/primitives)，一次调用可混合多个问题，针对同一 state 并行、独立评估。问题数增加对时延的影响需单独测量；本次八问对照不能证明“多问不增时”。

## 三个核心技术亮点（为什么 Jev 值得关注）

### 1. 任务从训练阶段固定 → 上下文中定义（In Context Learning）

传统决策模型（分类器/小模型路由）的能力边界在训练那一刻就被冻结了：训练时没见过的意图类别，部署后无法处理，改能力 = 重新标注 + 重训。

Jev 的"任务"（问什么、选项是什么）完全在推理时由请求定义——**questions 就是任务本身**：

```python
# 不需要任何训练，下一条请求就能定义一个全新任务
questions = {
    "route": Choice(instructions="...", criteria={"新工具A": "...", "新工具B": "..."}),
    "is_roadtrip": Noul(instructions="用户是否在规划自驾游？"),   # 全新判断维度
}
```

工程含义：**工具清单即配置**。新增一个工具/意图，改 `ROUTES` dict 下一条请求立即生效，与 LLM 的 prompt 一样灵活，但响应速度是决策模型级的。

### 2. 以校准决策概率为训练目标（RLCD）

官方将 **RLCD** 定义为 **Reinforcement Learning for Calibrated Decisions**。理想校准意味着：许多预测概率约为 0.9 的事件中，实际约 90% 发生。这是批量统计性质，不是单个答案的保证。见[官方训练目标说明](https://docs.typesafe.ai/introduction/machine-learning-primer)。

需要区分三个概念：

- **probabilities / noul**：选项或事件的预测概率；校准评估需对照大量不同、有人工作为参考标注的样本。
- **confidence**：由概率分布计算的集中程度指标；`confidence=0.8` 不等于“80% 正确率”。见[官方 Confidence 定义](https://docs.typesafe.ai/confidence)。
- **重复稳定性**：同一输入多次返回接近的答案。它有助于工程可预期性，但稳定的判断也可能是错的。

当前 `CONFIDENCE_MIN = 0.8` 等值是实验门槛，应以快路径覆盖率和错误执行率验证。demo2 本次结果支持讨论输出稳定性与不确定性表达，**没有验证校准**。

### 3. 输出从自回归生成字符串 → 并行产生类型化决策

生成式 LLM 通常自回归地产生输出 token。单请求八问可以摊薄调用开销，并使用 JSON Schema 约束结果；因此公平对照应包含批量与并发，而不能只比较串行八次调用。

Jev 的接口直接提供**类型化决策对象**（Choice/Noul/Score），以并行评估提供多个判断，不生成自由文本。实际端到端收益还受网络、服务负载和问题规模影响。

工程含义三连：

| | 自回归 LLM | Jev |
|---|---|---|
| 输出 | 字符串（需解析） | 类型化对象（直接 `.choice`/`.noul`） |
| 多问题 | 可批量生成，也可并发请求 | 单请求独立评估多个问题 |
| 正确性 | Schema 可约束格式，语义仍需验证 | 类型与候选空间受约束，语义仍需验证 |

这三个方向分别是任务配置、概率训练目标和输出接口。它们提供了值得验证的工程能力，不等于已经在本项目中证明准确率、校准或全面的速度优势。

## 快慢分工架构（核心实验）

```
用户输入 ──> Jev 快判断（一次调用 ~250-600ms）
                │
                ├─ ⚡ 快路径：简单意图 + 工具可直接执行
                │    跳过 ReAct 多轮 + 跳过 LLM 生成，直接调工具 worker
                │
                └─ 🐢 慢路径：复杂/模糊/多工具意图
                     进 ReAct（LLM 慢思考 + 异步工具 + 结果回灌）
```

实测分流效果：

| 输入 | Jev 判断 | 路径 |
|------|---------|------|
| "打开车窗" | car_control conf=1.00 | ⚡ 快路径直接执行 |
| "暂停播放" | media conf=1.00 | ⚡ 快路径直接执行 |
| "播放周杰伦的晴天" | conf=0.72（media/music_search 职责重叠） | 🐢 慢路径，LLM 精细决策 |
| "查天气+找酒店+推荐歌" | 多工具组合 reasoning=0.37 | 🐢 慢路径，并发创建 3 个任务 |
| "你叫什么名字" | chitchat conf=0.98 | 🐢 慢路径，需 LLM 生成文本 |

快路径判据（阈值可调）：`needs_reasoning < 0.4 且 confidence ≥ 0.8 且 risk ≤ 0.7 且工具在白名单`。

## demo2：四方案时延对照

四种方案使用相同的客诉 state、问题说明和判据。默认对照模型是 `doubao-seed-2-0-mini-260428`，关闭思考，temperature=0；Jev 默认 `jev-latest`。先从仓库根目录运行一轮验证：

```bash
/Users/jiachexu/Code/mind/.venv/bin/python -m aicore.v2.experiments.jev_lab.demo2 --repeats 1 --warmup 0
```

正式重复比较八问，或比较问题数增加后的耗时：

```bash
/Users/jiachexu/Code/mind/.venv/bin/python -m aicore.v2.experiments.jev_lab.demo2 --repeats 10 --warmup 1
/Users/jiachexu/Code/mind/.venv/bin/python -m aicore.v2.experiments.jev_lab.demo2 --question-counts 1 2 4 8 --repeats 10 --warmup 1
```

这里使用经本次会话确认的 macOS 项目 `.venv`；Windows 环境应使用其对应解释器。`TYPESAFE_API_KEY` 从环境变量或本目录 `.env` 读取。小模型优先读取 `ARK_API_KEY` / `ARK_BASE_URL` 环境变量，否则沿用项目 credentials 配置。

| 策略 | 完成八问的方式 | 每轮 API 调用数 |
|---|---|---:|
| `llm_serial` | 同一小模型逐题调用，每题只提供该题与共同 state | 8 |
| `llm_batch` | 同一小模型一次返回八个 JSON 字段，主要公平基线 | 1 |
| `llm_concurrent` | 同一小模型同时发起八次单题请求 | 8 |
| `jev_batch` | 一次提交八个 typed questions | 1 |

默认 `--repeats 3 --warmup 1`，共 72 次 API 调用；一轮八问冒烟为 18 次。不同策略整组顺序随机打乱、彼此不重叠；`--seed` 控制顺序。`--question-counts` 使用原八问的前 N 个，`--warmup` 对每个问题数、每种策略都执行指定轮数。两端自动重试均禁用；`--timeout` 是每次调用的超时，因此串行八问整组可能耗时接近八倍 timeout。

报告默认写入本目录 `results/demo2_<UTC时间>.json`，也可用 `--output /tmp/jev-comparison.json` 指定新文件，不覆盖现有文件。每完成一组即保存：

- 每次调用与整组耗时，单题/整组成功或失败状态；失败只记录异常类型，避免泄露 SDK 请求信息。
- 各方案的共同判断字段、小模型原始 JSON、usage 和返回模型版本；Jev 完整原生响应。
- 输入、问题、运行参数、预热记录、正式记录，以及成功整组的 p50 / p95 和失败数。

计时从请求准备到答案解析及校验完成，复用客户端，不计客户端创建、终端打印和报告写入。并发方案计时是等待全部请求结束的墙钟时间，不是单请求耗时相加。预热不计入统计；失败不伪装成低延迟成功结果，正式轮次有失败时程序返回非零退出码。

为避免额外输出拖慢小模型，其 JSON 只包含 Choice 的选项、Noul 的 yes 概率和 Score 的加权分数，不要求生成解释、confidence 或完整分布。Jev 原生分布另存于报告。Schema 校验只代表格式有效，不代表语义正确或概率校准；这是同一业务判断任务的服务级比较，不是相同响应字节数的推理内核比较。替换 `--model` 时需支持当前方舟 Chat API 的 strict JSON Schema 和关闭思考参数；不支持会如实计为失败，不自动换成更宽松格式。

这是一条固定客诉的演示，p95 在少量轮次下仅供参考；重复相同输入也可能受缓存、网络和配额影响。展示时应同时查看答案与失败数，不能仅由耗时推导 Jev 比所有小模型快，也不能据此证明校准。

## demo2 实测：2026-09-22

原始报告：[demo2_20260922T060238055814Z.json](results/demo2_20260922T060238055814Z.json)。本节从该报告核对，不是新增运行。

- 输入：同一条英文客诉，内容为重复扣费、表达愤怒、要求当天解决，否则注销账户。
- 规模：每方案 1 轮预热 + 3 轮正式八问，共 72 次 API 调用；预热与正式调用全部成功，正式完整判断为每方案 3/3 成功。
- 模型：`doubao-seed-2-0-mini-260428`；Jev 请求别名 `jev-latest`，实际返回版本 **`jev-1.13.0`**。
- 以下时延均为完成整组八问的墙钟时间；预热排除。p95 为 3 个样本的插值结果，不能视为可靠的尾延迟估计。

### 时延：显著优于串行，未胜过批量基线

| 方案 | 单轮 API 数 | 正式成功 | p50（ms） | p95（ms） | 正式耗时范围（ms） |
|---|---:|---:|---:|---:|---:|
| 小模型串行 `llm_serial` | 8 | 3/3 | 5584.5 | 6341.8 | 4419.0–6425.9 |
| 小模型批量 `llm_batch` | 1 | 3/3 | **1117.6** | **1380.9** | 874.9–1410.2 |
| 小模型并发 `llm_concurrent` | 8 | 3/3 | 1370.4 | 1914.5 | 820.8–1974.9 |
| Jev 批量 `jev_batch` | 1 | 3/3 | 1265.2 | 2289.1 | 710.4–2402.9 |

按 p50 比较：

- **对比小模型串行**：Jev 耗时降低 **77.3%**，串行耗时约为 Jev 的 **4.41 倍**。
- **对比小模型批量（主要公平基线）**：Jev 耗时高 **13.2%**，本次批量小模型更快。
- **对比小模型并发**：Jev 耗时低 **7.7%**，但仅三轮且范围重叠，不足以证明稳定优势。
- Jev 正式三轮为 710.4 / 1265.2 / 2402.9 ms，存在明显波动；不能只选最快的一轮作结论。

**可用于演讲的结论：同一输入八问时，Jev 与小模型批量、并发均达到约秒级，明显优于串行；本次并没有证明 Jev 比优化后的小模型调用更快。** “明显”描述本次观测幅度，不是统计显著性检验。批量小模型本身已大幅改善串行开销，因此不能把全部收益都归因于 Jev。

### 输出：本例 Jev 重复结果接近，调用组织方式影响小模型答案

下面列出三轮正式输出；这些字段均为 Noul 概率，不是 `confidence`。

| 判断 | 小模型串行 | 小模型批量 | 小模型并发 | Jev 批量 |
|---|---|---|---|---|
| 隐含或明确退款诉求 `refund_requested` | 0 / 0 / 0 | 0 / 0 / 0 | 0.8 / 0 / 0 | **0.91 / 0.90 / 0.90** |
| 主要问题是否为技术故障 `technical_issue` | 0.9 / 1 / 1 | 0 / 0 / 0 | 1 / 0.9 / 1 | **0.52 / 0.52 / 0.51** |

另外，所有方案三轮的主意图均为 `billing`；负面程度大多为 2，小模型串行第三轮为 1.667。Jev 的 urgent / angry / churn_risk / human_needed 分别在三轮中保持 0.93 / 0.98 / 0.91 / 0.86。

两个适合现场讨论的例子：

1. **退款诉求**：题目明确包含“implicitly requesting”。从业务解释看，重复扣费并要求解决可以暗示退款；Jev 三轮均赋予较高概率，而小模型多数为 0。这值得人工复核，但没有标注标准时，不能直接宣称 Jev 正确、小模型错误。
2. **技术故障**：客诉没有交代扣费原因。Jev 返回接近 0.5，表达了不确定性；小模型串行/并发接近 1，批量则全部为 0。说明本例中判断对请求组织方式敏感，但不能单凭此例确定差异的原因。批量结果本身也三轮稳定，不能概括为所有小模型输出都不稳定。

**可用于演讲的结论：本例 Jev 返回了重复接近、可区分不确定程度的概率；这是输出行为观察，不是领域校准或准确率证明。**

### 这次未验证什么，下一步怎么补

- **未验证“多问几乎不增时”**：这里只有八问；需在相同 state 下比较 1 / 2 / 4 / 8 问。
- **未验证概率校准**：重复同一客诉三次不等于三个独立标注样本。需不同输入与人工标签，比较概率分箱均值与事件实际发生率；不要将 confidence 分箱直接解释成校准正确率。
- **未验证总体质量与生产时延**：需覆盖清晰、模糊、否定、复合等输入，增加重复次数并同步报告准确率、失败率和时延。当前缺少网络/部署位置测量，不能把差异完全归因于模型架构。

## 其他原型的历史观察

以下保留先前演示背景，不属于上述 demo2 对照结果：

1. **路由接口**：`agent_router.py` 展示了工具路由、复杂度、风险与确认需求；早期 README 记录过 10 例路由观察，但缺少对应标注和完整结果，不作为准确率评测。
2. **快路径接入**：车控/媒体 worker 接受自然语言 command，可绕过上层 ReAct；真实链路仍依赖下游 FC 提槽，mock 成功也不等于真实工具已验证。
3. **概率消费**：代码可以依据分布和阈值分流，但本目录尚无领域校准验证；单个两可输出不构成校准证据。

## 已知边界

- **开放槽位提不了**：歌名、地址等自由文本需要生成能力，Jev 只能做封闭枚举（Choice）——所以天气/POI 工具（需结构化参数）即使路由明确也走慢路径
- **不能生成文本**：chitchat/reasoning 必须走 LLM，快路径只对"路由到工具的简单指令"开放
- **火山 FC PPE 环境不稳**：服务端 `vehicle.model.data_provider_for_model` 在 lf 机房无实例且禁止回退（取号 400），实验默认用 mock worker 隔离

## 在整体架构中的位置

Jev 不是替代规则层，而是插在规则和 LLM 之间的**语义泛化层**：

```
规则 explicit call（毫秒级、零成本、确定性提槽）
        ↓ 未命中
Jev 快判断（~0.5s、语义泛化、接住规则覆盖不到的变体表达）
        ↓ 复杂/模糊
LLM ReAct 慢思考（多步推理、开放生成）
```
