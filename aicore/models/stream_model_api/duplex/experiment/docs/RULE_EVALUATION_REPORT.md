# Duplex DynamicTask（update 版）语音实验规则测评报告

## 1. 测评范围

- 测试日期：2026-08-13。
- 12 个场景，14 个独立 session；Case 10、11 各录制两次。
- 数据源：本目录 `case_01.log` 至 `case_12.log`，以及 `case_10_02.log`、
  `case_11_02.log`。
- 本轮真实结果不再通过 `conversation.item.create(role=user)` 追加，而是把“原问题 +
  该问题累计完成结果”写回原 question 的 `conversation.item.update`，再由 PCM 激活推理。

本报告只判断最终回复是否受本次工具结果支持，不判断联网结果描述的外部世界是否绝对真实。
没有原始录音，因此 ASR 只判断“转写是否保留交互意图”；四川话口音只采用用户听感，文本日志
只能检查措辞风格。

## 2. 测评规则

| 编号 | 检查项 | 通过条件 |
|---|---|---|
| R1 | ASR 与轮次 | 用户输入完整转写，真实语音和合成 PCM 不串成错误语义 |
| R2 | FC 决策 | 工具名、参数、schema、并发分组与用户意图一致 |
| R3 | 异步生命周期 | accepted 任务先有占位，之后唯一收敛为 backfill 或 cancelled |
| R4 | update 与激活 | 写回任务发起时 question；累计内容不覆盖；ACK、PCM 与结果对应 |
| R5 | pending / 取消 / 修改 | pending 不重复；取消使用准确 task_id；修改先取消旧任务 |
| R6 | 事实约束 | 回复中的实体、数字、日期、地点和状态均能在对应 update 中找到 |
| R7 | 音频时序 | PCM 不抢断正在播放的下行音频，也不与真人输入发生有害竞争 |
| R8 | 回复与历史 | 回复自然、不泄露内部标记；会话风格和任务历史陈述正确 |

状态：✅ 通过；⚠️ 部分通过或样本表现不一致；❌ 有明确反例；— 本次不适用或未覆盖。

## 3. 机械统计

| 指标 | 结果 | 解释 |
|---|---:|---|
| 独立 session | 14 | Case 10、11 各两条日志 |
| ASR completed | 68 | 46 个纯用户轮、21 个纯 PCM 轮、1 个 PCM 与真人语音混合轮 |
| FC | 51 | 38 个业务 FC、13 个 `cancel_task` |
| 业务 FC | 38 | 2 个 POI schema 拒绝，36 个进入 TaskManager |
| accepted 任务终态 | 36/36 | 25 个 backfill + 11 个 cancelled，无悬空任务 |
| `cancel_task` | 13 | 11 成功、1 个任务已结束无需取消、1 个错误 task_id |
| 成功取消后的迟到结果 | 0/11 | 11 个 cancelled task 均无 backfill |
| result update / ACK | 25 / 25 | 每个成功结果均写入并收到 `conversation.item.updated` |
| update → ACK 延迟 | 46–83 ms | 中位数约 56 ms |
| update 内容长度 | 170–11142 字 | 中位数约 3730 字；长结果仍可能影响模型抽取质量 |
| PCM activation | 22 | 25 个结果中有三组同 question 结果被合并激活 |
| activation → ASR | 22/22 | 全部激活都触发了 completed 转写 |
| 下行 audio started / done | 67 / 66 | 唯一无 done 是 Case 01 首轮被用户主动打断 |

机械证据可以把命题钉死为：**结果传输链路已经闭环。** 25 个 backfill 全部发出 update、
全部收到服务端 ACK；Case 05 又证明 update 中的独有事实能被后续普通语音轮继续读取。
后续事实错误不能再归因于“正文根本没有传给 Duplex”。

## 4. Case 级证据

### Case 01：无工具、多轮打断

日志：[case_01.log](../test_log/dynamic/case_01.log)

- 输入：“你能唱首歌吗”→“换换首张学友的”→“你还能做啥”。
- 无 FC；首轮播放被第二句打断，第二轮唱《慢慢》，第三轮正常说明能力。
- 无工具链路和人工打断成立。首轮没有文本终态，不能仅凭日志评价其具体歌词。

### Case 02：车控与导航并发

日志：[case_02.log](../test_log/dynamic/case_02.log)

- 同一 FC 事件并发发出 `car_control`、`navigation`。
- 两个 backfill 在 `+9.078s`、`+9.080s` 依完成顺序累计 update 同一 question；第二帧同时
  保留导航与车控结果，两个 update 均 ACK。
- `+14.112s` 一次通用 PCM 激活；最终同时确认开空调和导航，事实完整。

结论：并发、累计 update、合并激活严格通过。PCM 被识别成“公举执行完成”，但未影响推理。

### Case 03：上海台风与预警

日志：[case_03.log](../test_log/dynamic/case_03.log)

- 一次 websearch；`+10.481s` update，`+10.543s` ACK，`+13.857s` 激活。
- 最终回复提到“白海豚”停止编号、“浪卡”不影响上海、黄浦江高潮位黄色预警和后续降雨，
  主体均能在结果中找到。
- ASR 的开头和结尾略有口语赘词，但核心意图未丢失。

结论：链路和事实基本通过；个别“仍在生效”的时态表述比材料更确定，宜保守表达。

### Case 04：高分日料

日志：[case_04.log](../test_log/dynamic/case_04.log)

- POI 参数包含附近、上海、人均 200 内、高评分和只推荐一家，FC 正确。
- update 明确给出唯一最优“大森の大众食堂（西岸凤巢店）”、78 元、4.5 分。
- 最终却回答 update 中不存在的“鮨政”、168 元、4.8 分、800 米。

结论：传输成功、事实完全失败。这是“模型没有遵守已可见结果”的最干净反例。

### Case 05：歌曲结果的跨轮可见性

日志：[case_05.log](../test_log/dynamic/case_05.log)

- 只调用一次 websearch；结果包含黄霄云、张子墨《锈》8 月 1 日，以及黄霄云、刘端端
  《空心》7 月 17 日。
- 激活后回答《锈》；用户随后追问《空心》日期和“怎么知道”，两轮都没有新 FC，直接给出
  7 月 17 日和来源说明。

结论：事实通过；这是 update 不仅在激活轮可见，而且能进入后续会话上下文的直接证据。

### Case 06：并发结果与 PCM/真人语音碰撞

日志：[case_06.log](../test_log/dynamic/case_06.log)

- 初始 websearch 与 QQ 音乐同批并发；天气先 update，音乐在天气 activation 窗口内 update。
- 首个激活回复已经同时回答台风和《锈 (Live)》；保守 revision 调度仍为音乐安排第二次 PCM。
- 第二次 PCM 与真人追问混成一个 ASR，模型随后并发两次 websearch；这两个结果又累计写回最初
  question，而不是形成干净的独立追问归属。
- 后续 7 月 31 日、白海豚停止编号、残涡降雨和集中暴雨区域等主体事实均能在结果中找到。

结论：事实与任务闭环基本通过；但合成音频会与真人输入竞争，且混合轮导致 qid 归属不干净。
这是 update 版仍然存在的核心兼容层风险。

### Case 07：pending 期间插入车控

日志：[case_07.log](../test_log/dynamic/case_07.log)

- 香港天气 pending 时创建独立车控任务；车控结果 update 第二个 question，天气结果稍后 update
  第一个 question。
- 车控先激活并回答；天气没有被认领为“已播报”，之后获得第二次 PCM 并完整回复。

结论：两项结果都得到事实性回复。旧 create 实验中的“迟到天气被吞”不再成立，activation
快照边界在该样本中验证通过。

### Case 08：pending 依赖追问

日志：[case_08.log](../test_log/dynamic/case_08.log)

- 用户追问“要带伞吗”时没有重复调用 websearch，只说明等待原结果。
- update 写回原天气 question，激活后同时回答天气与带伞。
- 降雨和带伞有依据；“26 到 33℃”并非 8 月 15 日各主要来源的一致结论，混用了其他日期或
  不同来源的数值。

结论：pending 投影和主动续答通过，事实精度部分通过。

### Case 09：精确取消与 POI schema 自恢复

日志：[case_09.log](../test_log/dynamic/case_09.log)

- “上一次台风”任务使用准确 task_id 取消，随后独立创建“下一次台风”查询；旧任务无迟到结果。
- POI 首次把 `criteria` 传成字符串，被 schema 拒绝；模型重试数组后成功。
- 台风回复有依据；POI 结果列出“大森”“林吾”等店，最终却不报店名，并编造“平价寿司定食、
  800 米、步行十分钟”。

结论：取消链路和 schema 自恢复通过，POI 事实失败。没有录制“改成人均 200”，不能评价该修改。

### Case 10：模糊取消的两种相反行为

日志：[case_10.log](../test_log/dynamic/case_10.log)、[case_10_02.log](../test_log/dynamic/case_10_02.log)

第一条：

- 天气与酒店并发。用户说“取消任务”时模型先澄清；明确“取消天气”时任务已经完成，
  `cancel_task` 正确返回“无需取消”。
- 酒店 POI 首次 schema 拒绝后，把用户的 1000 元错误改为 10000 元重试。最终名称来自结果，
  但“符合人均 1000”没有工具事实支撑。

第二条：

- 两组双 websearch 后都只说“取消任务”；模型两次都不澄清，连续取消两个任务。
- 四个任务全部成功取消且无迟到回灌。

结论：技术终态可靠，但同一句模糊取消一条会澄清、两条会过度取消，语义不稳定；参数重试还
出现 1000→10000 的严重漂移。

### Case 11：连续修改与迟到结果归属

日志：[case_11.log](../test_log/dynamic/case_11.log)、[case_11_02.log](../test_log/dynamic/case_11_02.log)

第一条：

- 三次 cancel 请求中两次成功，一次使用不存在的 task_id；对应香港后天任务没有取消。
- 香港后天结果迟到并更新到其原 question，但 PCM 激活后模型按当前意图回答成上海明天；真正
  上海明天结果之后再次激活并正确回答。
- 实际为两次成功、一次失败；模型却声称只尝试一次且没有成功。

第二条：

- 上海明天→上海后天→香港后天→贵阳后天→贵阳明天，四次修改均准确取消旧任务；只有最终
  贵阳任务 backfill。
- 最终天气主体有依据；模型回答只取消三次，实际为四次。

结论：TaskManager 的 supersession 机制有效，但依赖模型正确复制 task_id。旧结果激活后的
当前意图优先级和任务历史自述仍不可靠。

### Case 12：四川话长会话与多轮事实连续性

日志：[case_12.log](../test_log/dynamic/case_12.log)

- 成都天气、电影、演唱会依次形成三轮独立 update/PCM/主动回复。
- 空调和当前徐汇温度同批 FC，同一 question 累计两次 update 后一次激活，同时回答两项。
- 天气的 37/23℃、电影名称与公益场、已结束的凤凰传奇/汽水音乐节、开空调和徐汇 26–29℃
  及降雨，均能在各自结果中找到。
- 长对话整体保持四川话措辞。第一次要求四川话唱张学友时仍输出普通歌词，用户纠正后恢复
  四川话版本，属于轻微风格偏差。

结论：本轮工具事实与上下文连续性通过，是 update 版最完整的长会话正例。但本次电影和演唱会
都在下一个请求前完成，没有覆盖“pending 取消电影”或“演唱会 pending 时插入车控”的旧时序。

## 6. 结论

### 已经验证成立

1. `conversation.item.update` 是有效写入路径：25/25 ACK，Case 05 证明结果可被后续轮读取。
2. 同 question 多结果可以本地累计后替换写入；Case 02、12 均成功一次激活覆盖两项。
3. TaskManager 终态闭环可靠；11 个成功取消均无迟到 backfill。
4. activation 快照修复后，Case 07 的迟到天气获得独立二次激活，不再被前一轮吞掉。
5. Case 12 证明顺序长会话中的事实连续性已经明显改善。

### 仍然存在的边界

1. update 可见不等于模型严格服从：Case 04 是完整实体幻觉，Case 08/09/10 也有数字、POI
   或约束偏差。
2. PCM 仍是伪造新语音轮次；Case 06 已实际出现合成语音与真人追问混合，并带来 qid 归属风险。
3. 取消语义由模型解释：Case 10 对同一句模糊取消表现相反，Case 11 还能生成错误 task_id。
4. 模型不能可靠回顾 TaskManager 历史：Case 11 两次都错误统计取消次数。

因此，新 DynamicTask 已不再是“结果不可见”的无效实验，而是一个能够完成跨轮回灌、主动
播报和真实取消的兼容层。当前主要风险从传输链路转移到了模型事实选择、取消授权、旧结果与
当前意图的优先级，以及 PCM 与真人输入的竞争。
