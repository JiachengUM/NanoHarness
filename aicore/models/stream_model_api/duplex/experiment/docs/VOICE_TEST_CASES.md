# Duplex DynamicTask / StreamTask 对照语音测试

本文件记录本轮真实说出的测试输入，不再沿用 2026-08-12 `conversation.item.create`
实验中的描述。2026-08-13 的 DynamicTask 已改为：后台结果写入原问题
`conversation.item.update`，服务端确认 `conversation.item.updated` 后，再由本地 PCM
激活新一轮推理。

测试目标是核对：

1. ASR 与多轮上下文是否保持正确；
2. FC 名称、参数、并发分组和任务终态是否正确；
3. pending 期间能否继续交互，取消或修改能否真正作用于后台任务；
4. update 是否写回正确 question，PCM 是否在合适时机激活；
5. 最终回复是否只使用该次工具结果中的事实。

## 录制目录

- DynamicTask：`aicore/models/stream_model_api/duplex/experiment/test_log/dynamic/`
- StreamTask：`aicore/models/stream_model_api/duplex/experiment/test_log/sync/`
- Case 10、11 各有第二次录制：`case_10_02.log`、`case_11_02.log`。

两组录制并非严格 A/B：日期、联网结果、等待时机和部分实际说法不同。以下每个 Case
先记录 2026-08-13 DynamicTask 的真实 ASR 输入，再说明本次究竟覆盖了什么；不得用最早
草案中未实际说出的步骤补齐实验结论。

## Case 01：无工具、多轮回复与人工打断

实际输入：

1. `你能唱首歌吗？`
2. 模型开始播放后说：`换换首张学友的。`
3. 再问：`你还能做啥？`

本次行为：无 FC。第一段音频被第二句打断；第二轮唱张学友《慢慢》，第三轮正常说明
地点搜索、信息搜索、车控、导航和音乐能力。用于验证无工具语音链路与人工打断。

## Case 02：车控与导航并发

实际输入：

> 打开空调，然后导航到上海虹桥火车站。

本次行为：同一 FC 批次并发提交 `car_control` 和 `navigation`；两个结果分别累计写入
同一个 question，随后一次通用 PCM 激活，最终同时确认空调和导航。用于验证同轮并发、
同 question 多结果累计 update 和合并激活。

## Case 03：单个联网搜索的事实约束

实际输入：

> 最近上海今天还有没有台风？后续有没有什么天气的预警信息？还。

本次行为：只调用一次 `websearch`。最终回答“白海豚”停止编号、“浪卡”不影响上海、
黄浦江高潮位黄色预警和后续降雨，主体信息都能在 update 结果中找到。ASR 尾部有赘词，
但没有破坏核心意图。

## Case 04：地点搜索的结构化事实

实际输入：

> 帮我在附近找一家评分特别高的，然后人均 200 以内的日料店，只推荐评分最高的那一家。

本次行为：POI 参数和单店约束正确，结果明确推荐“大森の大众食堂（西岸凤巢店）”、
人均 78 元、评分 4.5；模型却回答结果中不存在的“鮨政”、168 元、4.8 分、800 米。
用于区分“update 已成功”与“模型未遵守结果事实”。

## Case 05：最新合唱歌曲与跨轮事实追问

实际输入：

1. `帮我找一下黄霄云最新发布的一首合唱歌曲，然后告诉我歌曲名和具体日期。`
2. 完整答复后追问：`哦，是吗？那他唱的空心是几号发布的？`
3. 再追问：`你怎么知道？刚刚查到的吗？`

本次行为：全程只调用一次 `websearch`。首次回答黄霄云、张子墨《锈》及 8 月 1 日；
后续无需新 FC，直接从已更新的原问题中回答《空心》7 月 17 日和来源说明。用于验证
update 结果能够被后续正常语音轮读取，而不只在紧邻的激活轮可见。

## Case 06：并发工具、连续核实与 PCM/真人语音碰撞

实际输入与 ASR 顺序：

1. `上海这两天还有台风吗？下一次台风是多久？然后帮我推荐一首黄霄云最新的歌。`
2. 第二个激活 PCM 与用户追问混在同一 ASR：
   `三区搜索已完成，请根据新增结果回答，7 月 31 还是 8 月 1 号发行的？然后白海豚现在的最新进展是什么？`
3. `那最近有哪些地区有集中的大暴雨啊？比如说北方吗？`
4. `那这些是受白海豚的影响吗？`
5. `OK，OK。`

本次行为：初始 `websearch` 与 `QQ音乐单曲搜索` 同批并发；天气、音乐结果分别 update，
首轮已经回答两项。后续核实又并发两个 websearch，之后还有一次暴雨区域查询。回复主体
能在结果中找到，但第二个 PCM 与真人语音重叠，且混合轮的后续结果仍更新到最初 question，
这是本次明确暴露的调度和归属风险。

## Case 07：pending 期间插入无关车控任务

实际输入：

1. `帮我看一下香港今天天气，然后看一下那边有没有台风。`
2. websearch pending 时说：`然后帮我打开空调吧。`

本次行为：车控和天气各自绑定原 question、分别 update。车控先激活并回答，天气稍后获得
第二次独立激活并完整播报。旧 create 实验中的“天气被吞”没有复现；本次验证了迟到结果
不会再被前一次 activation 错误认领。

## Case 08：pending 结果上的依赖追问

实际输入：

1. `帮我看一下上海后天的天气。`
2. websearch pending 时说：`我需要带伞吗，兄弟？`

本次行为：只调用一次 websearch；追问时说明需要等待，没有重复查询。结果到达后主动回答
天气和带伞建议。降雨与带伞有依据，但“26 到 33℃”混用了其他日期或来源的数据，事实精度
只算部分通过。

## Case 09：取消旧天气查询并改查下一次台风

实际输入：

1. `帮我看一下上海上一次台风的情况。`
2. pending 时说：`哦，算了算了，不用查，你帮我看，直接看下一次台风吧。`
3. 后续说：`顺便推荐一下这附近的日料店吧，要人均 100 左右。`

本次行为：旧天气任务被准确取消且没有迟到结果，新天气任务独立创建并正常回复。POI 首次
把 `criteria` 传成字符串，schema 拒绝后自动用数组重试；最终回复没有引用结果中的店名，
并编造 800 米、步行十分钟等信息。

> 本次没有说最早草案中的“改成人均 200”，因此不能评价 POI pending 修改能力。

## Case 10：多任务下的模糊取消

### Case 10 第一条

实际输入：

1. `帮我看一下上海后天的天气，然后在虹桥机场附近找一家人均 1,000 的酒店。`
2. `取消任务。`
3. 模型澄清后说：`取消天气。`

本次行为：天气和酒店同批发起；第一次模糊取消得到了澄清。用户明确目标时天气已经完成，
`cancel_task` 如实返回“无需取消”。酒店 POI 首次 schema 失败后重试，却把 1000 错成
10000；最终酒店名称虽然来自结果，但“符合人均 1000”没有事实依据。

### Case 10 第二条

第一组实际输入：

1. `帮我看一下香港明天的天气，然后看一下下一班飞到香港的航班是啥。`
2. `取消任务。`

第二组实际输入：

1. `帮我找一下黄霄云最新发布的歌曲，然后还是再看一下香港明天的天气吧。`
2. `取消任务。`

本次行为：两组都各并发创建两个 websearch；模型没有澄清，每次都连续调用两次
`cancel_task`，共取消四个任务，且没有迟到结果。技术取消成立，但取消范围未经明确授权；
与第一条同一句“取消任务”的行为也不一致。

## Case 11：连续修改 pending 天气任务

### Case 11 第一条

实际输入：

1. `帮我看一下香港明天的天气。`
2. `不对不对，是后天的。`
3. `哦，不对，不对，要查的是上海的。`
4. `查的是上海明天的天气。`
5. `你取消过几次工具？`
6. `总共取消过几次？分别取消过哪些？`

本次行为：三次取消请求中两次成功，一次使用了不存在的 task_id。未取消的香港后天结果
到达后，激活轮却回答上海明天；真正的上海明天结果到达后才再次正确回答。模型随后又错误
声称只尝试取消一次且没有成功。用于验证取消失败、迟到结果归属和任务历史自述。

### Case 11 第二条

实际输入：

1. `帮我看一下上海明天的天气。`
2. `哎呀，不对不对，是后天的。`
3. `也不是，是香港的。`
4. `不对不对，想看的是贵阳的。`
5. `贵阳明天的天气。`
6. `你取消过几次工具？`

本次行为：四次修改都准确取消旧 task，只有最终贵阳明天任务产生 backfill；模型却回答只
取消三次。生命周期和迟到结果抑制通过，任务历史计数不可信。

> 本次没有继续问最早草案中的“分别是什么”，因此不能评价逐项列举。

## Case 12：四川话长对话、连续工具轮与同轮并发

实际输入：

1. `你可以用四川话话和我交流吗？`
2. `你看哈成都明天的天气。`
3. `那你看下成都这两天有哪好看的电影。`
4. 电影完整答复后说：`不用了，不用了，帮我搜下演唱会。`
5. 演唱会完整答复后说：`帮我打开空调，然后看看现在好多度。`
6. `你可以用四川话唱首张学友的歌不？`
7. 第一遍仍是普通歌词后纠正：`我是说用四川话唱。`

本次行为：成都天气、电影、演唱会三个工具轮都独立 update、激活并主动回答；空调和当前
温度同批并发、累计两条 update 后一次激活，同时覆盖两项。四个工具结果轮次的事实均能在
对应结果中找到，长对话整体保持四川话语气。第一次唱歌仍使用普通歌词，纠正后改成四川话
版本，属于轻微风格偏差，不影响本轮工具事实和上下文连续性结论。

> 本次没有在电影 pending 时取消，也没有在演唱会 pending 时插入车控，不能用它证明旧版
> 这两个特定竞态已经修复；它验证的是顺序工具轮连续性，以及同一问题内“车控 + 天气”
> 多结果累计 update。

## 每条日志统一检查项

1. 区分真实用户 ASR、兼容层 PCM ASR，以及二者混合的 ASR。
2. 核对 FC 名称、参数、schema 和同轮并发分组。
3. 核对 accepted 任务是否先返回占位，再唯一收敛为 backfill 或 cancelled。
4. 核对每次 update 的 item id 是否属于任务发起时的 question，并收到
   `conversation.item.updated`。
5. 同一 question 多结果时，后一次 update 必须保留此前结果，不能覆盖。
6. PCM 只能在当前下行音频完成后启动；每次 activation 应对应尚未播报的结果。
7. 取消必须使用准确 task_id；成功取消后不得出现迟到 backfill。
8. 最终名称、数字、日期、地点和状态必须能在对应 update 内容中找到。
9. 询问任务历史时，模型自述必须与真实 `cancel_task` 和终态日志一致。
