# 什么叫做"跑一个测试用例"——车载助手测试全流程认知对齐

> 目标读者：所有参与车载助手测试相关工作的人（用例编写、审核、数据合成、测试执行、结果分析）。
> 目标：读完本文，你能准确回答——"跑一个测试用例"到底是一个什么过程？数据合成和自动测试分别在其中扮演什么角色？
> 配套代码：数据合成见本目录，自动测试执行见 `../auto_test_and_rl_data_generator.py`。

---

## 0. 一句话版本

**跑一个测试用例 = 让一个"假人演员"以车主的身份，在预先布置好的前提条件下，与被测车机助手进行一段（或多段）真实的多轮对话来触发被测能力；对话结束后，由一个"裁判"拿着断言清单（nl_assertion）和车机日志，判定助手这一次的表现是 Pass 还是 Fail。**

它不是"发一句话看看回复顺不顺眼"，而是一个有前提、有剧本、有判分标准、有执行证据核对的完整过程。

---

## 1. 核心心智模型：一次独立测试的三段式

我们对测试的基本理解是：

> **一次独立的测试，由三部分构成——构建前提条件、验证、收尾。**

| 阶段 | 回答的问题 | 失败后果 |
|------|-----------|---------|
| **① 构建前提条件** | 助手被测的那一刻，世界是什么样？（车在什么状态？导航开着吗？在播什么歌？用户是谁、记住了什么？） | 前提不成立，被测行为根本不会发生，或不可复现——测了等于没测 |
| **② 验证** | 在这个前提下，用户说出测试意图后，助手是否**听懂了 + 做对了 +（必要时）说清楚了**？ | 这是唯一的判分区，Pass/Fail 只在这里产生 |
| **③ 收尾** | 对话怎么自然结束？车辆状态怎么恢复干净，不污染下一个用例？ | 残留状态（还在导航、还在放歌）会污染后续用例的前提，让整个测试集不可信 |

三个关键认知：

1. **这三段不是三种 case，而是每一条 case 内部的三段结构**。任何一条测试用例，无论多简单，都可以拆出这三段。
2. **只有第②段产生判分**。前提构建轮和收尾恢复轮都是"搭台"和"拆台"，不进判据。
3. **三段必须闭环**。前提要在 case 内部真实建立（生产→消费闭环），收尾要把状态还回去——不能"搭了台不拆"。

## 2. 测试现场的角色

自动测试运行时（`auto_test_and_rl_data_generator.py`）里有一个剧场，四个角色：

```
┌─────────────────────────────────────────────────────────┐
│                    测试剧场（一次 case）                    │
│                                                           │
│   假人演员(FakePerson)  ←──对话──→  被测助手(bot_to_test) │
│        │    （扮演车主，说口语台词）      │                  │
│        │                                  │ 每轮产生        │
│        │                                  ▼                │
│        │                          车机日志/trace            │
│        │                                  │                │
│        ▼                                  ▼                │
│   裁判(Judge)：对话结束后，拿断言清单+日志，判 Pass/Fail     │
└─────────────────────────────────────────────────────────┘
```

| 角色 | 是什么 | 能看到什么 | 看不到什么 |
|------|--------|-----------|-----------|
| **假人演员 FakePerson** | 一个 LLM，按人设+剧本演绎"车主" | 人设、car_info（车况/身份/偏好）、剧本 expected_script、case 预期效果、对话历史 | 助手的后台实现、记忆库内部 |
| **被测助手 bot_to_test** | 真实的车机助手（接口或语音通道） | 只有用户说出口的话 + 注入的上下文（api 模式） | 剧本、断言、人设之外的测试意图 |
| **裁判 Judge** | 另一个 LLM，测试结束后一次性判分 | 对话全程记录、人设、car_info、车机日志（trace 摘要 + 证据）、剧本、断言 nl_assertion | 助手内部决策过程、记忆库里实际存了什么 |
| **车机日志/trace** | 助手每轮的实际执行轨迹（工具调用、入参、结果、界面推送） | ——它是证据，不是角色，但**它是"助手真的做了吗"的最终事实来源** | —— |

两个容易被忽略的要点：

- **演员和裁判能看到车机 log**，所以执行结果（空调调没调、导航启没启动）从 log 核对，**不要求助手口头把执行结果念一遍**。助手只回一句"好的"也可能判通过——只要 log 显示它真的做了。
- **裁判看不到工具调用的过程细节**（调了哪个接口、参数怎么拼），只能看到执行**结果**。所以断言写"助手须执行XXX"，不写"须调用XX工具"。

## 3. 三段式如何被"编码"进一条 case（数据合成侧）

一条测试用例（`vehicle_assistant_cases.json` 里的一个元素）就是三段式的**编码**。逐字段看：

```json
{
  "id": "multi-turn-benz-001",
  "case_id": "单次多轮-导航中追问前方路况",
  "context_config": {
    "car_info": "当前系统时间：...\n当前位置：上海市浦东新区世纪大道100号\n导航状态：导航中，目的地外滩\n当前播放音乐：无",
    "profile": "普通的40岁男性中年人。"
  },
  "max_round": 16,
  "user_query_lists": [[{"role": "user", "content": "前面堵不堵啊"}]],
  "expected_script": "（前导段）...\n\n用户：先带我去外滩\n管家：（期望助手启动导航去外滩）\n用户：前面堵不堵啊\n管家：（期望助手基于当前导航查询前方路况并答复）\n用户：行，那就这么走吧\n管家：（期望助手继续导航）\n用户：算了不导了\n管家：（期望助手取消导航）",
  "nl_assertion": ["助手须基于已建立的导航任务答复前方路况。", "助手不得在未建立导航时臆造路况。"],
  "case_description": "测试导航中路况查询。前置：对话建立导航任务；验证：路况答复与实际导航一致；收尾：退出导航。",
  "tags": ["路况查询", "多轮对话_3轮", "可完成"]
}
```

| 字段 | 承载三段式的哪一段 | 说明 |
|------|------------------|------|
| `context_config` / `car_info` | **① 前提（状态类）** | 车速、档位、家/公司地址、系统时间、人设 profile、记忆库配置。原则：**叙事进 car_info，用户嘴里只说短指令** |
| `user_query_lists` | **① 前提（会话切分）** | 每个元素 = 一次**独立对话会话**（一次冷启动）。单会话多轮只放 1 条；跨会话记忆类（先记后用、间隔消费）才放多项 |
| `expected_script` | **① 前提构建轮 + ② 验证轮 + ③ 恢复轮** | 剧本 = 前导段（人设/演绎规则）+ 正文（`用户：xxx` / `管家：（期望…）` 交替）。前序轮建立任务态，中段触发被测行为，末尾恢复轮还原状态 |
| `nl_assertion` | **② 验证（判分标准）** | 裁判唯一依据的 Pass/Fail 清单。只评助手行为，每条都能勾对错 |
| `max_round` | 全程轮数预算 | = 用户台词轮数 × 2（覆盖演员重试、助手追问等剧本外轮次） |
| `tags` | 都不是——**给覆盖统计用，不给裁判看** | 标签树叶子，用于"测了什么"的覆盖率管理 |
| `code_assertion` | ② 验证（可选硬断言） | 需要严格变量级核对时才用 |

### 数据合成的几条铁律（都是三段式的直接推论）

1. **生产→消费闭环（前提必须对话生产）**：测"切歌"必须先通过对话"播放XXX"建立播放态；测"取消导航"必须先"导航到XXX"。**禁止用 car_info 预设"导航中/播放中"来代替对话建立任务态**——那测的不是真实链路，助手在真实场景里也不会凭空"正在导航"。
2. **剧本首句 = 冷启动台词**：`expected_script` 正文第一句用户台词，必须与 `user_query_lists` 里的冷启动句逐字一致，否则演员开场就乱。
3. **恢复轮保留但不作为判据**：改变车辆长期状态的 case（媒体/导航/车控/定时）末尾必须有恢复轮（"暂停播放""退出导航""关掉空调"），用自然口语，不说导演话。恢复失败**不影响**本 case 判定——它拆的是台，不是戏。
4. **前提不可架空引用**："取消刚才那个提醒"——被引用的提醒必须在本 case 内真实创建过，不能引用剧本外的虚构背景。

## 4. 三段式如何被执行（自动测试侧）

`auto_test_and_rl_data_generator.py` 的 `AutoTestAndRLDataGenerator` 是执行引擎。对每一条 case：

### 4.0 运行前：搭好干净的台

- **记忆隔离**：默认把 `case_id` 用作记忆库 `user_id`，让每条 case 用独立的记忆空间，互不串味。
- **记忆重置**（`memory_reset_mode=True`）：每轮全量测试前清空记忆，防止历史测试的残留记忆污染本轮前提。

### 4.1 构建前提条件（执行侧）

```
bot_to_test.create(context_config)          # 创建被测助手实例，注入 car_info/人设/记忆配置
对每个会话：
    bot_to_test.aupdate_context(mock_info, mock_time)   # 按会话覆盖 mock 车况和模拟时间
```

- **api 模式**（默认）：car_info 等前提直接注入被测助手，助手"天然知道"车况和身份。
- **voice 模式**：模拟真实语音通道——助手**收不到** car_info（除当前位置），车辆状态类前提仍然注入，但**身份/偏好/任务上下文类前提由假人在对话中口头"搬运"给助手**（需要导航中的前置，就先开口说"导航去XXX"）。前提构建轮次由假人自主完成，裁判被告知这些轮次不是评测重点。

两种模式共用同一份 case 数据——**case 设计不绑定测试方式**，这正是"前提用对话生产"原则的好处：对话生产的前提天然兼容两种模式。

### 4.2 验证（对话循环）

以一次会话为例（api 模式）：

```
冷启动：start_query（user_query_lists 首条用户消息）→ 发给被测助手
循环：助手回复 → 假人看着剧本+人设+助手刚说的话，回应下一句
      → 再发给助手 → ……
终止：假人说出"谢谢，退下吧，我给你打X分"（含"退下"）
      或达到 max_round（对话被强制 cut）
每轮：bot_to_test.adump_state_trace() 采集该车机执行轨迹
```

- 假人**不是照念剧本**——剧本是"参考设计"，假人根据助手的实际回复即兴组织台词（这就是 expected_script 里前导段定义演绎规则的原因：管家耳背怎么重试、让选列表时盲选第一个、助手只说"好的"时直接接下一句）。
- 假人最后给助手的**满意度评分（1-5分）**是演员的主观评价，与裁判的 Pass/Fail 是两个独立信号，前者辅助分析，后者才是判分。
- 多会话 case：逐个会话执行上述循环，历史以"第N次对话的记录"拼接后整体交给裁判。

### 4.3 判分（裁判）

对话全部结束后，裁判（Judge）一次性审阅：

```
裁判输入：
  ├─ 用户人设（profile）
  ├─ 背景信息（car_info）
  ├─ 完整对话记录（history_for_judge）
  ├─ 车机日志：每轮执行轨迹摘要（trace_summary）+ 车机端证据报告（car_evidence，如有）
  ├─ 预期剧本（expected_script）
  ├─ 预期效果（case_description）
  └─ 判分标准（nl_assertion）          ← 唯一的 Pass/Fail 依据
裁判输出：
  result: Yes / No
  reason: 结合预期效果的理由（多轮场景附逐轮分析表，每轮1-5分）
```

裁判的工作方式：

- **对照 nl_assertion 逐条勾 Pass/Fail**，结合剧本预期判断整体 result。
- **口头与日志不一致时以日志为准**：对话历史由假人生成，假人可能描述不准；日志里有明确执行记录（指令下发、界面切换、HAL 写入、播放状态）就视作已实际完成。
- **不要求助手把结果说全**：助手回复简略时，参考日志中的重要事件综合判断，不因"没在回复里念出完整信息"而判 Fail。
- 导演**不依赖标签（tags）打分**——tags 是出题与覆盖管理用的。

### 4.4 收尾（三件事）

1. **对话收尾**：假人说"退下"结束本会话（或超 max_round 被 cut，该 case 通常会因对话不完整而难通过）。
2. **状态收尾**：剧本层面的恢复轮（"退出导航""暂停播放"）在对话内把车辆状态还原——这是**工程完整性要求，不是判分点**。
3. **环境收尾**：case 之间记忆隔离/重置，保证下一条 case 的前提不被本条污染；全部跑完由 ReportWriter 汇总 markdown 测试报告（含每条 case 的通过情况、理由、逐轮分析表、标签覆盖统计）。

## 5. 用一个例子完整走一遍

**测试目标：助手能否在导航中正确答复前方路况**（三段式全程可见）：

| 阶段 | case 里的编码 | 执行时发生了什么 |
|------|--------------|----------------|
| ① 构建前提 | `user_query_lists` 冷启动句："先带我去外滩"；`expected_script` 前序轮"用户：先带我去外滩 → 管家：（启动导航）" | 假人说"先带我去外滩"，助手启动导航（log 记录导航任务建立），**前提由对话生产，不靠 car_info 预设** |
| ② 验证 | 冷启动后的剧本轮："用户：前面堵不堵啊"；`nl_assertion`："助手须基于已建立的导航任务答复前方路况 / 不得在未建立导航时臆造路况" | 假人问"前面堵不堵啊"，助手答复路况；裁判核对：答复内容与导航状态一致（从 log），断言逐条勾选 → Yes/No |
| ③ 收尾 | 剧本末尾恢复轮："用户：算了不导了"；case_description 写明"收尾：退出导航" | 假人说"算了不导了"，助手取消导航；裁判**不因**这轮的好坏改判——前面②段已定胜负 |

如果前提缺失（冷启动直接问"前面堵不堵"），正确的助手行为是反问或说明当前未导航——这就变成了另一条 case（未导航时问路况应拒答），而不是本 case 的失败。**前提决定测什么，断言决定对错。**

## 6. 常见误解 FAQ

**Q1：跑一个 case 不就是发一句话看回复对不对吗？**
不是。是"布好前提 → 多轮对话触发被测行为 → 拿日志和断言判分 → 恢复现场"的完整过程。一句话评测没有前提、没有证据核对，也无法覆盖多轮能力。

**Q2：为什么前提不能直接写在 car_info 里让助手"知道自己在导航中"？**
因为那测不到真实链路。真实世界里"正在导航"是用户先说了"导航去XXX"的结果。用 car_info 预设任务态 = 跳过了链路中最容易坏的一环（生产），只测消费。原则叫**生产→消费闭环**。

**Q3：助手只回了句"好的"，算通过吗？**
看日志。log 显示空调温度真的设为 22 度 → 通过；没执行 → 不通过。口头反馈不是判据，执行结果才是。这是"执行结果从 log 核对"原则。

**Q4：恢复轮里助手没成功关掉空调，这条 case 判 Fail 吗？**
不判。恢复轮是工程收尾（避免污染下一个 case），不是被测能力的评测点。缺恢复轮在审核中只是 MINOR 建议。

**Q5：为什么电话类 case 不放进自动测试集？**
被测助手拨通电话后进入通话态，麦克风语音被切到电话通道，助手听不到后续指令，假人说"挂断"也传不到助手——测试会卡死。电话类 case 单独存档，仅供人工测试。

**Q6：tags 是裁判打分用的吗？**
不是。tags 是标签树叶子，用于出题覆盖统计和校验。裁判只看 nl_assertion、剧本、对话记录和日志。

**Q7：假人演员和裁判都能看到车机 log，那还要剧本干什么？**
剧本给演员提供"演绎方向"（该说什么、何时说），给裁判提供"预期参照"（正常流程长什么样）。假人不照念剧本，但偏离剧本核心意图的即兴会被裁判结合断言识别。

**Q8：api 模式和 voice 模式，case 要写两份吗？**
不用。case 设计不绑定测试方式：对话生产的前提天然兼容两种模式（voice 模式下假人把前提"说"给助手听）。同一份 case 两种模式都能跑。

## 7. 术语速查

| 术语 | 含义 |
|------|------|
| case / 测试用例 | 一条完整的"前提+验证+收尾"编码，JSON 结构见 `case_schema.py` 的 `TestCase` |
| 冷启动台词 | 一次会话的第一句用户话，取自 `user_query_lists` 每个会话的首条用户消息 |
| 会话 | 一次独立的多轮对话。`user_query_lists` 的每个元素一个会话；跨会话间隔/记忆消费才用多会话 |
| 前提 / 前置状态 | 被测行为成立所需的条件：车况（car_info 注入）、任务态（对话生产）、记忆（跨会话生产） |
| 生产→消费闭环 | 前提必须在 case 内通过对话真实建立，再在后续轮次消费验证 |
| 剧本 expected_script | 前导段（人设/演绎规则）+ 正文（用户/管家交替）。管家括号块写"期望助手xxx"，是期望不是命令 |
| 断言 nl_assertion | 裁判判分的唯一标准清单，只评助手行为 |
| 车机日志 / trace | 助手每轮实际执行轨迹（工具调用、入参、结果），"真的做了吗"的事实来源 |
| 前导段 | 剧本开头的演绎规则说明（人设、重试规则、盲选规则、简洁承接规则等），合法且强制保留 |
| 恢复轮 | 剧本末尾还原车辆状态的轮次，不作为判分依据 |
| 退下 | 假人结束对话的固定信号："谢谢，退下吧，我给你打X分" |
| max_round | 单会话轮数预算 = 用户台词轮数 × 2 |
| 记忆隔离 | case 间用独立 user_id（默认=case_id）隔开记忆，防止串味 |
| FakePerson / Judge / ReportWriter | 假人演员 / 裁判 / 报告写手，均为执行引擎中的 LLM 角色 |
| api / voice 模式 | 前提注入方式不同的两种执行模式：接口注入 vs 语音通道口头搬运 |

---

## 8. 总结：一句话对齐

> **我们把"测试"理解为一次有剧本的演出：先搭台（构建前提条件——状态靠注入、任务靠对话、记忆靠跨会话），再演戏（验证——用户说出意图，助手听懂并做对，裁判拿断言和日志判 Pass/Fail），最后拆台（收尾——退下结束对话、恢复轮还原车况、记忆隔离防污染）。数据合成负责把这三段编码进每一条 case，自动测试负责把这三段忠实执行出来。**
